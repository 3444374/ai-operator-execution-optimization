## 异质问答单Map试验

2026-10-11。用途：选择下一项数据组织试验，复用当前接入与已有组织器；下列五路径尚未实施。
首次[原生长度检查](../results/diagnostics/squad_native_length_20261011/README.md)已完成：调参切片90/10比值1.84127，未达到预先要求的2，停止在离线画像，真实模型调用0。
不调整条件、输入或评价分区继续运行；以下清单保留原要求，不作为已经完成的模型比较。
当前整合参照为`9d767fe3`；[接入收尾](../results/postgresql/native_adapter_integration_20261009/README.md#sema-closeout)的修复在所有相关路径保留。
本节决定接下来做什么；下方历史容量方案和旧运行数字不作为这次选点结果。

### 选择：SQuAD短答案问答，先使用LOTUS批任务接点

问题是：完整请求长度确有差异时，只改变有限候选的提交次序，能否改善整查询完成或减少等待与留存，收益是否覆盖分词和组织成本？
先检验现有简单长度次序，不新增预测模型、动态控制器、多Job或缓存方法，也不将简单长度排序称为新算法。

| 现有候选 | 适用性与本轮决定 |
|---|---|
| SQuAD v1.1 dev单Map问答 | 优先。已有原始解析、按context隔开调参与评价、短答案EM/F1评分和Map输入导出；原生上下文可能提供输入长度差异，须先按完整LOTUS消息计数确认 |
| 当前Movie情感Map | 保留为既有近同质参照；最新短Map结果用于解释执行成本，不能拼入新问答排名，也不增加一轮Movie模型运行 |
| ShareGPT首个人类消息 | 后续候选。虽有自然长度差异，但现有有限切片存在任务遵从和输出长度失败记录，先用它会额外引入质量与选样工作，见[原输入预演](../results/postgresql/data_execution_pilot_20260909/README.md) |
| BurstGPT或图像输入 | 本轮不用。前者是服务轨迹，不能直接提供同语义问答结果；后者需要另一套模型与表示资格 |

选择LOTUS，是因为当前`LM._process_uncached_messages`接点已经接收完整消息批次，位于原请求池之前，原生与SemLoom都保留原LM整批返回和解析。
DuckDB的供给仍受实际vector调用影响；Sema只能在原请求抵达服务后组织，尚不能证明原池之前的就绪时刻。
本轮不同时扩三家，不为增加候选去改它们的算子或原池；后续需要移植时再核对各自实际供给。
首轮身份是**LOTUS原生DataFrame语义API的外部输入试验**，整查询时间不标成SQL时间，也不据此声称PG已接入这一组织配置。
已有PG Map解析与组织只作复用来源；若首轮有机会信号，再另列PG匹配SQL验证。

### 输入与同方法要求

- 使用[官方SQuAD v1.1 dev](https://rajpurkar.github.io/SQuAD-explorer/dataset/dev-v1.1.json)，来源摘要与解析见[数据入口](../../data/README.md)。本机未找到原始数据目录，服务器资产状态须在后续准备时核对。
- 复用`parse_squad_dev`及`prepare_capacity_samples`的context分区和自然抽样逻辑，按LOTUS实际消息检查资格后抽样，不能原样调用其中的PG模板计数；预先采用seed20261011。
  调参、评价各512行，所选行按原文件位置排列，不预置长任务优先来削弱原序参照；容量短测只用调参的前256行。
  先列出已知开发ID/context及排除结果，再保存新清单与摘要；历史覆盖核查范围写清楚，不声称已排除所有旧实验。
- 用现有`INPUT_TEMPLATE`生成context、question和answer位置，`INSTRUCTION`要求只返回最短答案；LOTUS仍通过原生`sem_map` formatter装配消息。
  所有路径使用同一输入序、instruction、原生提示、parser、单模型与generation；一次完整调用仍对应一个问题。
  沿用temperature0、top_p1、输出上限64、一个choice、关闭算子缓存和重试；不拼提示、不拆请求、不加级联、不改变答案处理。
- **重新计数LOTUS实际生成的完整消息**，不能把`prepare_capacity_samples`按PG模板得到的token字段直接当LOTUS工作量。
  先用声明tokenizer检查输入加64不超过context4096；超出者在选择前登记，不截断，也不根据模型答案决定选样。
- 不调用模型先保存完整请求输入token的最小值、10/50/90/99百分位与最大值、变异系数、JSON字节及长度分组占比。
  调参输入的第90百分位与第10百分位之比至少为2，作为本轮机会检查的工程选择条件；评价分布照实报告，不根据结果换seed或挑子集。
  若不满足，记录“SQuAD当前自然切片不适合检验长度组织”，结束该方案，不人为补长文本、调大输出或自动换数据运行。
- 线上长度信息只来自当前已生成的完整请求。离线全量画像服务于清单选择和报告，不免费提供未来任务给组织器。
  每个SemLoom候选必须是已接纳、尚未提交的合法任务；保存实际候选数和提交次序，候选始终单项或顺序未改变时，不解释成排序收益。

### 五条路径与归因

| 路径 | 执行负责人和作用 |
|---|---|
| LOTUS原生 | 原LM/LiteLLM请求池与vLLM；保持原生方法，评价实际完整路径 |
| LOTUS＋薄转发 | 保留原LM请求池，仅在HTTP入口增加现有简单有界转发；不接Core组织器，评价普通并发控制与接入成本 |
| 同核心静态SemLoom | 当前完整任务接入、请求数控制、输入先后次序、Daft＋Ray；不在线分词，作为修复后的强静态参照 |
| 同核心静态SemLoom＋长度描述 | 同一Core、同一次序和容量，逐请求分词并记录工作描述；工作额度设为不可能限制合法请求，单独识别信息与记账成本 |
| SemLoom有限候选长度次序 | 与上一条只改变候选内的长度升序；物理准备批、worker、容量、推进、返回和观测设置全部相同 |

第一条与第二条成对说明转发的实际成本；第三条到第四条说明取得信息的成本；第四条到第五条才用于解释改变次序的增量。
第五条仍须与第三条比较净收益，并与前两条比较完整路径表现。已有接纳、释放、结果收取和期限修复不能被撤回充当弱参照。
原生HTTP与适配SDK序列化可能有字节差异：逐行核对完整JSON值、模型参数和实际token；三个SemLoom组另核对请求字节完全相同。
每条512行比较查询应恰有512个调用与512个关联结果，错误、缺失、重复、未确认请求和重试全部独立记录，不通过重新编号掩盖关联错误。

### 配置和最小运行清单

环境候选沿用单张GPU0、缓存Qwen2.5-7B-Instruct、BF16、单模型服务、context4096、max-num-seqs128、batched-token8192、前缀缓存关闭和分块输入处理。
硬件、模型/服务/SDK/扩展版本、tokenizer及输入摘要在后续preflight重新确认；旧Movie的最佳并发不直接继承。
设施常驻且充分准备后开始查询；tokenizer加载和Ray启动单列，其常驻内存仍计入资源报告，逐查询分词、构造和组织仍计时。

| 项目 | 首轮设置 |
|---|---|
| 调参 | 原生、薄转发、静态SemLoom各检查C32/C64/C128；每点64行预热、两次256行测量，保留全部值。C表示各路径自己的请求上限，不改vLLM调度 |
| 选点 | 每路径按完整查询有效吞吐选择已测最好中位数3%以内的最小C；只是有限选点，不称服务饱和或统计等效。信息/长度两条继承静态Core的C，不在评价时重选 |
| Core留存与候选 | 三条Core共用H256；最大候选256，组织器最多选256项；静态原序与长度组保持相同候选范围，不等待凑满窗口。H表示Core持有任务上限，源DataFrame的512行另计 |
| 工作额度 | 静态请求数仍每项计1；长度描述/长度次序用`输入token+64`，按各session声明单位。活跃work额度取不限制合法请求的`C×4096`，请求上限才是有效限制；验证没有work-only阻塞，本轮不同时测试token接纳控制 |
| 物理执行 | 三条Core固定Daft＋Ray、物理准备块2行、2个worker；Ray对象空间512MiB、准备窗口4MiB、传输对象额度128MiB。各客户端共用4个可用CPU的同一集合，Ray声明4逻辑CPU、每worker1CPU；CPU编号后续核对，模型使用另一集合。复用逐请求完成，不加入整组等待；Arrow＋Ray暂不扩测 |
| 空间 | 每查询原输入文件不超过64MiB；Core输入/结果各256MiB，单项限额沿用现有完整请求/响应规定；LM保留整批结果的16MiB检查继续执行。进程实际内存另测，启动前核对资源可达 |
| 短比较测量 | 每路径64行预热＋8次512行完整查询；五路径按循环轮换和反向顺序交错，同一模型服务，所有轮次和查询ID预先写入schedule |
| 观测开销 | 长度描述/长度次序各在调参输入做一次摘要/完整观测配对，每次256行，共4查询；保留固定模式，不用日志变更制造性能差 |

原生与薄转发保留各自合理选点；若它们和Core最终C不同，主表明确列出，差值解释为完整执行路径表现。
机制归因只在三条同Core路径间做；不得把不同C路径的差值全部归给排序。原生设施与闲置Ray持有的资源也单列。
正确性5×8＝40次；容量9×(64＋2×256)＝5,184次；观测4×256＝1,024次；短比较5×(64＋8×512)＝20,800次。
合计最多**27,048次模型调用、81条查询、75分钟含启动与清理**。整查询120秒，模型HTTP期限30秒；薄转发入口等待与完整响应共用一次期限，Core沿用原flow/backend期限。
实际计时起点随配置登记，不声称五组逻辑请求期限完全相同；首次错误停止，不重试、不自动追加。
预计约30～60分钟，仅是准备估计；用容量阶段的实际耗时更新剩余估计，超过总时间上限保留已完成材料。
本轮只写方案，模型调用0；后续按已有持续服务器授权准备和执行，无需逐阶段重新确认。

### 指标与各阶段耗时

主计时为`完整消费EOF－调用原生sem_map之前`，设施与源数据已就绪；包含本次formatter、HTTP装配、分词、组织、执行及原生解析。
另报应用时间`EOF－开始读取本次输入`，以及启动、预热、清理、评分时间。共同消费端立即读完全部结果，不引入人工慢消费或写回表。
首轮没有数据库写回，写回字段标明“未执行”；以后SQL运行另使用真实数据库开始/结束事件。

| 阶段 | 起止与报告方式 |
|---|---|
| 输入读取/装载 | 开始读取清单至DataFrame就绪；报告wall时间和CPU时间，在应用时间内，单列于就绪查询时间之外 |
| 原生提示与请求装配 | sem_map入口至完整消息批次就绪；HTTP编码另从逐调用准备事件记录。保持原formatter，并区分共同审计构造与真实出站装配 |
| 工作描述与组织 | 每条完整消息的本地token计数；每次组织器开始/结束，累计wall/线程CPU、调用数、候选数和选择成员。该独立组织计时当前尚缺，需小型包装探针 |
| 接纳与待提交 | 批任务就绪至Core接纳、接纳至提交记录；包含容量等待和部分推进，不称纯排队CPU成本。原生请求池内部无探针的部分写unavailable |
| 表示与传输 | 复用payload/Ray事件，分报Daft/Arrow构造、序列化、对象put、RPC提交与worker接收；wall、实际工作、排队/恢复分别列，原生/薄转发无Ray阶段标“不适用” |
| 模型HTTP | 共同观测代理开始上游POST至收齐完整响应；含网络、服务等待与生成，不称纯模型执行时间。running/waiting、token、KV/抢占只在实际服务暴露字段时报告 |
| 返回与Core处理 | worker响应完成至驱动端收取、Core确认/交付；缺逐条时钟或可验证关联写unavailable，不从HTTP间隔反推 |
| 原LM返回与消费 | 完整SDK列表返回、原生统计/parser、结果逐行交付至共同EOF；保留LOTUS整批返回语义，并记录完整响应等待和结果留存 |

阶段既有并行也有嵌套。查询关键时间线、累计CPU和单请求区间分表，不把阶段累计相加、乘行数或从JCT扣除来构造加速。
现有`submitted`记录在接纳并尝试提交之后，不是精确取得执行名额的时刻；本轮不为追求细分补一套全局时间系统。

| 指标 | 定义与样本解释 |
|---|---|
| 整查询耗时/有效吞吐 | 每次就绪查询原值、P50、均值、最大值及配对差；有效吞吐＝合法且完整交付的行数/JCT。语义错答保留在质量分母 |
| 调用者端到端P50/P95/P99 | 当前可靠口径为批次完整消息就绪至原LM取得完整SDK列表，所有路径保留同一起止；同批各行共用起止，因此其P99退化为批次尾部，不能当独立模型响应延迟 |
| SemLoom执行响应P50/P95/P99 | 批次就绪至该调用完整响应交给已有`on_response`回调，包含接纳、准备、RPC、HTTP和收取；三条Core可配对。原生/薄转发没有对应内部响应钩子时写unavailable，不用LM整批返回补值 |
| HTTP P50/P95/P99 | 另表报实际完整上游HTTP往返，并按调参确定的输入长度分组报告；短/长任务的HTTP开始与完成顺序用于解释组织动作 |
| 查询P99和P99.99 | 最近秩定义为第`ceil(p×n)`项，单位和n随表给出。每路径只有8条查询，其P99为观测最大值；请求4,096个但重复同一512行，P99.99也为最大值，不作总体尾部估计 |
| 信息与资源代价 | 分词/组织CPU、driver和worker分开采样的CPU/RSS、准备/待提交/在途/已完成未释放的峰值与占用时间积分、对象put字节/RPC数、实际HTTP供给曲线 |
| 质量与行为 | 复用EM（规范化答案完全匹配率）/F1（答案词项重合率）；保存逐行差异、实际输入/输出token、finish_reason、调用集合、exactly-once、失败和最终资源归零 |

从批次就绪到共同HTTP响应的逐调用区间，仅在实际row/调用/HTTP关联可验证时补报；缺项不以代理到达代替任务就绪。
请求样本不作为独立系统重复；配对分析以完整查询为单位，不把同次查询的512行当作512次独立实验。
成功的工程观察至少需要请求/关联/容量核对通过、排序确实改变提交、质量差异解释完整。
候选相对无分词静态参照的JCT中位收益至少3%、至少6/8次配对改善，作为是否继续投入的预设选择信号，并报告全部差值；这不是统计显著性标准。
P99改善但JCT变差、长请求等待增加、内存上升或质量变差均单列；不能仅凭短请求更快采用方法。
若简单原序已足够、vLLM吸收了长度差异、候选不足或信息成本抵消收益，保留静态参照并结束此项，不追加全面重构。

### 最小实现缺口与交付

| 复用落点 | 必要的小改动与核对 |
|---|---|
| `squad_map.py` / `squad_capacity.py` / `squad_pg_map_pilot.py` | 复用解析、分区、CSV导出和评分，补小型外部输入JSONL转换与LOTUS完整消息长度侧记录；原消息不改，不能沿用PG token画像 |
| `LotusBatchExecutor` / `prepare_native_task` | 增加默认关闭的完整调用工作描述回调，复用已生成payload与未接纳后缀；工作描述每个调用只做一次，默认请求数路径保持原行为 |
| `build_native_execution` / `WorkWindowOrganizer` | 使用已有`organize`参数和长度升序；不改SessionEngine、Ray调度或vLLM。PG专用`MapOrganizationConfig`不是LOTUS可直接插入的配置，需要薄装配 |
| 现有简单转发 / 常驻查询runner | LOTUS薄转发仍待装配：优先复用`SemaRequestService`的原样转发实现及现有错误处理，不调用Sema程序；核对URL、完整正文/状态、期限、停止和回收，不能把改BASE_URL称作已验证 |
| `native_adapter_metrics.py` / 已有事件与采样器 | 加组织计时，借已有`on_response`记完整响应到达适配器的事件，补离线五组汇总；不另建指标平台。完整HTTP实际关联、跨进程时钟或模型内部指标缺失时，保留原因 |

## 当前 M1：有效吞吐平台附近的在途工作与资源代价（2026-09-20）

本实验只回答两个问题：在单查询、不可变全扫描、固定模型与输出目标下，维持接近已测最高有效吞吐需要多少供给；
在该区域增加在途工作，是否仍有完成收益，还是主要增加排队与留存。目标不是最小提交量或服务队列恒为零：
需要保留覆盖取数、构造、通信及补充波动的供给余量。不得先减少有用计算供给，再用 HTTP P99 下降宣称查询优化。

**旧 M1 已结束其测量任务**：[常驻对照](../results/postgresql/waiting_positions_persistent_20260914/README.md)
中，W512 对 work 最小值 187 的任务最多容纳两项，不能充分使用四个受控服务槽。
HTTP P99 下降 42.23%，完整查询时间却从 0.395086 增至 1.315864 秒。这是指标反例，
不证明 token 控制优于调优请求数，也不证明有限候选优于全局轻量信息。不继续重复这一欠供给比较。
原始输入、代码快照、时间线及全部失败保留。

### 先检查可达性，再消耗模型额度

`m1_campaign.py` 改为显式 v2 配置，每次只执行一个阶段。`--preflight` 只读本地身份与预算，
不连接 PG、不加载模型或 tokenizer、不初始化请求账本。各扫描点共用同一份存储设置、CPU/服务配置和输入身份。
逐点输出请求上限、Core 留存项数、结果预留可支持项数、输入字节可支持项数、PG 行窗口/留存/暂存与客户端配置。
服务 `max-num-seqs` 是内部执行配置，不直接等同于客户端在途数；真实 running/waiting 需另测。

源码每项 Map 最大响应预留为 1 MiB，因此旧 Core 结果 32 MiB 使实际接纳数不超过 32，C64 扫描点不可达。
32 MiB 是上游配置，不是 GPU 能力。若计划留存 128 项，仅 Core 结果预留就需至少 128 MiB；输入、PG 等还须逐项通过。
新的静态估量采用 manifest 字节上限、最坏 JSON 转义、现有 PG 行分配公式及保守元数据余量；
它只证明声明资源允许目标供给，运行中仍要核对实际计划窗口、字节使用和持续在途曲线，不能用瞬时峰值代替。
资源不够时返回具体原因，不在线缩减响应预留、切换 CPU、降低模型 context 或改输入来凑出有效点。
若研究固定存储下的限制，另立身份，不混入服务能力扫描。

### 分阶段选点与独立评价

1. **容量筛查 `screening`**：只用调参输入；匹配请求数 FIFO（按输入先后提交），两条路径使用相同的、至少三个可达 C。
   PG 复用 `PersistentMapGateway`；匹配 direct 复用 `pg-source-direct` 的有界客户端，模型消息与生成设置逐项核对。
   该 direct 仍含 PG 源读取和每查询客户端准备，属于匹配执行参照；两条路径时间不能相减解释为纯 PG 开销。
   若两者都停止增长，只能先报告各自路径的平台候选；要把它解释成服务能力，须另以已有 `DirectMap` 的准备输入路径
   排除共同取数/客户端供给限制，并核对服务观测，不新建调度器或把参照冒充原生系统。
2. **工作量调参 `strategy-tuning`**：仅在供给有解释力的区域，固定 FIFO 顺序，以已调优请求数为参照，
   在相同有限较高 C 下检查少数预先列出的 W。C 作为保护上限，W 由调参结果决定，不预置“紧 W4096 必须有效”。
   各策略获得相同资源与调优机会；记录尝试过的全部点与额度。W 未触发、吞吐下降或与简单控制相当均保留，
   不调整 context 迫使 W 起作用，也不换评价数据追求优势。
3. **独立评价 `evaluation`**：先保存调参决定及其 SHA，记录选定组、服务签名、输入身份、资源和判定规则；
   评价配置须逐项匹配该决定，使用独立评价输入。主要组见下表；不在看到评价结果后重选 C/W。
4. **观测开销 `observation`**：仅选少量代表组做完整/摘要记录配对；不将日志模式扩成所有 C×W 的矩阵。
   每次显式列出全部轮次顺序；第零轮为预热，其余是同服务生命周期内的配对重复，不冒充独立服务启动样本。

| 比较组 | 选取依据 | 能回答什么 |
|---|---|---|
| 有限较高并发 request FIFO | 已测平台附近或更高、资源允许的 C；不使用故意 OOM 的无限提交 | 更多提前提交的完成收益及资源代价 |
| 调优 request FIFO | 调参中维持近似吞吐的较小 C，独立评价复核 | 简单请求数控制能做到什么 |
| 调优 token FIFO | C 为相同的较高保护上限，W 独立调参；实际有 work-only 阻塞 | 工作量信息相对调优请求数的增量 |
| 少量 token 表征消融 | 与较高 request FIFO 同 C，W 对所有该 C 项集合均不生效 | 分词、描述与记录成本；也给同 C、只改 W 的归因提供参照 |

完整策略比较允许 C/W 数值不同；归因 W 时保持同 C、同顺序、同观测和其余设置。

### 平台与不确定性的判定

主量为 `X(C)=完整且合法完成的任务数 / 调用入口至客户端 EOF 的完整查询时间`。
合法但语义判断错误的输出保留在吞吐计数和质量分母中；非法、缺失、重复输出以及关联/资源/请求计数错误停止该阶段，
失败证据继续保存，不能删掉失败重复再选点。实际输入/输出 token、输出变化与标签质量同时报告。

只在声明的可达集合内计算 `Xmax`。`epsilon` 在运行前确定，候选较小 C 满足 `X(C) >= (1-epsilon) Xmax`。
3% 可以作为待审阅选择，程序不再内置 97% 规则；同时必须声明最少重复数、可接受重复范围以及中段供给判定参数。
`select_capacity()` 要求完整配对记录、实际 HTTP 持续供给与重复原值，并分别返回：

- `platform_candidate`：已测集合内的平台候选，仍须独立评价；不宣布饱和或统计等效。
- `no_platform_observed`：最高两个档位仍有超过声明差异的持续改善。
- `inconclusive_supply`：至少一个点缺少持续供给；优先检查实际读取、通信、留存和客户端。
- `inconclusive_repeat_variation`：重复波动或配对差异跨过判定值，当前不明确。
- `lower_supply_range_unresolved`：最小档位已是观测最好点，尚未辨明更低供给范围。

程序使用配对吞吐比的全部原值和观测最小/最大范围进行保守筛查，该范围不是置信区间。
至少三次测量只是输入完整性要求，不保证充分重复；最初小规模筛查若波动太大，先报告不明确，
再单独设计新的重复数与额度，不自动追加。评价同样报告配对差异，不能挑最快重复。
查询全程的启动和排空保留在主指标；固定中段仅用于解释是否持续供给，不删除不利时段制造平台。

### 指标、数据与解释规则

主表保留完整 JCT（调用至消费完毕的时间）、有效完成吞吐、合法性、任务质量、输出差异、失败和实际调用量。
机制表按数据所在位置分别记录：尚未物化、已准备未提交、HTTP 在途/服务等待、模型执行、已完成未消费。
不能把尚未物化任务数叫内存字节，也不能因服务排队减少就声称整个系统少留存了数据。

现有记录器继续提供逐行等待、PG 留存峰值、Core 逻辑占用、实际 HTTP 曲线及进程 RSS/CPU 采样。
新增离线汇总给出每个逻辑域的占用时间积分、每个已采样进程的 RSS 字节秒与 CPU 时间增量，
从观测区间计算；缺少区间不填零，Core 结果预留不当成实际响应大小，PG 完整字节时间线缺失则写 unavailable。
所有常驻 gateway 与 driver 在两条路径运行期间统一采样，活跃 PG reader 另由各查询采样。
逐进程峰值不能相加称同时峰值；RSS 可能重复计共享页，逻辑预算下降不等于物理内存同比下降。

vLLM 0.25.1 的 [Production Metrics](https://docs.vllm.ai/en/v0.25.1/usage/metrics/)
列出 running/waiting、排队、KV 与抢占等字段；未来执行前按部署实例实际输出核对，不把文档字段当本轮已测值。
当前编排会明确记录服务指标尚未附加；未来由已有服务采样器提供独立文件。GPU 利用率与 MFU（模型算力利用率）仅用于解释，
MFU 缺少可信运算量及对应精度峰值时不报告。[Optimization and Tuning](https://docs.vllm.ai/en/v0.25.1/configuration/optimization/)
讨论了抢占/重计算的代价，但本项目旧 M1 没有测出该机制，不能借文献补写因果。

| 观察 | 解释 |
|---|---|
| 吞吐相近，实际留存或服务排队减少 | 存在减少多余提前工作的空间；先排除队列转移 |
| HTTP 尾延迟下降，完整 JCT 变差，上游等待增加 | 等待移动或供给不足；明确吞吐代价 |
| 吞吐改善且测到额外工作减少 | 有执行收益信号，机制仍须对应证据 |
| token 与调优请求数相当或更差 | 当前负载保留简单请求数参照，不强求复杂控制 |
| 合理点持续增长或供给始终不足 | 尚不能评价服务平台附近的限制 |

已准备的短评论继续用于基础容量、表征成本和近同质控制，不单独支持异质 work 优势。
若请求工作量相同为 w，则 W 等价于请求数上限 `floor(W/w)`；当前 work 174–249、均值约 199.833 的评价输入
尤其需要面对调优请求数参照。后续只有明确的工作量失配假设才增加一种真实异质性；
不通过调大最大输出冒充长输出，应报告真实输出长度。

全局轻量信息、有限物化和候选范围仍归 M2；多查询服务分配与长查询代价归 M4，可按其自身共享资源和输入资格独立推进，
不要求所有单查询先达到所谓完美极限。E 已有共享服务，token 组织仍有单 Job 接入要求，两者不混称。
M1 不新增长度排序、全局信息策略、公平算法或 vLLM 调度修改。

**当前交付**：研究设计、v2 可达性预检、分阶段运行表、选点及资源/输出汇总和无外部服务测试。

### 2. 最小模型：信息、责任与用户目标

对查询j保留逻辑输入、依赖和实际SQL语义；对合法工作i保留行出现ID、所属查询/阶段和完整请求身份。
模型允许轻量全局元数据与有界payload同时存在；不能因当前API尚不暴露某信息，就在对照中禁止获取它。

| 量 / 状态 | 定义与现有观测 | 不能混用的事实 |
|---|---|---|
| 查询释放r_j、终点F_j | 主目标JCT_j=F_j-r_j。先声明终点为客户端观测EOF，另报结果持久化时间；若比较写回，则F_j改为已核验写回提交，两种合同不混排 | 现有q0计时从SQL/direct release开始，**不含**此前gateway/tokenizer启动；新实验须另报查询专属准备和冷启动，不能重解释旧JCT |
| 工作资格a_i | 与被比较策略独立的合法可执行时刻：固定全扫描可用共同release/离线输入条件定义，依赖场景由上游语义结果决定 | child被拉取、token化结束或Core接纳会受策略影响，不能直接当共同a_i；不能观察时标unknown，仅报告release至完成及可测子段 |

在这些时点均可比较时，逐项保留恒等式：

$$
d_i-a_i=(s_i-a_i)+(f_i^{obs}-s_i)+(g_i-f_i^{obs})+(h_i-g_i)+(d_i-h_i).
$$

资格到提交和完成到消费的等待不能遗漏。若只能观察child返回后的时间，须明确这是部分区间；
不能靠把资格时间推迟到接纳时来降低“端到端”延迟。
全扫描主要比较完整JCT、资源和质量；多查询增加逐查询JCT/slowdown与最长无服务时间；
LIMIT另比较需求满足时间及多做的工作，并先满足原有严格按需语义，不用全扫描重排权限替代LIMIT资格。

可复用metadata必须另报建造/刷新/储存成本和按什么复用次数摊销，不将预先算出的评价集信息免费提供给某一臂。

### 3. 可以证明什么，以及目前不能证明什么

以下是明确模型下的数学推导和证明任务，**不是新增算法贡献，也不是完整实现已被形式化验证**。

**资源安全。** 对内存域r，令L_r(t)为仍由该域负责的数据，m_ir(t)为它实际计费的表示或足以覆盖分配的预留，
M_fixed为固定开销。要求：

$$
M_r(t)=M_{r,fixed}(t)+\sum_{i\in L_r(t)}m_{ir}(t)\le B_r.
$$

若初始状态满足预算，每次转换都在分配前检查“旧占用+新表示+必要暂存”的峰值，责任交接不重复漏计，
只在相应责任真正结束后扣账，则对转换次数归纳可得不变量。C的证明对象仅为实际计费的行上下文/元数据及各自有界暂存；
要将结论连到代码，还需列出全部接纳、转换、结果预留、交付、异常与未知终态转换并检查。它不约束整个PG/gateway/Ray RSS，
也不证明吞吐或最终一定完成。现有测试与事件重放是该证明任务的支持证据，不替代穷尽转换的证明。

**积压面积。** 对包含所有a_i和d_i的完整有限观测区间，N(t)=Σ_i 1{a_i≤t<d_i}，有

$$
\sum_i(d_i-a_i)=\int N(t)\,dt,\qquad
\sum_j\omega_j(F_j-r_j)=\int\sum_j\omega_j1\{r_j\le t<F_j\}\,dt.
$$

证明是对每个指示函数积分，再有限求和；第二式要求权重预先固定。内存驻留成本另记为∫M_r(t)dt，单位B·s。
观测不完整时只能积分截断区间，并报告未完成/取消项，不能把其当作完整sojourn或只剩成功样本。
离散RSS采样面积只是采样近似；完整逻辑状态转移的阶梯积分可以精确重算。
这些有限样本恒等式不需要假设M/M/1；[Little的2011原文](https://pubsonline.informs.org/doi/10.1287/opre.1110.0940)
§2.1.2也讨论完整、两端为空的有限观察段，不能反过来要求所有有限查询均为平稳过程。
平均关系本身不能推出P99、最优窗口或当前有限工作集的系统稳定性。

**按序消费的反例。** 单个单位速率串行执行器、全部任务在0时刻合法、确定耗时p_i>0、无局部性/切换收益，
结果按输入序即时交付，且没有额外传输、消费阻塞或并发效果。任意顺序完成输入前缀i至少处理Σ_{k≤i}p_k的工作，故

$$
d_i\ge\sum_{k=1}^{i}p_k.
$$

无空闲FIFO对每个i达到该下界。输入耗时[10,1]时，FIFO的有序交付为[10,11]，短项优先为[11,11]。
因此不能用短任务优先的无序完成优势证明本项目按序结果一定更快。方法必须指出利用了哪条不成立的假设，
例如并行资源互补、真实prefix复用或阶段重叠，并用对照单独识别它。

**有限动作的决策误差。** 给定同一状态s、同一有限时域/终端代价和有限合法动作集A(s)，
令J为真实代价、Jhat为预测，假定对所有候选同时成立
|Jhat(a|s)-J(a|s)|≤ε，选择误差至多δ，即Jhat(ahat|s)≤min_a Jhat(a|s)+δ。令a*最小化真实代价，则

$$
J(\hat a\mid s)\le\hat J(\hat a\mid s)+\varepsilon
\le\hat J(a^*\mid s)+\delta+\varepsilon
\le J(a^*\mid s)+2\varepsilon+\delta.
$$

若采用逐动作界ε_a，只有Jhat(a)+ε_a<Jhat(a_0)-ε_0才可在这些界成立时判断候选优于强静态a_0；
实际下发动作还须满足对应不等式，不能忽略近似求解误差。RMSE、单个动作的覆盖率或被选动作上的误差均不自动满足同时误差界。
若使用统计界，须声明覆盖概率、候选比较/自适应选择的处理；有限时域结论不推出整查询全局最优，未获保证时保留静态动作。

**进展与公平仍是独立证明任务。** 有界队列可把积压转移到入口；平均服务差也不能推出查询P99有界。
证明候选不会永久饿死某项，至少需要有限或受约束到达、每项可容纳、消费最终继续、资源释放被观察、后端最终给出权威终态、
选择器具有公平机会等前提；未知终态可能合法保持计费，此时应有限地失败/隔离而不是编造完成。
尚未证明当前端到端执行在任意黑盒服务下均可推进。Neely有限缓冲研究中的丢包条件与SQL不能丢弃必要行冲突，
有限重排缓冲的颜色切换成本也不等于KV生命周期；见[理论迁移条件](../../docs/research/研究定位.md#execution-transfer-cards)。

### 5. 候选方法与既有实现落点

候选为**消费进度感知的有界组织**：只对合法、可观测、尚未提交的工作，比较继续准备、现有FIFO/长度次序、
促进结果前缀消费及少量准备深度动作。它是等待M1/M2及最近邻审查的候选，不是已实现/已证明的新算法。
在物化预算内保留多少未承诺工作，需要真实查询进展和驻留代价支持；不添加十几个无依据的评分权重。

| 数学对象 / 能力 | 已有落点 | 本轮决定 |
|---|---|---|
| 行身份、合法输入、消费序和取消 | PG child plan、语义节点、独立结果绑定 | 沿用数据库语义；新动作不能扩大合法求值范围 |
| 行/暂存计费与消费释放 | `sem_pump.c` total预算；资源事件 | 沿用C；增加域或证明时逐一列实际责任，不能映射成进程RSS |
| 完整消息work及校准身份 | 模态adapter、`WorkDescriptor`、`MapOrganizationConfig` | 复用D；与真实token usage核对；不把单项max-new上界解释为运行时长 |
| 候选和组内次序 | `WorkWindowOrganizer` / 已有organization回调 | 现有FIFO/有限长度控制作对照；消费进度信息尚未接入该策略，不宣称已支持 |
| 计算容量、提交、终态 | `SessionCapacity`、`SessionEngine` | 不复制账本；后端权威终态前保留未知责任 |
| 查询机会与阶段能力 | 既有Job/flow选择、MethodDriver和可替换backend | E/F按实验需要补最小适配；PG方法桥接、动态份额和图像阶段不因接口存在而算已验证 |
| 全局元数据、反事实与误差 | 实验/离线分析层 | 先构成强对照，未知未来完成时长仅可作明确的离线oracle；不泄露给在线候选 |

每个动作都要对应实际变化：读取/准备次数、被提交任务、提交时刻、传输或资源使用至少一项改变。
只改batch ID而物理执行不变的分组不能成为独立优化；不允许拼接多个prompt或强加整组完成屏障来制造收益。
对于未来候选，先在小状态空间枚举/受控反例核对合法性、安全和有限模型下的反事实，再安排真实M1/M2；
模拟只能证明所声明模型，不替代真实PG/模型对照。

#### 按合法窗口和消费需求检查共享准备（2026-10-03）

这是用户要求完整场景/工程/理论分析后的候选切片，不是新增运行授权。
机制依据、完整流程与采用条件见[方法分析](../../docs/research/优化方法依据.md#query-specific-execution-opportunities)。
当前文本路径、单图接入与外部多模态producer保持各自身份；不恢复旧图像矩阵或直接增加训练任务。

先收窄到一个Job：语义producer已经确定窗口、所需资产及版本，准备函数确定且结果表示相同。
每个逻辑窗口保持独立任务、完整输入和结果身份；共享的只是它们确实重复需要的准备。
第一项可测试动作是复用确定性decode/resize，之后才比较消费位置参与准备选择。
转换前核对至少一个完整合法窗口和旧/新表示同时存在的峰值能容纳；容量不足明确拒绝，不改变窗口或模态。
原生loader或数据引擎本来已经做过的lazy准备、缓存和混洗先作为对照，不能故意关闭来制造优势。

| 工程步骤 | 复用的当前落点 | 新增项及检查内容 |
|---|---|---|
| 取得合法任务与依赖 | `TaskKey`、版本化语义、模态producer和`WorkDescriptor` | 每窗口的有序资产/时间/模态/掩码及处理器版本；重复采样仍为不同逻辑任务，不擅自改trainer的采样 |
| 分开逻辑与准备身份 | `StageBlockDescriptor`的内容、变换和模型签名 | 现有编码摘要包含row_ids，需另取内容/变换键；adapter内的单Job共享准备索引保留每次独立行绑定，随机变换的相关随机状态进入身份 |
| 管理共享缓冲 | `BoundedStageBroker`的字节、work和lease | 记录所有消费者与真实物理缓冲；缓存持有也计费，已提交/未知工作保持引用，空闲项按字节上限淘汰 |
| 选择准备时机 | `SessionPolicies`与现有静态FIFO/工作量组织 | 先以原顺序对照，再用实际消费位置及缺少的准备项作小规则；不加入没有校准的GPU剩余时间预测 |
| 验证旧路径 | 现有文本/单图取消、未知结果和资源检查 | 不改变独立请求、模型输入与结果关联；共享/取消/末尾释放、多视图持有大缓冲、容量不足等行为分别检查 |
| 接入真实场景 | 独立核心检查通过后，再选择实际PG算子或获准外部producer | 当前图像规格不包含多相机/history/action；新语义与PG/wire接入单独检查，trainer的采样、跨rank和恢复另验 |

先用明确标识的本地受控窗口核对工作次数与字节，保留无共享、变换不一致、稀疏窗口、
一项被取消但另一项仍在途、未知结果、消费慢及缓存容量不足的反例。
连续16帧/步长8仅用于可精确复算的机制诊断；不得改真实采样以迁就这个形状。
本阶段不需要训练模型或在线机器人，CPU替身结果不作为真实decoder或GPU时间。

若实际输入存在重复准备，再按目标环境读runtime材料、核对依赖和版本，另列有限无模型或模型运行清单。
公平对照保持合法输入、逻辑采样/顺序、固定实际CPU/GPU、存储与模型语义；
共享准备的识别/索引/缓存建造、额外读入、对象传输及退出成本均计入。
实际模型已充分供给或原生同信息策略没有差距时，停止增加控制，保留简单执行。

#### 物理需求、表示与不确定后继准备的补充对照

对应[方法补充](../../docs/research/优化方法依据.md#heterogeneous-demand-supplement)，
在上述单Job切片有实际需求后选择一项推进，不增加整套异构调度器或自动启动实验。

| 待回答的问题 | 有限动作与匹配对照 | 必须记录及否定条件 |
|---|---|---|
| 目标窗口重叠是否真的省物理工作 | 相同目标帧/状态的原读取器与合法读区间/解码依赖合并；读取、准备与模型保持各自合适粒度 | 目标帧、实际读字节/区间、解码帧次、decoder重置与装配；目标少而实际物理工作不变，或多读/状态切换抵消收益则不采用 |
| 哪种表示/展开位置值得使用 | 在实际支持的CPU/GPU后端中比较编码传输后准备、先准备再传输、原生缓存/不缓存；固定处理输出与资源 | 定位、转换、网络/H2D、同SSD的cache/spill竞争、暂存及释放；FP32膨胀、GPU争用或缓存建造使整条任务更慢则不采用 |
| 筛选未结束时是否提前准备 | 相同前段与后段语义，比较全部延迟、固定提前、有限预算提前；原生也获相同筛选/消费信息 | 需求确定时刻、用上/未用上的准备、后继启动、完整完成及退出等待；未使用准备延长结束、污染错误行为或减少必要模型供给则不采用 |

准备共享不减少逻辑任务或应有模型调用；表示/decoder替换先定义逐元素相同或已获许可的误差标准。
视频状态、随机增强和训练更新另核对，不能从单图确定性处理推到所有模态。
“提前”只作用于已获访问/求值许可、可安全放弃的准备，后继模型调用不在该动作内；
损坏媒体的错误何时可见、消费者消失、未知结果仍持有引用与停止新增准备分别列行为检查。
只够单帧而不能容纳完整合法窗口时明确拒绝，不缩短输入。

源码新增范围先限定模态producer的需求/资产版本与准备键、adapter支持的读取/处理路径，
以及broker内物理持有者/暂存和待消费准备状态；继续由现有SessionEngine负责任务与请求容量。
普通内存、Ray对象、锁页内存与显存记录包含关系，不能把准备张量额度冒充全进程硬上限。
实际资产延迟读取、后继求值许可和延迟错误需要新增接口，当前尚未实现；PG路径另做语义及wire检查。

计划中的后续诊断先复用无共享、不同变换、稀疏窗口、慢消费、原生热cache与模型充分供给的反例；
增加低通过率、准备长于筛选、损坏但被筛掉的媒体、相同目标但decoder状态不同等情景。
元数据/索引、cache建造更新、冷/热I/O、spill/restore、未使用准备和结束等待均计入。
事件按各自时钟记录并对齐定义；异步提交只记提交，设备完成另取可确认事件。
这些是待执行的检查项，不是本次已有检查结果；环境、资源清单、重复与停止条件确定后才安排运行。

具体引擎接入位置先按[架构选择](系统架构.md#engine-extension-placement)确定推进、额度及终态负责人。
原生媒体对照保留固定版本已有的批内同shard解码；按episode关联减少帧行，仍需实际I/O/解码证据。
固定任务与完整语义系统按[分层对照](reference/对照规范.md#execution-comparison-levels)分别报告，不更换原生执行负责人。
