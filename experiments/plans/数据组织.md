## LOTUS Filter：从记录准备到语义结果（main 待集成）

目标是在同一 LOTUS 优化算法上检验准备、传输与供给的额外收益，职责按[架构](系统架构.md#lotus-data-execution)划分。
本单元首先完成 baseline 接入、公共方法适配和 runner 资格；SemLoom 同方法边界的适配也按接入验收，
其准备调度、数据复用／搬运／回收策略的研究收益在匹配静态与原生参照上另证。
先独立完成原生 Ray Data 的 SemBench 普通 Filter，直接与原生 LOTUS 核对，再在同一范围接 Movie Q3 Filter＋COUNT 的原全局 helper-LM 级联；随后接 SemLoom 静态同任务。首切片不等全矩阵，最终对照必须补齐 Daft、Ray Data、IMLane，并保留原生 LOTUS、SemLoom 静态／候选；未完成者列为缺项，不从目标中删除。
这是拟议的查询配置，不把原 runner 调用 `sem_filter()` 视为已启用级联；[当前接点与源码边界](../../code/src/semantic_methods/lotus/README.md#filter-execution-boundary)另列。

分支安排：`integration/baselines` 保留现有 request 配置与历史身份；`integration/data-execution` 集成记录准备／本地模型／原生后端，短期功能分支验证后汇入。新路径成熟后再评估旧包装及独立 HTTP 配置的保留／退役，历史由 commit／tag 追溯；SemLoom 通用能力另审进入 main。分支实现与资格见[下文](#model-engine-roadmap)，不把规划或分支进度写成 main 已集成。

新主链保留以下必要合同，按需复用已有 LM、logprobs 与 `settings.context()`；不要求经过旧 request adapter：

| 必要工作 | 范围与完成条件 |
|---|---|
| 阶段与结果关联 | 当前类级 `observe_filter_rows` 和 `_LotusBatchObservation` 假设每批覆盖全部输入；新链保留 query／model role／algorithm stage／row occurrence／call 关联，无需继承旧记录器。分别保存 `sample_indices` 与 `low_conf_idxs` 的位置映射，支持 helper、校准样本和回退子集，重复抽样保留独立发生项 |
| 输入索引兼容 | Q3 普通过滤后可留下稀疏 pandas index，而固定 LOTUS 以位置产生 `sample_indices` 后使用 `.loc`。先定义所有臂相同的输入边界及索引规范，保留 `_execution_row_id` 核对原行关联、重复样本与最终 COUNT；这是兼容修正，不是方法创新 |
| 调用预算与来源资格 | 当前 Movie CLI 按每行一次计算总调用预算 N；级联须按模型角色／阶段设有限调用上界并记录实际工作。固定原模型、有效参数与缓存策略，来源核验覆盖实际采用的 `sem_filter.py`、`cascade_utils.py` 及校准、采样、阈值函数，不能沿用仅请求接点的资格 |
| 前置方法检查 | records 在媒体展开前交接时，先提取原 Filter 的轻量检查，覆盖 main／helper 列、examples 的 Answer、helper LM、单 token 输出及 helper CoT 限制；公开 runner／session／hook 均在模型分配前检查环境与有效参数，缓存命中不能绕过；不以全量解码兜底 |
| runner 与输入资格 | 阶段／角色身份、调用预算与共同计时须在首次 records 性能测量前就绪；核验 manifest 内容摘要与任务、谓词、列 schema／LOTUS 图像类型的绑定，不把任意字符串列认作媒体。媒体后置时，将 Animals 元数据读取与 `image_identity()` 字节／像素核验分开，保留冻结输入版本及执行时或独立资格检查。性能模式按实际调用生成关联，不先在 driver 构造整表 expected 消息；资格样本核对实际消息、阶段与发生项 |

验证与推进顺序：

1. **原生 Ray Data 普通 Filter 首闭环**：固定 SemBench 输入、模型、查询与原生 LOTUS 执行作为正确性参照，独立构建记录→原准备／SDK 调用→原解析／COUNT 的原生程序。
   不要求先提取旧图或经过 `LotusNativeBatchExecutor`／`NativeCallExecutor`；旧 adapter 只作其既有资格范围内的补充参照，`native-records` 方法提取控制可按需增加。
   先以固定响应核对有效输入、LM 参数／usage／输出、逐行判定与统计，再做所用真实库资格；未支持范围明确拒绝，不以最终 COUNT 相同代替方法差分。
2. **同范围原全局级联**：在普通闭环上覆盖 helper、校准样本和回退；样本评价与阈值统计分开，后者仍复用原函数，不能让校准调用悄悄退回未声明的执行路径。
   固定响应和随机种子，核对有效消息、helper 分数、kwargs 合并与 `top_logprobs` 默认、usage／统计／必要输出／logprobs、错误与限制，以及全局校准、稀疏 index、重复样本及修正权重、阈值、fallback、merge 和逐行结果，覆盖空／非空回退。
   首版限定选定普通／helper-LM 形态，未支持参数明确拒绝；可限定结果缓存关闭，不能据此省略其他 LM 职责或宣称全部缓存语义已支持。原路径与扩展补丁分别保留来源资格。
3. **SemLoom 静态同任务与两臂对照**：用 Daft＋Ray Core／Actor 独立接同一普通／级联范围，继续运行上述差分，先与原生 Ray Data 形成匹配闭环；Core 复用到哪里由实际数据流决定。
   用早准备快、晚准备慢的输入，在无全局依赖阶段验证首发早于末准备，并记录峰值留存、准备所在 worker 和缓冲释放。
   新 prepare／finish 阶段也核对框架隐式重试，保持无隐藏重发；多分支／重复 action 不重复触发 helper 模型工作，合法重复采样仍逐发生项保留。
   在连续查询中核对客户端与取消状态隔离；只在必要校准或结果复用处保留屏障，其余准备不在公共 driver 整表完成。Daft 与 IMLane 分步补齐最终对照，媒体按任务扩展；模型引擎第二层可并行，不等待完整 HTTP 矩阵。
4. **少量真实确认后再评价机制**：明确优化开关、模型角色与质量目标，先核 helper／主模型实际调用、校准规模、阈值、路由和质量，
   再按[同算法对照](reference/对照规范.md#lotus-algorithm-execution)比较原执行、原生控制／流水及 SemLoom 同入口静态与候选策略。
   新增级联配置单列，真实候选与调用波动如实记录；测得准备／移动／重复工作减少及完整查询收益后，才决定是否采用候选。

旧图内核／追加段提取仅是可选复用工作；若修改该实现，回归其请求、结果、异常和清理。新链按自身[所有权边界](系统架构.md#lotus-data-execution)验证，不把旧控制结构当作准入条件。

records 流水可能在非法后缀被发现前已发送合法前缀，不沿用旧整批预检的零调用承诺。
覆盖坏后缀、解析与关闭失败和未知远端工作，保留已发送工作、逐调用成功／失败及未确认状态，按错误规则报告查询失败并完成取消／回收结清；部分成功不报成完整查询成功，也不污染下一查询。

本单元只覆盖普通／级联 Filter，不扩 PZ、所有算子、任意 DAG、多节点或通用 compiler。
IMLane 的新数据函数／schema 是最终对照的必需接入，不阻塞 Ray Data／SemLoom 首两臂；旧请求级结果保持原身份。
按作者 DBEnd 多行桥＋echo 核对发生项及 Lane 复用后的输出所有权，再接原准备＋替身，随后 CPython 单 worker／单 GPU 模型；作者 Ray 的 GPU／环境装配与实例生命周期另验。
桥／协议及方法接线按下述固定实施来源核对，已完成接口不重复建设；作者实库／模型资格按各自范围继续。具体所有权见[架构](系统架构.md#model-engine-execution)。

固定 vLLM `RequestOutput` 不是 LiteLLM 响应。结果适配保留 token IDs、finish reason、真实 usage 与输出 logprobs，
按[同版本 chat serving 转换](https://github.com/vllm-project/vllm/blob/v0.25.1/vllm/entrypoints/openai/chat_completion/serving.py)核对 token-ID 字典到原 chat 格式及 helper 置信度解释；
不能仅返回 text 或自造概率。首版限定支持参数，不实现全 OpenAI 协议，也不默认沿用 HTTP replay。
调用账本独立于最终合并结果，保留 helper、校准、fallback 的各次响应、usage 与失败，恢复原 LM 的统计／额度语义；不能用最终判定之和估计全查询 token。
账目归档不要求完整请求／输出缓冲无限留存；大 payload 按真实消费者及引用寿命释放，逻辑释放不保证 RSS 或显存立即下降。
原评价器调用、真实 LOTUS／Ray／Daft／vLLM 接线、GPU 生命周期与生产 Core 接入分别取得证据；候选 CPU 测试只能支持其覆盖的合同。

推进顺序为：**CPU 模板／参数／结果映射与身份合同 → 同 Qwen2.5 文本单 GPU 同步资格 → `AsyncLLM` 有界持续供给 → 同 Animals Q1、同 Qwen2-VL 小规模资格 → 原生 backend 同配置完整查询对照**。
CPU fixture 不能代替模型资格；同步调用批内渲染／计算与跨调用排空分别测量。独立执行单元中的 CPU 准备与 GPU 计算可重叠，不以 AsyncLLM 为前提；同引擎在已有请求未结束时持续接纳新请求才是该异步接点的目标，重叠均由实际时间线验证。
异步阶段先验证迟到输入与已有请求并存、最终结果／logprobs、abort 后终态和下一查询隔离，不以 token 回调作为必要条件；token 片段不是调用终态，不能据此推进需要完整解析结果的后继。
Animals 固定 RGB、媒体占位／网格和 processor，先保原 messages 与一次模板，再把去 PNG／base64 往返作为独立表示优化比较。
真实性能前先核模型输出与质量、预算和资源身份；保留普通／级联方法所需全部校准依赖，不能按计算批重新学习阈值。
同生命周期静态／候选机制比较与 HTTP→引擎接点的工程比较分别报告；未减少完整查询时间也保留负结果，不从准备并发或 GPU 利用率推导收益。

#### 当前普通 Q3 切片的执行与计时边界

以下按各条固定源码描述普通 Q3 切片，不将小样接通扩大为全库质量、最优吞吐或持续流水：

- [共同数据源](https://github.com/3444374/ai-operator-execution-optimization/blob/c0be45dd1278163a9e1e612694ff9752cfb433e0/code/src/baselines/text/movie_records.py#L131)先离线选原 CSV 的有限前缀，投影为带身份、无评价标签的 `records.csv`，标签另存 `references.csv`；后端原生读取该 records 关系。driver 在主计时前通过 `preflight()`／`expected()`读取并核验 records、references 与原 CSV；后端还会再次核验和读取，不能称为未经准备的原 CSV 全流程或只读一次。
- [同步引擎](https://github.com/3444374/ai-operator-execution-optimization/blob/c0be45dd1278163a9e1e612694ff9752cfb433e0/code/src/serving/backends/vllm_engine.py#L328)等待一批 `LLM.chat` 完整返回；[共同结果端 `d2915206`](https://github.com/3444374/ai-operator-execution-optimization/blob/d2915206c945e3c5db658a6533f3e6fed9b8cc6a/code/src/experiments/lotus_records_movie.py#L143)仍在 driver 累计 `raw`，整个 Filter 的 terminal rows 收齐、关联后才调用原 parser／COUNT，随后评价。两者是不同屏障，结果迭代不表示逐请求完成即推进后继算子。
- [普通 Core `_fill`](https://github.com/3444374/ai-operator-execution-optimization/blob/d2915206c945e3c5db658a6533f3e6fed9b8cc6a/code/src/execution_provider/adapters/lotus_records_core.py#L233)每个 source occurrence 提交一个 `OfferedTask`，`estimated_work=1`、工作单位 `model_calls`，prepare／model batch 均为 1；源读取批、准备批、Core 任务单位和模型执行批是不同边界。

### 后续算子与有限链（路线与实施范围）

普通Filter与有限文本链已有各自固定来源的接口和模型证据，按[总纲当前状态](../../PROJECT_OUTLINE.md#8-当前执行顺序)使用，不再重复立项建设。下一切片复用这些方法与continuation接点，检验合法依赖、后继组织和物理数据寿命；全局级联保持原控制器、校准总体与阈值，不采用简化控制器。

按本次变更选择少量复用例子：在已支持表示／方法内换数据、列或提示只改任务绑定；Map→Filter 组合已有节点；新方法增加绑定与关系处理、复用模型管理；新依赖形态才增加必要适配。
Filter→Map 保留实际幸存行仍需的源列，Map→Filter 将真实生成列交给后继；关系结果与调用终态／usage 按[既有合同](系统架构.md#model-engine-execution)分开。只释放本阶段大临时；原生链式模式避免每算子 `evaluate`→整表回 driver→重建图的固定边界。逐 pandas accessor 返回完整表具有物化边界；有限链原生图是明确的新增模式，作用域设置不会自动改变 pandas 的求值方式。
阶段式组合可作为正确性控制；支持组合不证明跨阶段流水收益，仍按[同模式对照](reference/对照规范.md#lotus-algorithm-execution)验证。

| 后续对象 | 额外方法与关系合同 |
|---|---|
| Map | 原 formatter／parser、输出列组织及与 Filter 幸存行的关联；验证同设施复用 |
| Extract | 原 JSON／结构化输出约束到引擎的映射，保留字段碰撞、索引及错误规则，不擅自加强 strict schema |
| Join | 原候选对／配对方法、左右来源身份与 Join 结果，不套单行输出恒等合同 |
| 语义 Agg | 普通 COUNT 为关系归约，不新增模型评价；语义聚合保留原分块、token 预算、分区／顺序、多轮依赖及所用末轮响应格式，不假设生成归约满足结合律 |
| Top-k | 原比较方法、方向与选择过程，不以任意排序替换算法 |

其余形态按实际 SemBench 任务逐个加入；权重、准备表示、提示／token 与答案缓存分别声明政策。方法与模型实例所有权沿[既有架构](系统架构.md#model-engine-execution)，完整计时及 native／静态／候选匹配沿[对照规范](reference/对照规范.md#lotus-algorithm-execution)。

### 依赖与数据表示的采用条件

| 候选范围/动作 | 必须先证明 | 无法证明时 |
|---|---|---|
| record：逐记录后继 | 必要前驱已成功解析；输入值、读取列及关系成员身份确定 | 保留原阶段等待，不提前生成调用 |
| group：重复label或显式依赖组 | 所有可能影响组值的源序更新已完成；可靠group closure证据、稳定schema/列序、None与缺键语义；获取证明的预扫描成本可计量 | 保留现有完整Extract关系装配与成功源EOF，不以暂时无pending或唯一index推断可提前推进 |
| global：级联/全局关系 | 原校准、采样、全局统计、阈值及fallback完成；阶段角色/用量可追踪 | 不按物理batch局部学习阈值，不改质量/生成策略 |
| 保留视图/压紧/紧凑源后重准备 | 实测表示确有共享buffer或独立副本；记录buffer身份/别名、真实消费者和copy/rebuild字节；新旧表示寿命交接可追踪 | 不把JSON/deepcopy称Arrow零复制，不将少行数或lease归零当物理释放 |

执行调用责任、消费者持有表示与紧凑审计分别计费。只有确认终态才释放对应执行责任，unknown继续占用；消费者结束前不释放仍读的数据。父结果转后继输入时采用显式所有权交接，预留合法后继进展空间，避免父结果占满额度而后继无法进入；失败/取消仍保存已发生调用，不把OS进程退出重写成历史成功。

任务↔表示映射至少保留occurrence、stage/call、representation/transform身份、底层buffer或独立副本身份、位置、当前合法消费者、可能后继及最后使用条件。模型结果改变后继集合/长度时更新映射，不把可能消费者当已经获准执行的工作；原图相同也不推出不同prompt的完整KV兼容。

阶段资源分开借用和归还：准备CPU槽在该段真实结束后可归还，准备表示仍由模型/后继持有；模型C/W只在确认终态结清，结果表示与parser/消费者有各自结束条件；结果容量按原协议提前预留，审计保存必要紧凑事实。模型执行批、传输批、分配块和可回收单元分别描述；细粒度记账不能绕过底层buffer/allocator的实际回收条件，改变物理粒度须计入管理和copy成本。设计依据见[跨领域参照的采用条件](../../docs/research/优化方法依据.md#selective-chain-transfer-basis)。

等待窗口中的主机工作先限定为可验证的记录/小块间yield，不假定tokenizer、decode或任意Python函数可中途抢占，也不控制GPU kernel。只有合法输入、独立CPU/字节额度和真实时间线显示机会时才准备、压紧或组织结果；ready积压时优先检验消费/回收而不是继续预取。保留工作年龄/最大延迟的预先规则，防止局部性偏好使少数任务长期拖尾；反馈和前后台维护的复杂选择在观测可靠后再加，不叠多个控制器。

### 对照、阶段验收与证伪

先用固定响应重放隔离方法和物理机制，再由唯一执行者按另行批准的计划排队真实模型；本节没有分配GPU/调用额度。每个新运行先固定源码、输入、模型/processor、资源、重复、总时间、调用上限和停止条件；不恢复历史额度。

| 顺序 | 最小检查与强对照 | 验收及推翻候选的条件 |
|---|---|---|
| 方法与暂停正确性 | 调优fused vs有界FIFO continuation无重组；F→M→E混合/全false、E→M跨批重复label、源尾报错、offer背压、慢消费者、unknown | messages/生成参数/原parser/关系/parents/实际调用一致；未接受不推进，重复完成不重发；若仍整批阻塞run_batch，不报告算子级暂停推进 |
| 依赖范围 | 相同调度，global保守版本 vs有证明的record/group版本；加入晚到覆盖、动态key、同名字段及缺键/None | 后继读取值和最终schema/顺序一致，合法就绪至提交等待减少；证明/预扫描成本大于等待收益则保留global |
| 物理组织 | FIFO无重组、后继优先无重组、同调度＋有限重组，另有byte-aware背压或阶段预算机制对照 | 实际copy/rebuild与唯一live buffer事件支持变化；只有多复制、没有query或驻留改善，则降为工程优化；机制对照不冒称原生Ray/Kalypso复现 |
| 分阶段资源责任 | 调优异步＋背压、拆阶段固定队列、再加压力控制；分别消融准备槽、表示持有和模型额度 | 准备槽归还但表示仍在、模型确认终态但结果未消费、交接失败、unknown和慢消费者均不提前归还其他owner资源；若只是换队列名而资源占用/等待不变，不报告解耦收益 |
| 简单物理控制 | 原生列投影、合理块大小、始终压紧、从不压紧；逐次只增加一种条件选择 | 按需重组须超过这些同信息控制；若静态投影/块大小解释全部收益则采用简单方案，不归为新联合机制 |
| 真实文本链 | 单遍Filter/COUNT无复用、便宜准备小任务、内存充足且模型计算占绝对多数的无机会反例；非空F→M→E/M→F→E、重复label E→M、真实全局级联 | 真实模型阶段调用/输出长度/质量与完整query齐全；若收益仅来自模型少加载、prompt/缓存/调用量变化，则不归因依赖或重组 |
| 扩展 | 原生Ray/Daft合理分阶段/fused与生命周期；Kalypso真实实现或忠实机制；图文先补原Animals接入 | 增强native图单列命名；新records仍拒绝image_url，旧Animals/CLIP不替代新资格；多卡只随已测移动瓶颈扩展 |

完整query和应用/CLI时间、调用工作与质量是主结果。每次保留ready→admit、admit→complete、ready→complete，合法依赖确定→后继实际提交等待，实际API/batch形状及模型UID/加载计数，准备/序列化/copy/rebuild次数和字节。主机驻留以唯一buffer身份去重，并积累`∫ live_unique_host_bytes(t) dt`；Python/JSON副本、Arrow共享底层、Ray object store、allocator保留、RSS及模型KV分开。RSS求和不等于唯一物理字节，GPU busy/API P99也不能替代query收益；观测开销计入并用独立轻量对照检查。

<a id="query-goal-extension"></a>
### 查询目标、软后继需求与后置扩展

第三份资料并入同一选择性链候选，近期仍先做无SLO的单卡调优fused、有界FIFO及已有后继/驻留消融，不先建设SLO控制器。已观察选择性可以更新尚不确定的后继规模、准备成本及表示需求；这些仅是软规划信息，不创建未合法的模型任务、不为所有可能后继占满硬quota。只有所需输入、依赖与求值许可确定后才进入对应硬准入；全局阈值未定时可评估模型角色预备，不能提前对未确定fallback推理。

可选查询SLO以预先规定的完整正确结果为终点：查询提交后的排队、读取/准备、传输、模型、解析、关系屏障、重组、结果消费及规定的必要收尾均在范围内。API TTFT/TPOT/P99单列，不由其达标率推断完整query达标；既有超时、取消与unknown责任不改名为SLO，也不因预测无法达标就跳行或缩短生成。离线批处理继续以完整时间/有效吞吐和资源成本评价，不要求每个任务有期限。

若后续评估剩余余量，可用`S_hat(q,t)=D_q-t-R_hat(q,t)`作有误差的启发式；`R_hat`须包含合法依赖/全局屏障、准备和重组、结果消费及已提交不可抢占工作形成的阻塞，考虑并行/组批，不能把行服务时间相加或只扣compute。估计绑定设备/模型/原生配置/负载签名并报告误差与信息成本，无法证实优势时回到同信息静态/FIFO；不从公式推出硬保证。

| 后续单元（非本次运行授权） | 对照与预先条件 | 不能通过的解释 |
|---|---|---|
| 单卡目标观察 | 先保留完整query与真实host寿命主结果，再在相同到达和任务上加入预先声明的query期限；调优fused/FIFO、后继队列/静态驻留与独立/联合消融 | 只移动准入前等待、只缩短API尾部、只增加状态管理，或相同信息的简单策略已解释全部收益 |
| 可选SLO评价 | deadline来自应用目标或评价前固定的敏感性区间，调参与评价分开；全部到达query为分母，接纳/拒绝、取消、超时、失败、缺失及未完成单列；按时正确完成query吞吐与资源成本一起报 | 测后挑有利deadline、只报成功接纳子集；一条query内2000条记录/模型调用不是2000个独立query，小样本不声称总体尾部保证 |
| 两卡/模型角色（后置） | 有实测移动/驻留或角色转换瓶颈后，先两个完整实例；比较工作守恒轮转、负载、局部性、联合完成估计，并比较延后/有界预备/始终保留/始终重建 | 计入无用预备、原模型KV/工作空间挤占和重配置；CPU服务、MPS、TP、DVFS、在途请求/KV迁移均需自身机制与资格，不由换actor或模拟延迟取得 |

已合法工作后续选择batch/实例时，联合比较输入表示何时就绪、实例可接收时间、紧凑源重准备或准备表示传递、排队及后继成本。先固定少量物理配置，快速层只在其内控制合法供给、准备深度与交付；不预设文本链存在可跨卡复用tensor。资源预备不等于记录推理，也不能把预计释放当实际释放。相关已有机制与迁移边界由[研究定位](../../docs/research/研究定位.md#selective-chain-increment)和[方法依据](../../docs/research/优化方法依据.md#query-goal-transfer-basis)维护。

<a id="short-concurrency-diagnostic"></a>
### 短期并发诊断与研究主线分开

按独立工程记录比较ee39 adaptive与fixed16反事实；B=1、transport不变、W关闭。本节只约束对照与解释，具体运行状态由唯一GPU owner的固定记录维护，不由此重启或重复分配。后续H1仅是待验工程启发式：cache-only事件保留当前operating C（当前reuse为16，来自上轮first接受值），旧收益证据标provisional/new-work-unverified；重新取得reference并暂停升档一个现有评估窗口，重复cache事件合并且不重置截止。同步actual C、epoch、phase、reference内部状态，不能只删除降档return或硬改8为16；事件前reference不是probe，新cache条件尚未验证。错误、超时和真实压力仍走原安全路径。

先用CPU事件重放验证状态/截止与责任，再比较fixed16、原adaptive、H1，必要时另测fixed32；H2剩余工作门槛＋吞吐爬山后置。W在混合长度上单独验证，等长输入可能只把C换单位；API P99下降若只是把等待挪到准入前，ready→complete或完整query不改善，则不称收益。
Netflix的[concurrency-limits](https://github.com/Netflix/concurrency-limits)与[Envoy Adaptive Concurrency](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/adaptive_concurrency_filter)只为延迟参考/采样和过载控制提供工程参照，不证明H1适合本工作负载；[Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)涉及引擎内prefill/decode调度，不把其收益转授外层C/W。

<a id="m1-throughput-platform"></a>
## 当前 M1：有效吞吐平台附近的在途工作与资源代价（2026-09-20）

本实验只回答两个问题：在单查询、不可变全扫描、固定模型与输出目标下，维持接近已测最高有效吞吐需要多少供给；
在该区域增加在途工作，是否仍有完成收益，还是主要增加排队与留存。目标不是最小提交量或服务队列恒为零：
需要保留覆盖取数、构造、通信及补充波动的供给余量。不得先减少有用计算供给，再用 HTTP P99 下降宣称查询优化。

**旧 M1 已结束其测量任务**：[常驻对照](../results/postgresql/waiting_positions_persistent_20260914/README.md)
中，W512 对 work 最小值 187 的任务最多容纳两项，不能充分使用四个受控服务槽。
HTTP P99 下降 42.23%，完整查询时间却从 0.395086 增至 1.315864 秒。这是指标反例，
不证明 token 控制优于调优请求数，也不证明有限候选优于全局轻量信息。不继续重复这一欠供给比较。
原始输入、代码快照、时间线及全部失败保留。

### 先检查可达性，再消耗模型额度

`m1_campaign.py` 改为显式 v2 配置，每次只执行一个阶段。`--preflight` 只读本地身份与预算，
不连接 PG、不加载模型或 tokenizer、不初始化请求账本。各扫描点共用同一份存储设置、CPU/服务配置和输入身份。
逐点输出请求上限、Core 留存项数、结果预留可支持项数、输入字节可支持项数、PG 行窗口/留存/暂存与客户端配置。
服务 `max-num-seqs` 是内部执行配置，不直接等同于客户端在途数；真实 running/waiting 需另测。

源码每项 Map 最大响应预留为 1 MiB，因此旧 Core 结果 32 MiB 使实际接纳数不超过 32，C64 扫描点不可达。
32 MiB 是上游配置，不是 GPU 能力。若计划留存 128 项，仅 Core 结果预留就需至少 128 MiB；输入、PG 等还须逐项通过。
新的静态估量采用 manifest 字节上限、最坏 JSON 转义、现有 PG 行分配公式及保守元数据余量；
它只证明声明资源允许目标供给，运行中仍要核对实际计划窗口、字节使用和持续在途曲线，不能用瞬时峰值代替。
资源不够时返回具体原因，不在线缩减响应预留、切换 CPU、降低模型 context 或改输入来凑出有效点。
若研究固定存储下的限制，另立身份，不混入服务能力扫描。

### 分阶段选点与独立评价

1. **容量筛查 `screening`**：只用调参输入；匹配请求数 FIFO（按输入先后提交），两条路径使用相同的、至少三个可达 C。
   PG 复用 `PersistentMapGateway`；匹配 direct 复用 `pg-source-direct` 的有界客户端，模型消息与生成设置逐项核对。
   该 direct 仍含 PG 源读取和每查询客户端准备，属于匹配执行参照；两条路径时间不能相减解释为纯 PG 开销。
   若两者都停止增长，只能先报告各自路径的平台候选；要把它解释成服务能力，须另以已有 `DirectMap` 的准备输入路径
   排除共同取数/客户端供给限制，并核对服务观测，不新建调度器或把参照冒充原生系统。
2. **工作量调参 `strategy-tuning`**：仅在供给有解释力的区域，固定 FIFO 顺序，以已调优请求数为参照，
   在相同有限较高 C 下检查少数预先列出的 W。C 作为保护上限，W 由调参结果决定，不预置“紧 W4096 必须有效”。
   各策略获得相同资源与调优机会；记录尝试过的全部点与额度。W 未触发、吞吐下降或与简单控制相当均保留，
   不调整 context 迫使 W 起作用，也不换评价数据追求优势。
3. **独立评价 `evaluation`**：先保存调参决定及其 SHA，记录选定组、服务签名、输入身份、资源和判定规则；
   评价配置须逐项匹配该决定，使用独立评价输入。主要组见下表；不在看到评价结果后重选 C/W。
4. **观测开销 `observation`**：仅选少量代表组做完整/摘要记录配对；不将日志模式扩成所有 C×W 的矩阵。
   每次显式列出全部轮次顺序；第零轮为预热，其余是同服务生命周期内的配对重复，不冒充独立服务启动样本。

| 比较组 | 选取依据 | 能回答什么 |
|---|---|---|
| 有限较高并发 request FIFO | 已测平台附近或更高、资源允许的 C；不使用故意 OOM 的无限提交 | 更多提前提交的完成收益及资源代价 |
| 调优 request FIFO | 调参中维持近似吞吐的较小 C，独立评价复核 | 简单请求数控制能做到什么 |
| 调优 token FIFO | C 为相同的较高保护上限，W 独立调参；实际有 work-only 阻塞 | 工作量信息相对调优请求数的增量 |
| 少量 token 表征消融 | 与较高 request FIFO 同 C，W 对所有该 C 项集合均不生效 | 分词、描述与记录成本；也给同 C、只改 W 的归因提供参照 |

完整策略比较允许 C/W 数值不同；归因 W 时保持同 C、同顺序、同观测和其余设置。

### 平台与不确定性的判定

主量为 `X(C)=完整且合法完成的任务数 / 调用入口至客户端 EOF 的完整查询时间`。
合法但语义判断错误的输出保留在吞吐计数和质量分母中；非法、缺失、重复输出以及关联/资源/请求计数错误停止该阶段，
失败证据继续保存，不能删掉失败重复再选点。实际输入/输出 token、输出变化与标签质量同时报告。

只在声明的可达集合内计算 `Xmax`。`epsilon` 在运行前确定，候选较小 C 满足 `X(C) >= (1-epsilon) Xmax`。
3% 可以作为待审阅选择，程序不再内置 97% 规则；同时必须声明最少重复数、可接受重复范围以及中段供给判定参数。
`select_capacity()` 要求完整配对记录、实际 HTTP 持续供给与重复原值，并分别返回：

- `platform_candidate`：已测集合内的平台候选，仍须独立评价；不宣布饱和或统计等效。
- `no_platform_observed`：最高两个档位仍有超过声明差异的持续改善。
- `inconclusive_supply`：至少一个点缺少持续供给；优先检查实际读取、通信、留存和客户端。
- `inconclusive_repeat_variation`：重复波动或配对差异跨过判定值，当前不明确。
- `lower_supply_range_unresolved`：最小档位已是观测最好点，尚未辨明更低供给范围。

程序使用配对吞吐比的全部原值和观测最小/最大范围进行保守筛查，该范围不是置信区间。
至少三次测量只是输入完整性要求，不保证充分重复；最初小规模筛查若波动太大，先报告不明确，
再单独设计新的重复数与额度，不自动追加。评价同样报告配对差异，不能挑最快重复。
查询全程的启动和排空保留在主指标；固定中段仅用于解释是否持续供给，不删除不利时段制造平台。

### 指标、数据与解释规则

主表保留完整 JCT（调用至消费完毕的时间）、有效完成吞吐、合法性、任务质量、输出差异、失败和实际调用量。
机制表按数据所在位置分别记录：尚未物化、已准备未提交、HTTP 在途/服务等待、模型执行、已完成未消费。
不能把尚未物化任务数叫内存字节，也不能因服务排队减少就声称整个系统少留存了数据。

现有记录器继续提供逐行等待、PG 留存峰值、Core 逻辑占用、实际 HTTP 曲线及进程 RSS/CPU 采样。
新增离线汇总给出每个逻辑域的占用时间积分、每个已采样进程的 RSS 字节秒与 CPU 时间增量，
从观测区间计算；缺少区间不填零，Core 结果预留不当成实际响应大小，PG 完整字节时间线缺失则写 unavailable。
所有常驻 gateway 与 driver 在两条路径运行期间统一采样，活跃 PG reader 另由各查询采样。
逐进程峰值不能相加称同时峰值；RSS 可能重复计共享页，逻辑预算下降不等于物理内存同比下降。

vLLM 0.25.1 的 [Production Metrics](https://docs.vllm.ai/en/v0.25.1/usage/metrics/)
列出 running/waiting、排队、KV 与抢占等字段；未来执行前按部署实例实际输出核对，不把文档字段当本轮已测值。
当前编排会明确记录服务指标尚未附加；未来由已有服务采样器提供独立文件。GPU 利用率与 MFU（模型算力利用率）仅用于解释，
MFU 缺少可信运算量及对应精度峰值时不报告。[Optimization and Tuning](https://docs.vllm.ai/en/v0.25.1/configuration/optimization/)
讨论了抢占/重计算的代价，但本项目旧 M1 没有测出该机制，不能借文献补写因果。

| 观察 | 解释 |
|---|---|
| 吞吐相近，实际留存或服务排队减少 | 存在减少多余提前工作的空间；先排除队列转移 |
| HTTP 尾延迟下降，完整 JCT 变差，上游等待增加 | 等待移动或供给不足；明确吞吐代价 |
| 吞吐改善且测到额外工作减少 | 有执行收益信号，机制仍须对应证据 |
| token 与调优请求数相当或更差 | 当前负载保留简单请求数参照，不强求复杂控制 |
| 合理点持续增长或供给始终不足 | 尚不能评价服务平台附近的限制 |

已准备的短评论继续用于基础容量、表征成本和近同质控制，不单独支持异质 work 优势。
若请求工作量相同为 w，则 W 等价于请求数上限 `floor(W/w)`；当前 work 174–249、均值约 199.833 的评价输入
尤其需要面对调优请求数参照。后续只有明确的工作量失配假设才增加一种真实异质性；
不通过调大最大输出冒充长输出，应报告真实输出长度。

### 2. 最小模型：信息、责任与用户目标

对查询j保留逻辑输入、依赖和实际SQL语义；对合法工作i保留行出现ID、所属查询/阶段和完整请求身份。
模型允许轻量全局元数据与有界payload同时存在；不能因当前API尚不暴露某信息，就在对照中禁止获取它。

| 量 / 状态 | 定义与现有观测 | 不能混用的事实 |
|---|---|---|
| 查询释放r_j、终点F_j | 主目标JCT_j=F_j-r_j。先声明终点为客户端观测EOF，另报结果持久化时间；若比较写回，则F_j改为已核验写回提交，两种合同不混排 | 现有q0计时从SQL/direct release开始，**不含**此前gateway/tokenizer启动；新实验须另报查询专属准备和冷启动，不能重解释旧JCT |
| 工作资格a_i | 与被比较策略独立的合法可执行时刻：固定全扫描可用共同release/离线输入条件定义，依赖场景由上游语义结果决定 | child被拉取、token化结束或Core接纳会受策略影响，不能直接当共同a_i；不能观察时标unknown，仅报告release至完成及可测子段 |
| 提交s_i、完成观察f_i^obs | 分别用Core实际提交和权威终态被Core处理的时刻；direct用自身出站/完成事件，路径定义分别登记 | Core终态是外部观察，不是真实GPU kernel结束；HTTP开始/结束不是Core计算责任释放，内部queue/model耗时未知时不拆造 |
| PG就绪g_i、节点交付h_i、客户端收到d_i | 诊断构建的result_ready、node_return与实际客户端received；用独立before-offer/accepted绑定连接行ID | 不将d_i-f_i^obs直接叫PG节点留存；同机时钟已核验后才能相减，多机时钟须另处理 |
| 输入观察范围、候选集、存储与计算责任 | 分开已知元数据集合、已物化payload、合法候选、已提交未结算、已完成未消费结果 | L是行数，B_r是特定内存域字节，C是请求数，W是校准单位work；相同数字不代表相同资源 |

在这些时点均可比较时，逐项保留恒等式：

$$
d_i-a_i=(s_i-a_i)+(f_i^{obs}-s_i)+(g_i-f_i^{obs})+(h_i-g_i)+(d_i-h_i).
$$

资格到提交和完成到消费的等待不能遗漏。若只能观察child返回后的时间，须明确这是部分区间；
不能靠把资格时间推迟到接纳时来降低“端到端”延迟。
全扫描主要比较完整JCT、资源和质量；多查询增加逐查询JCT/slowdown与最长无服务时间；
LIMIT另比较需求满足时间及多做的工作，并先满足原有严格按需语义，不用全扫描重排权限替代LIMIT资格。

查询专属全局扫描、metadata排序、额外随机读取、token化和组织均进入新比较的外层计时；
可复用metadata必须另报建造/刷新/储存成本和按什么复用次数摊销，不将预先算出的评价集信息免费提供给某一臂。

### 3. 可以证明什么，以及目前不能证明什么

以下是明确模型下的数学推导和证明任务，**不是新增算法贡献，也不是完整实现已被形式化验证**。

**资源安全。** 对内存域r，令L_r(t)为仍由该域负责的数据，m_ir(t)为它实际计费的表示或足以覆盖分配的预留，
M_fixed为固定开销。要求：

$$
M_r(t)=M_{r,fixed}(t)+\sum_{i\in L_r(t)}m_{ir}(t)\le B_r.
$$

若初始状态满足预算，每次转换都在分配前检查“旧占用+新表示+必要暂存”的峰值，责任交接不重复漏计，
只在相应责任真正结束后扣账，则对转换次数归纳可得不变量。C的证明对象仅为实际计费的行上下文/元数据及各自有界暂存；
要将结论连到代码，还需列出全部接纳、转换、结果预留、交付、异常与未知终态转换并检查。它不约束整个PG/gateway/Ray RSS，
也不证明吞吐或最终一定完成。现有测试与事件重放是该证明任务的支持证据，不替代穷尽转换的证明。

**积压面积。** 对包含所有a_i和d_i的完整有限观测区间，N(t)=Σ_i 1{a_i≤t<d_i}，有

$$
\sum_i(d_i-a_i)=\int N(t)\,dt,\qquad
\sum_j\omega_j(F_j-r_j)=\int\sum_j\omega_j1\{r_j\le t<F_j\}\,dt.
$$

证明是对每个指示函数积分，再有限求和；第二式要求权重预先固定。内存驻留成本另记为∫M_r(t)dt，单位B·s。
观测不完整时只能积分截断区间，并报告未完成/取消项，不能把其当作完整sojourn或只剩成功样本。
离散RSS采样面积只是采样近似；完整逻辑状态转移的阶梯积分可以精确重算。
这些有限样本恒等式不需要假设M/M/1；[Little的2011原文](https://pubsonline.informs.org/doi/10.1287/opre.1110.0940)
§2.1.2也讨论完整、两端为空的有限观察段，不能反过来要求所有有限查询均为平稳过程。
平均关系本身不能推出P99、最优窗口或当前有限工作集的系统稳定性。

**按序消费的反例。** 单个单位速率串行执行器、全部任务在0时刻合法、确定耗时p_i>0、无局部性/切换收益，
结果按输入序即时交付，且没有额外传输、消费阻塞或并发效果。任意顺序完成输入前缀i至少处理Σ_{k≤i}p_k的工作，故

$$
d_i\ge\sum_{k=1}^{i}p_k.
$$

无空闲FIFO对每个i达到该下界。输入耗时[10,1]时，FIFO的有序交付为[10,11]，短项优先为[11,11]。
因此不能用短任务优先的无序完成优势证明本项目按序结果一定更快。方法必须指出利用了哪条不成立的假设，
例如并行资源互补、真实prefix复用或阶段重叠，并用对照单独识别它。

**有限动作的决策误差。** 给定同一状态s、同一有限时域/终端代价和有限合法动作集A(s)，
令J为真实代价、Jhat为预测，假定对所有候选同时成立
|Jhat(a|s)-J(a|s)|≤ε，选择误差至多δ，即Jhat(ahat|s)≤min_a Jhat(a|s)+δ。令a*最小化真实代价，则

$$
J(\hat a\mid s)\le\hat J(\hat a\mid s)+\varepsilon
\le\hat J(a^*\mid s)+\delta+\varepsilon
\le J(a^*\mid s)+2\varepsilon+\delta.
$$

若采用逐动作界ε_a，只有Jhat(a)+ε_a<Jhat(a_0)-ε_0才可在这些界成立时判断候选优于强静态a_0；
实际下发动作还须满足对应不等式，不能忽略近似求解误差。RMSE、单个动作的覆盖率或被选动作上的误差均不自动满足同时误差界。
若使用统计界，须声明覆盖概率、候选比较/自适应选择的处理；有限时域结论不推出整查询全局最优，未获保证时保留静态动作。

**进展与公平仍是独立证明任务。** 有界队列可把积压转移到入口；平均服务差也不能推出查询P99有界。
证明候选不会永久饿死某项，至少需要有限或受约束到达、每项可容纳、消费最终继续、资源释放被观察、后端最终给出权威终态、
选择器具有公平机会等前提；未知终态可能合法保持计费，此时应有限地失败/隔离而不是编造完成。
尚未证明当前端到端执行在任意黑盒服务下均可推进。Neely有限缓冲研究中的丢包条件与SQL不能丢弃必要行冲突，
有限重排缓冲的颜色切换成本也不等于KV生命周期；见[理论迁移条件](../../docs/research/研究定位.md#execution-transfer-cards)。

### 5. 候选方法与既有实现落点

候选为**消费进度感知的有界组织**：只对合法、可观测、尚未提交的工作，比较继续准备、现有FIFO/长度次序、
促进结果前缀消费及少量准备深度动作。它是等待M1/M2及最近邻审查的候选，不是已实现/已证明的新算法。
在物化预算内保留多少未承诺工作，需要真实查询进展和驻留代价支持；不添加十几个无依据的评分权重。

| 数学对象 / 能力 | 已有落点 | 本轮决定 |
|---|---|---|
| 行身份、合法输入、消费序和取消 | PG child plan、语义节点、独立结果绑定 | 沿用数据库语义；新动作不能扩大合法求值范围 |
| 行/暂存计费与消费释放 | `sem_pump.c` total预算；资源事件 | 沿用C；增加域或证明时逐一列实际责任，不能映射成进程RSS |
| 完整消息work及校准身份 | 模态adapter、`WorkDescriptor`、`MapOrganizationConfig` | 复用D；与真实token usage核对；不把单项max-new上界解释为运行时长 |
| 候选和组内次序 | `WorkWindowOrganizer` / 已有organization回调 | 现有FIFO/有限长度控制作对照；消费进度信息尚未接入该策略，不宣称已支持 |
| 计算容量、提交、终态 | `SessionCapacity`、`SessionEngine` | 不复制账本；后端权威终态前保留未知责任 |
| 查询机会与阶段能力 | 既有Job/flow选择、MethodDriver和可替换backend | E/F按实验需要补最小适配；PG方法桥接、动态份额和图像阶段不因接口存在而算已验证 |
| 全局元数据、反事实与误差 | 实验/离线分析层 | 先构成强对照，未知未来完成时长仅可作明确的离线oracle；不泄露给在线候选 |

每个动作都要对应实际变化：读取/准备次数、被提交任务、提交时刻、传输或资源使用至少一项改变。
只改batch ID而物理执行不变的分组不能成为独立优化；不允许拼接多个prompt或强加整组完成屏障来制造收益。
对于未来候选，先在小状态空间枚举/受控反例核对合法性、安全和有限模型下的反事实，再安排真实M1/M2；
模拟只能证明所声明模型，不替代真实PG/模型对照。

以及broker内物理持有者/暂存和待消费准备状态；继续由现有SessionEngine负责任务与请求容量。
普通内存、Ray对象、锁页内存与显存记录包含关系，不能把准备张量额度冒充全进程硬上限。
实际资产延迟读取、后继求值许可和延迟错误需要新增接口，当前尚未实现；PG路径另做语义及wire检查。

计划中的后续诊断先复用无共享、不同变换、稀疏窗口、慢消费、原生热cache与模型充分供给的反例；
增加低通过率、准备长于筛选、损坏但被筛掉的媒体、相同目标但decoder状态不同等情景。
元数据/索引、cache建造更新、冷/热I/O、spill/restore、未使用准备和结束等待均计入。
事件按各自时钟记录并对齐定义；异步提交只记提交，设备完成另取可确认事件。
这些是待执行的检查项，不是本次已有检查结果；环境、资源清单、重复与停止条件确定后才安排运行。

具体引擎接入位置先按[架构选择](系统架构.md#engine-extension-placement)确定推进、额度及终态负责人。
原生媒体对照保留固定版本已有的批内同shard解码；按episode关联减少帧行，仍需实际I/O/解码证据。
固定任务与完整语义系统按[分层对照](reference/对照规范.md#execution-comparison-levels)分别报告，不更换原生执行负责人。

### 6. 近期交付与停止开发的条件

1. **已完成文档交付**：本节五类设计选择与来源/反例表、明确作用域的最小模型与推导、M1—M4对照规格；
   知识库维护论文可见信息/动作/目标/保证/迁移条件，证据仍归各结果目录。
2. **下一步定位 M1 供给问题**：本轮真实容量筛查未得候选，先解释gateway CPU和观测成本，再制定新校准。M2实验层全局元数据已运行，实际SemMap接入与方法效果另验。
   这些测量/对照缺口尚未实现；先使比较可执行、可审核，再给出有限GPU预算，不能先实现复杂proposed再找支持数据。
3. **按反事实选择方法**：全局元数据净收益更好就采用全局/混合；调优请求数已足够就将token额度定位为资源控制；
   只有消费序/驻留代价解释了真实改善，才实现消费进度策略。M3/M4按其结果选择，不串行建设完整E/F。
