# 原生基线校准

本计划区分两个问题：已有 LOTUS 方法＋框架执行图中的工程限制是否合理，以及直接使用框架原生 AI API 的
SemBench 端到端表现。不是官方 runner 复现声明，也不将依赖版本不同的产品比较解释成纯调度收益。
接口与默认值归[执行配置](../../docs/执行配置与优化开关.md#native-baseline-controls)，实现资格归
[代码状态](../../code/INFRA_STATUS.md)，正式指标沿[对照规范](reference/对照规范.md)。
首测失败与后续CPU修复见[诊断报告](../results/diagnostics/native_sembench_q3_20261106/README.md)，
本计划不把准备完成或已有输出解释成完整实机通过。

## Movie Q3 的固定语义与输入

使用 SemBench `c814e3807e72d4cf876b852b17e77f3cc94575c2` 的
[原 Q3](https://github.com/SemBench/SemBench/blob/c814e3807e72d4cf876b852b17e77f3cc94575c2/src/scenario/movie/runner/lotus_runner/lotus_runner.py)：
完整读取 Reviews，先按 `id == "taken_3"` 筛选，再判断
`Determine if the following review is clearly positive. Review: {reviewText}`，最后 COUNT 返回 `positive_review_cnt`。

本次公开 `files/movie/data/sf_2000/Reviews.csv` 原字节 SHA256 为
`df231cfb189c9e169aa6afe415e4fa24533b04499179bbd61416c4c6af28ca21`，Git blob 为
`710028a863dbf04853e45a3e618113dff7521b4d`；本地已核实654791字节、2000行、1865个唯一 reviewId。
普通筛选后120行，120个唯一 reviewId，无空 reviewText；标签14 POSITIVE／106 NEGATIVE。
仍按完整源位置生成 occurrence_id，不假设业务 reviewId 唯一，不去重、不截断，不向模型提供标签。
旧4016次 campaign 不是此输入，不能混合或按重复实验删除。

[中立任务合同](../../code/src/baselines/text/sembench_movie_native.py)不导入 LOTUS 或 SemLoom 执行器。
消息与普通 Qwen 模型的 LOTUS1.2.4 DEFAULT、非 CoT Filter 做真实 SDK CPU 差分：
原上下文格式、原指令、原 Answer 解释、True 优先和解析失败 default=True 均保留；另显式记录 unparsed 数。
Ray 使用原生 chat-template stage；Daft 的原生 AI 表达式接收原始字符串，由同一个模型 tokenizer
对这些消息调用 `apply_chat_template(tokenize=False, add_generation_prompt=True)`。运行前须比对实际模板输入，
不能把 raw 文本直接交给 Daft 而声称模型输入相同。此合同不扩展到 DeepSeek 专属后处理或其他序列化格式。

质量同时报告原 MovieEvaluator._evaluate_q3 及120条的 TP／FP／TN／FN、未解析数和 count error。
COUNT 恰好相同不能掩盖 FP／FN 抵消。审计和计数消费同一份物化预测，不为审计重新执行 AI 图。

CPU 阶段支持的 concurrency 可以调；此 pin 的 stage batch_size 实际会被 processor batch_size 覆盖，不能发布无效旋钮。
真实 builder 会初始化 Ray、读取／下载模型元数据，不能在所谓零模型 CPU check 中直接调用。

## Ray具名信号量的零模型复现（已执行）

先修复下次临时控制器的判定：只调用一次`resource = monitor.finish()`，完整成功同时要求原worker／进程／GPU条件
和`resource['passed']`；原轮FINAL保持原字节。这不修复IPC来源，也不能靠人工unlink把原失败改成通过。

原四例计划使用现有Python3.12.3／Ray2.56.1／tqdm4.67.3环境，实际已各执行一次，模型请求为0，
不导入vLLM／Torch／模型模块，不读取权重、不建立推理服务。每例独立监督进程，最多60秒且包含末尾10秒强制清理，
总工程上限4分钟，不自动重试；非预期错误或归属不明即停止。仅后三例启动CPU Ray，每例`address='local'`、
`num_cpus=1/num_gpus=0/object_store_memory=128MiB`；GPU不可见、沿既有host租约与CPU亲和性，
采样RSS／SHM边界分别8GiB／512MiB，产物至多32MiB，全部位于新的数据盘私有目录。
这些是小型CPU诊断的显式边界，不改变原生Q3测试资源或框架默认。

| 例 | 关闭方式 | 需要区分的行为 |
|---|---|---|
| 普通spawn | 子进程首次创建tqdm后正常返回 | 单锁创建和Python正常unlink对照 |
| Ray显式关闭 | actor中显式close并确认子进程退出，再丢弃handle | 业务子进程先正常关闭是否避免残留 |
| Ray actor GC | 丢弃handle，保留runtime并等待actor退出 | 隔离原生actor GC的child kill／callback顺序 |
| Ray runtime关闭 | 丢弃handle后立即shutdown | 原计划区分额外影响；实际GC早于shutdown，本例不能单独证明其因果 |

用Pipe通信，避免Queue／Event额外创建信号量。必须在首次tqdm构造前安装仅观测、不改变参数／返回值的诊断包装，
记录每个SemLock的实际名称、kind、创建栈（basename／函数／行号）、register／cleanup／unregister；
读回父默认context、指定Process context和child target实际默认context，不能由环境变量推测。
私有证据另保存tracker PID／命令类型／pipe inode、child exitcode、actor hook进入／完成时间和原Ray kill列表。
不因“正好一个锁”就将所有新`sem.mp-*`归给tqdm。

正常对照要求新对象名称／身份匹配、exitcode0、清理回执和对象消失；GC若未复现则记未复现，
不扩大模型规模补证据。只有已确认本次创建、inode／ctime及归属匹配、无活动持有者且自有进程退出的对象，
才可单独回收并另记恢复；禁止按前缀清空SHM。

实测与固定Ray源码已指向正常退出先杀子进程的顺序。最小上游候选是正常路径先完成actor shutdown callback，
再清理尚存子进程，强制／超时路径继续保留child cleanup，并在同一期限内完成；须由上述CPU反例验证。
当前公开Processor没有模型actor的close入口，不能为了规避该顺序改用项目私有执行器；
不全局关闭Ray child cleanup，也不把延迟driver shutdown或降级vLLM当成已验证修复。
四例实测总19.443秒，spawn／显式close自动清理，actor GC／runtime各留4KiB；创建栈及锁身份匹配tqdm RLock，
子进程被Ray以-9结束且缺少unregister。原失败和已确认对象的后续恢复分别保留，
见[CPU证据与因果边界](../results/diagnostics/native_sembench_q3_20261106/README.md)。
没有修改或重建第三方库；官方0.22组合若另行安装，仍需独立环境和完整解析，不能覆盖候选结果。

## Ray公开HTTP拓扑的显式服务所有权（CPU已验证，模型待验）

[独立绑定](../../code/src/baselines/text/frameworks/ray_data_http_sembench_native.py)使用公开
HttpRequestProcessorConfig／build_processor，不访问内部model actor。外部caller先启动服务，再启动独立Ray query worker；
完整物化／COUNT后确认worker退出和Ray自有资源，再显式关闭服务、join并检查外部资源。服务不是Ray actor的子进程。
原local-vLLM路径及失败不改；这是服务拓扑不同的项目profile，不能标作原失败修复或官方runner。
SDK连接断开和进程物理退出分别记录，后者由外层资源supervisor核对。

先做两例零模型软件HTTP验证：完整Movie2000→120、固定回复COUNT14；另用1个eligible行返回明确错误JSON，
要求保留失败、不得落入default=True、服务仍正确关闭。正常情形预计120＋1次软件POST，无模型请求或warmup；
原生Ray任务重试保持并从endpoint观测实际attempt，不能仅按逻辑数推断。
HTTP默认batch64／concurrency1／qps=None／max_retries0不覆盖，qps=None批内原生逐条await；
实际inflight从服务观测，软件delay仅区分重叠，不产生模型吞吐结论。
每例新service／Ray worker／目录，显式8核亲和性、num_gpus0、Ray object store512MiB、20GiB采样RSS及1GiB SHM边界；
每例总180秒含20秒收尾，末尾8秒用于强制停止。全部数据盘、沿既有host租约；不安装软件、不改第三方库、不启动GPU。
意外请求／输出或资源错误保留并停止，只有两个预定case各自满足正常／失败合同且清理通过才算CPU资格。

上述两例已在准确6996各执行一次，实际POST为120＋1，独立读回无supervisor强制信号／错误、
服务nonce正确且显式关闭／资源检查通过；预期错误的原failed状态保留，不重跑完整查询。
正常例实际HTTP peak inflight2，未修改原生默认；软件正常回复由金标固定，不是模型质量。
详细原件摘要及初版私有probe未覆盖的异常路径见[CPU报告](../results/diagnostics/native_sembench_q3_20261106/ray_http_cpu.json)。
软件HTTP通过仍不证明真实vLLM服务退出；真实GPU服务、tokenizer／chat template、生成配置、模型ready、
实际容量与physical attempt均待独立资格。将来冷查询包含服务启动及关闭，常驻查询另计；
不能把只含Ray query的API时钟与此前完整冷查询直接排名。
