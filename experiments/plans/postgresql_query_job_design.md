# PG查询级Job归属：详细设计与最小接入

状态：当前接口详细设计；普通Filter/Map最小切片已验证，后续choice/窗口扩展仍待单独设计。基线`c2bf4c5e`。
结果见[查询Job验证](../results/scheduling/query_job_20260909/README.md)。权威范围是PG查询执行身份、外部Job登记和算子流归属；
不替代[多Job核心设计](semloom_multisession_design.md)，不新增SQL组合或动态借用算法。

## 目标与最小路径

同一次PG查询执行中的多个语义算子使用一个外部Job、一份预算；重复执行同一个prepared SQL必须
得到新的查询执行身份，两个游标也不得因SQL相同而混用Job。最小验证使用已有的双Filter AND和
Filter→Map，不为了验证身份先扩展双Map/CTE/任意嵌套支持。Filter保持逐行请求的同步SQL行为，
请求仍由共享增量核心执行；Map复用v6，首版查询归属模式采用窗口1。

## PG归属与生命周期

一个EState的es_query_cxt拥有一个QueryJobOwner；多个算子登记本次执行内稳定的流序号。
节点初始化只登记本地信息，不访问网络；所有节点完成初始化后，首次真实任务才建立查询控制连接。
控制连接登记已知算子流数，服务返回新的随机能力令牌；令牌只保存在本次执行内存，不进入计划、
SQL参数、GUC、EXPLAIN或日志。PG仅传递归属/流数，不给Job发放资源预算。

- 正常EndCustomScan：关闭所属流；全部节点End后结束查询控制连接。一个节点EOF不能单独结束Job。
- ReScan：保留当前明确拒绝的行为。本轮不扩展重扫；未来支持时另行规定重新求值和旧远端任务的回收。
- ERROR、取消、游标关闭、backend退出：查询资源释放与内存清理兜底关闭控制连接，网关结束该Job。
- 清理不得等待模型、再次抛错或要求成功发送最后一帧；控制连接EOF也足以结束登记。
- 查询结束不表示事务提交。外部层不得据此宣布INSERT已提交；PG仍拥有事务与结果生命周期。

## 版本化登记层

新增显式opt-in的query-job接入模式；旧v3/v4/v5/v6用户路径保持原行为。登记层有独立版本，
先完成query_open或stream_join握手，再使用原语义协议，避免把查询身份塞入语义prompt或payload digest。
验证与观测记录“登记层版本+语义wire版本+provider身份”，不能只记录旧wire版本声称路径未变化。

1. query_open携带版本和正整数flow_count；服务端分配一次Job预算，返回不可预测的令牌和登记结果。
2. stream_join携带令牌和流序号；服务验证控制连接仍存活、同一可信peer进程、序号在范围内且无旧占用。
3. 语义open/task/completion复用既有严格codec和parser，不把query token加入CompletionRequest。
4. 控制连接结束后拒绝所有新加入，取消现存流；迟到权威终态继续回收旧Job，不能投递新查询。

首版可信peer来自Linux AF_UNIX SO_PEERCRED，绑定uid/pid与活控制连接；不是客户端自报字符串。
不同peer即使知道标签也不能加入。PID不是查询身份，同进程不同查询仍由不同控制连接和令牌区分。
不支持该peer验证能力的平台明确拒绝本模式，不能静默降级为任意令牌/相同用户名即可加入。
所有新连接仍受同一连接数、frame字节数与超时限制；令牌不可写入观测日志。

## 一份Job预算与流内进展

服务/Job预算归执行组装与核心。登记层只申请；默认分配策略从Job存储份额中给每个已声明流
保留最低接纳空间，所有流合计不得超过Job份额。声明更多流不会获得更大Job份额；预算不足时
在登记阶段拒绝，而不是让PG执行到一半陷入等待。

只做Job总上限还不够：若一个流占满所有结果预留，而PG正在等待另一个流，就可能没有进展。
首版静态流存储份额用于避免这一情况；计算额度仍由共享核心检查与轮转，不在PG实现调度器。
方法状态总预算和动态借用不在本轮实现。Map首版窗口1；后续扩大窗口须按协商容量补充接纳/背压验证。

流关闭后有未知远端工作时保留原占用，不能让同一流序号重新打开而获得第二份额度。Job直到
控制连接结束、各流关闭、全部lease和权威终态结清后才退还预算。

## 网关实现与复用

复用现有连接管理、单控制线程、命令槽/结果槽、SessionEngine、执行组装和backend。不增加第二个
服务循环。连接线程完成有界首帧解析并向控制线程申请登记/加入；只有控制线程改变核心账本。
同步Filter协议处理器通过同一会话代理提交和收取完成，不能再直接调用另一个独占容量的模型客户端。
跨连接组关闭由登记层统一触发，单连接断开与整个查询结束有独立含义。

## 验收与停止条件

- 同查询双算子同Job；另一条查询不同Job；重复prepared执行、两个游标分别建立身份。
- 多流预算合计不超限，增加流数不增加Job机会；容量不够时有明确错误，无无限等待。
- 零任务/NULL/LIMIT0/EXPLAIN不调用模型，最好不建立控制连接。
- 取消、错误、LIMIT、游标关闭、子事务错误与backend断连；重扫继续明确拒绝；另一查询继续，旧资源不提前释放。
- 非法令牌、错误peer、重放/重复流、已关闭控制连接、超出声明流数均拒绝；有界收发仍成立。
- 保持所有旧路径回归。真实模型沿实际双Filter或Filter→Map验证语义与归属，不用producer冒充PG接入。
- 真实运行前补充独立请求账本、具体输入/预期调用上限、源码/模型身份与清理条件；任何断言失败
  保留证据并停止该次运行，修复后新建账本，不以fixture通过替代真实模型验证。

## 本轮实现及运行切片

实现落点：`pg_query_job.c`负责查询控制连接、流登记和ResourceOwner/查询内存清理；
`uds_connection.c`复用原非阻塞建连和FD记账；`QueryRegistry`将已核验的内核peer与活控制连接
映射到Engine句柄；`IncrementalExecution.open_query_job()`从既有Job分配策略取得预算后分割
流存储份额。网关沿用同一个控制循环，Filter v3通过会话代理执行，Map使用v6。

首版`query-job`只接入普通生成Filter v3与Map v6；choice Filter v4明确拒绝，旧独立v4路径保留。
PG Map窗口固定为1。`query_error`返回固定错误码`QUERY_CAPACITY`或`QUERY_MEMBERSHIP`，
不返回令牌、输入或策略异常原文。连接容量检查覆盖控制连接与声明的流；闲置查询控制连接
不使用单次模型超时，查询结束/断连负责关闭它。重扫仍按现有carrier拒绝。

PG18.3固定源码的`src/include/utils/resowner.h`提供ResourceOwnerDesc及Remember/Forget；采用
资源释放回调和查询MemoryContext回调互相兜底，不增加全局Executor hook。ResourceOwner已移除
条目后，回调不得再次Forget，也不得等待模型。节点初始化登记本地流数，第一次任务才连接；
一个流正常断连保留Job，查询控制连接关闭才取消整个组。

真实模型验证是工程正确性测试，不做性能、质量或公平性结论。使用已验证的Qwen2.5-7B-Instruct
固定版本、单服务实例和原服务参数；运行前重新核对模型/代码/扩展哈希与环境。模型由本次控制器
启动和清理，不使用公司输入。全部输入为合成文本`TRUE`，Map要求原样输出，两个Filter分别判断
“输入为TRUE”和“输入非空”。Job数3、总任务存储6、物理并发2、连接容量12；这是验证配置，
不是最佳配置或GPU容量结论。每次运行独立账本，上限24次HTTP POST：

| 场景 | POST数 |
|---|---:|
| 双Filter、Filter→Map各LIMIT 1 | 4 |
| 同一prepared SQL执行两次 | 4 |
| 两个PG连接并发执行Filter→Map | 4 |
| 同一backend两个游标，各取一行 | 4 |
| INSERT约束错误及单Map恢复 | 3 |
| 双流已运行后取消正在等待输入的PG查询 | 3 |
| 取消后新查询恢复 | 2 |
| 合计 | 24 |

LIMIT0、NULL与plain EXPLAIN必须零POST且无外部Job。受控backend额外验证控制连接关闭时
在途远端额度仍保留、另一Job继续推进；真实取消场景不会冒充模型请求在途取消。任何断言失败即
停止本次运行并保存账本；修复后的复测使用新目录与新账本。验收要求12个查询Job、11个双流Job、
1个单流Job，15次Filter及9次Map完成，每个结束Job的任务/在途计数归零；模型/PG/gateway
进程、监听端口和GPU占用清理后才报告运行完成。


### 首次真实运行与复测调整

首轮按上述不同条件运行，第二个条件“输入非空”对TRUE返回UNKNOWN；LIMIT 1最终读取两条非NULL行，
共4次POST后预期结果断言失败。该运行保留为模型判断未达到合成用例预期的失败证据，未更改解析器或
将UNKNOWN改判为TRUE。查询归属与消息核对没有发现内容改写。

后续复测仍采用上表24次上限及严格TRUE输出，双Filter改成两个相同的“输入为TRUE”条件调用。
先用EXPLAIN确认两次调用未被折叠，再核对相同payload的任务仍属于两个独立session。
这将双Filter部分限定为重复调用的执行身份与生命周期验证；不同自然语言条件的质量不是该复测结论。
复测使用新目录、新账本；首轮4次与复测请求分别报告，不能相加称全部通过。

### 关闭幂等性修复后的最终验证

第二轮24次工程用例通过后，最终代码复核发现runtime重复close会再次增加结束流数。使用实际
C关闭函数的受控调用确认重复计数，补上已关闭状态检查，并修正同步处理器的完成返回类型标注。
不改模型、语义和24次用例；修复后再做同一组24次真实请求，独立第三个账本。第二轮通过记录
仍保留，最终代码身份以第三轮为准。
