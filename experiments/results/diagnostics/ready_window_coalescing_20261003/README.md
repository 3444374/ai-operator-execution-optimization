# 就绪窗口聚合的本地原型

**减少准备窗口没有自动改善完成时间，本次不启用候选。** 在固定模拟成本的突发输入中，
窗口数从29–31降至22–23，但完整替身完成时间三次中位数慢4.55%。稀疏输入没有减少窗口，
平均每行响应增加约0.90毫秒。原型仅以[可恢复源码补丁](source/candidate.patch)保存，未并入运行代码；main保持即时提交。
这不是Daft、Ray、PostgreSQL或GPU的性能测量，真实模型排名不更新。

来源为main `7cbc888c8bb8adbcc33f47baf67fe4da225413be`及测量时尚未提交的候选。
按[查询调优计划](../../../plans/查询调优.md#就绪窗口聚合的本地尝试2026-10-03)，服务器关闭后只使用本地受控对象；
HTTP、PG、GPU及模型请求均为0，未连接服务器、安装依赖或下载数据。
文献依据与反证条件见[优化方法依据](../../../../docs/research/优化方法依据.md#就绪准备窗口的有时限聚合2026-10-03)。

## 改动及最小复现

本地候选对[Ray Map传输](../../../../code/src/execution_provider/adapters/ray_map_transport.py)增加显式`RayMapConfig.ready_wait_ms`：
仅在同Job还有等待交付的已发出调用、当前就绪行不足一批时，给予一个固定等待期限。
达到行数或字节条件、遇到其他Job或取消、该Job没有仍在等待交付的已发出调用时及时继续。
首批立即推进；新到达或唤醒不延长本次期限。期限由事件循环处理，事件循环被其他工作占用时可能较晚恢复。
等待中的行继续占用原请求容量，没有增加准备线程、对象额度或额外数据缓存。
每行仍为完整独立请求，结果逐行返回；已发出且结果未确认的调用继续持有对象计费。
客户端在途状态不能说明GPU是否繁忙，因此不能将这个条件当作服务利用率控制。

[同一复现脚本](raw/repro.py)通过真实`execute/_flush`，只替换数据批构建和厂商调用：
第一行调用未返回，首窗准备已结束时，第2行先到，随后3行到达。
main三次均得到`[1,1,3]`，候选显式1毫秒三次均得到`[1,4]`；5行结果返回且资源归还。
[main记录](raw/main-replay.txt)的断言失败是预先定义的准备次数反例，不是查询或模型故障；
[候选记录](raw/candidate-replay.txt)通过。两次执行使用同一脚本摘要，源码摘要与UTC时刻见[检查元数据](raw/checks-metadata.json)。

## 设置与全部重复

运行标识为`ready-window-local-probe-20261003`，macOS15.6.1 arm64、Python3.12.6。
完整运行的UTC开始/结束、运行顺序、源码及探针摘要见[原始记录](raw/probe-results.json)。
本机缺少Daft、Arrow和Ray；使用现有`FakeRay`及受控`PreparedTable`，虽然配置字段保留`payload_backend=daft`，
实际没有调用Daft。模拟每个准备窗口在唯一准备线程等待0.5毫秒，每个外部调用等待10毫秒加
`(sequence % 7) × 0.3`毫秒；这些参数不是服务器成本估计。

两臂容量64、批次16行、窗口4096字节、对象8192字节，只有等待参数为0或1毫秒。
突发输入256行：每8行间隔0.25毫秒，组内逐次让出事件循环；稀疏输入128行：每行间隔4毫秒。
供给和模拟调用共用本地事件循环；容量满时等待完成再供给，不预存超过64个活动请求。
每个对照一次预热和三次交错测量，共16次、3,072次模拟外部调用，全部通过；
单次30秒、整体5分钟及首次错误停止要求均满足。计时从供给循环开始至最后响应，
不含传输构造、最后关闭和事后核对；包含受控输入等待，不能称完整SQL时间。

突发三对均更慢：`100 × (0.05890620802529156 / 0.05634245800320059 − 1) = 4.550299%`。
首行中位数12.370→12.034毫秒，平均每行响应的三次中位数12.519→12.694毫秒，
两臂模拟调用峰值均64；首行没有等组批不等于后续行没有成本。
稀疏完整时间少0.978%，但输入供给和计时器共用事件循环，所有窗口仍各1行，
平均每行响应12.742→13.639毫秒，调用峰值均3。这个小的总时间差不能解释为准备节省或稳定改善。
全部单次首行、平均/最长行响应、窗口大小、对象批次数、模拟调用峰值与等待原因在原始记录中。
未做CPU隔离；没有真实服务队列、推理、质量、真实Arrow内存或PG输入与交付测量。

## 后续判断

本次只证明能减少某些到达序列的准备次数，并给出等待成本抵消节省的反例；不选择1毫秒为推荐配置。
下一步优先取得实际库的每窗固定成本、现有Arrow方式以及供给时序，先做无模型同容量对照。
完整完成时间与行响应都值得保留后，再另列PG生命周期与真实模型清单；本报告不授予新增请求额度。
准备重用、数据选择与服务供给的其他候选继续按[方法依据](../../../../docs/research/优化方法依据.md#serving-cooperation-candidates)评估，
不能把动态分批这一已有机制本身当作新增研究结论。
