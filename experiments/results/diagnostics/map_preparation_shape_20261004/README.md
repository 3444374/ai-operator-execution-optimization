# 真实分批成本与单／双Job供给形态

按[服务器准备清单](../../../plans/查询调优.md#server-preparation-shape)完成3,632行固定窗口准备、
20个Core case、2,080次本机HTTP和24项检查。模型、GPU执行及PostgreSQL查询为0；生产源码和默认未改。
这是SemLoom内部工程诊断，报告与紧凑证据按下方保存入口定位，不更新原生Daft／Ray Data或数据库真实模型排名。

**观察信号：** Daft的小窗口重复执行有明显固定成本，但它与其余阶段重叠。
双Job下约99%的对象只有一行；Arrow大幅减少准备调用时间，完整消费收益仍小，包含准备后的结果也不一致。
暂不启用等待、成组远程过程调用（RPC）或新默认。
下方[就绪队列补充](#ready-queue-snapshots)已完成选取前观察，未支持优先实现同Job零等待重排；下一项核对准备与Core在途名额的联动。

## 问题、来源与实际设置

对照为同一真实Linux UDS、查询登记、共享Core、Ray HTTP actor、Daft／Arrow；
输入由有限外部producer生成，使用v6计划／任务／结果消息，不是PostgreSQL SQL执行。
任务选择与提交由SemLoom Core拥有，Ray Core运行actor与远程调用，Daft Native只执行已选有限窗口中的图。
单Job包含128行，双Job各64行；完整HTTP正文集合相同，双Job只按逻辑序号分成两半。
各生产者连续offer后消费，使用同一启动事件；第三个登记Job只接纳一条后取消，没有派发。
语义fixture为固定Echo输入及确定性结果，不提供模型质量证据。

独立Git副本来自`codex/gateway-isolation-diagnostics@d4edc80393ae0c605c1386008024cbe333d5f058`。
857份code／runtime文件与本机同一版本逐项摘要匹配；诊断脚本及修订摘要分别见两份归档的`probe-manifest.json`。
运行标识为`map-preparation-20261004a`（组件完成、Core启动失败）与`map-preparation-20261004b`（修订后Core完成）。
服务器现存仓库未改。环境和源码原始报告在首份归档，第二份`prerequisites.json`按摘要引用原记录。

实际环境为Python3.12.3、Ray2.56.1、Daft0.7.21、Arrow24.0.0、HTTPX0.28.1；
Ray upstream commit为`06729817574615e25afe8f20902b37660c2e6962`。
128个CPU、容器32个CPU配额；Ray登记4CPU／0GPU、128MiB对象存储、一个HTTP actor，Daft／BLAS各4线程，未做物理CPU隔离。
固定全局活动4、每Job留存128行、总留存384行、输入12MiB、输出预留384MiB、最多8连接；
批次4行、窗口2MiB、表引用4MiB。逐条SQLite发送前计数和内存事件记录在四项中相同。
本机HTTP每行人为等待10–12毫秒，HTTP协议与worker初始化也在执行时间中，不能称纯模型耗时。

四项各8行检查、128行一次预热与三次交错测量，`4×(8+4×128)=2,080`次HTTP；
每case60秒、整体10分钟，首次错误即停。成功Core监督进程耗时101.709秒，套件自身99.272秒，共享Ray启动9.486秒单列。
每case新建gateway、actor和payload线程池，集群与Python模块在套件中共享；不能与先前共享gateway／worker的模型JCT直接比较。

## 固定输入窗口：实际库的重复成本

每项128行，按1／2／4行切成有限窗口，实际运行`iter_payload_batches`，完整核对行键与payload字节。
两种backend各8行检查、128行预热与三次测量，另有四个128行cProfile函数调用分析case；总准备3,632行。
组件8.429秒，没有HTTP、Ray调用或PG；函数分析case不进入以下未插桩时间。

|---|---|---:|---:|
| Daft／1 | 444.564 / 501.028 / 490.082 | 490.082 | 128 |
| Arrow／1 | 12.859 / 13.601 / 15.216 | 13.601 | 128 |
| Daft／2 | 252.418 / 241.569 / 230.572 | 241.569 | 64 |

Daft每窗口约3.56–3.83毫秒；减少窗口数减少实际准备成本。该回放保持输入和窗口划分，
并未证明Core能在零等待条件下取得相同窗口，也不把组件时间差扣除为查询收益。

源码每个Daft窗口调用`from_arrow → into_batches → to_arrow_iter`。
cProfile的单行128窗口样本中，`from_arrow`128次、累计80.901毫秒，`to_arrow_iter`累计667.901毫秒，
其内部`NativeRunner.run_iter_tables`累计634.339毫秒；缓存后的`configure_daft_runner`累计0.116毫秒。
四行样本只创建32个图。累计值包含子调用与等待，生成器调用数包含恢复，不能相加或称独占CPU时间；
实际官方Python入口及文件摘要见第二份归档的`runtime-source.json`，未继续细分Rust内部执行。

组件显式import调用为Arrow94.905、Daft130.013毫秒，不能当整机冷加载。
Core的Ray import阶段只有约0.008毫秒，因为外层已初始化Ray。
首次Daft检查的`first_payload`为2961.107毫秒，保留在原始case中；它包含初次准备、排队和恢复，尚未细分到各个库。

本签名先不实现重排；保留逐行容量、完整请求、结果交付、取消和未知执行责任。
逐行RPC暂未获得改成成组RPC的净收益依据。

## 资源、失败与适用范围

2,080个HTTP开始／结束、计费、Core提交／终态／释放和wire结果逐行匹配；
全部请求正文与固定窗口输入摘要一致，SQLite投影核对预付、1至N编号、完整摘要与单元关闭。
每case另一个Job仅接纳后取消，Core和transport最终记账为0，未确认集合为空。
实际HTTP最大活动4，Arrow对象记账总峰值1,224字节；组件单表峰值808字节。
这些是逻辑／缓冲记账，未采集全进程驻留内存或物理对象存储峰值。所有观察占用符合声明额度。
本轮服务退出，两张GPU检查时均0%／1MiB；PG snapshot、权限、运行中模型取消、多节点和多模态仍pending。

首轮组件完成后，新增Core启动脚本误把Ray `gcs_address`属性作为函数，0个Core case、0次HTTP。
保留失败源码／日志；只读核对实际API和服务退出后，用户授权新的10分钟、剩余2,080次HTTP。
修订只移除这一次误调用，组件没有重放。此前本机SSH helper路径包装错误及准备阶段SSH超时没有模型调用，
原始过程保存在Git外；已存在的环境报告和源码摘要随后核对，没有将准备失败写入性能聚合。
