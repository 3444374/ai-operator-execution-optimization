# 单行补充输入的待准备尾块追加

2026-10-08。原三次真实测量的3,072行借用记录已离线核对：每次初始128行之后，896次借用均只有一行已接纳、尚未准备。
新增可关闭的待准备尾块追加选项，本地24,672次模拟调用及服务器最终147项检查通过。
随后16项PG检查、26次本机模拟HTTP及10条查询/8,224次真实模型请求通过；完整查询中位数10.069→12.686秒，追加慢25.987%。
低准备成本的本地反例与真实负结果均保留，暂不推荐启用，原即时默认与追加选项的False默认保持。

研究对象是 PostgreSQL 内置 AI 语义算子的外部分布式物理执行与调度优化。
实施与已授权的服务器清单见[查询调优计划](../../../plans/查询调优.md#queued-preparation-coalescing)。

## 原记录与诊断选择

[原验证报告](../../postgresql/text_map_preparation_validation_20261004/README.md)记录每1024行928个准备块，其中896个为单行。
本次按原公开清单恢复三份事件内容并核对字节数/SHA-256，累计接受与借用各3,072行，无重复；
用已接受集合减去已借用集合，得到每次借用瞬间可用的行数。[复算脚本](raw/analyze_borrow_population.py)与[输出](raw/borrow-population.json)保留完整分布。
后三段各896次的候选数全部为1，说明动作份额修订不能单独解决这些块。

较早的本地动作分配反例在两个Core入口均失败：16行已经接纳，4条终态集中返回后，下一次借用4行缩为2行。
该现象保留，但没有据它修改Core；它与原运行后段只有一行可借用的事实不同。
随后用一个正在准备的块加两条逐行到达输入复现真正的队列机会：原路径生成三个单行对象，候选生成1行和2行两个对象。
最小复现先失败，修订后通过；首次fixture的batch容量装配错误也保留，不把它当作机制失败。

## 可选实现与行为

[`RayMapConfig.coalesce_queued_preparation`](../../../../code/src/execution_provider/adapters/ray_map_transport.py)默认`False`，开启仍要求已有准备配置。
[`MapInputPreparation`](../../../../code/src/execution_provider/adapters/map_preparation.py)只追加到同session、同Job、同工作量签名且未取准备lease的队尾。
开始准备、已经就绪、存在取消成员或版本/会话不同的块不扩展；稀疏输入立即开始，不设置凑批计时器。
尾块容不下而新块容得下一行时，另建有限块；原每行完整请求、模型名额和Core动作额度保持。

[`BoundedStageBroker.extend_encoded`](../../../../code/src/scheduling/runtime/stage_broker.py)原子更新编码字节与新增行登记，
保持旧行前段、FIFO位置、创建时间、处理器/模型版本及工作量单位；已有准备lease的描述不可再变。
追加后仍须符合行数、字节和预计工作量上限，取消、失败和未知结果继续持有相应输入及共享对象。
这是处理已复现供给形态的工程候选，不单独主张研究新颖性。

## 返回等待的离线与本地隔离

用户授权继续后，本项只复算已有六次1024行测量，并运行71个本地fixture、4,107次模拟调用。
HTTP、PG、真实模型及GPU调用均0，生产执行源码与默认保持；新增代码均为诊断或分析。
[离线脚本](raw/analyze_return_wait.py)、[有限运行入口](raw/run_return_wait_isolation.py)和[当前分析](raw/return-wait-analysis.json)定位同一组数字。

旧同步guard的结束测量时刻没有单独字段，但位于内部guard观察时刻与外层guard观察时刻之间。
