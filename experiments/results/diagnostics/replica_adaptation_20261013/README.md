# 单查询副本供给与路由的软件验证

本报告仅是实际Core、HTTP客户端和localhost服务的**软件fixture**，GPU／模型／PG／原生LOTUS SDK均未运行。
源码共同基点`28093954`，四个被测模块的精确SHA-256见[完整观测](raw/probe.json.gz)的`source_sha256`；
全部比较使用同一代码、请求字节、到达、Core记账及完整响应适配器。[计划](../../../plans/查询调优.md#replica-adaptation)先于探测落盘。

## 已有与新增

旧`3bd53587` Q2有120次出现、119个不同完整值摘要，manifest固定副本分配60/60。
这是Core外共同router的决定；Core只见逻辑`model`，前后metrics不反馈。原模型单／双卡结果不用于本次收益计算。
本基点已有真实副本组装、声明硬容量、round-robin跳满与Core权威终态，快副本能够自然补位；没有重新实现这项能力。
新增为显式`adaptive`：估计完成work／transport忙时给已有least-work提供同单位速率，队列/KV压力逐样本一槽改变供给，
可选软work排空目标；旧默认保持。缺少完整压力时回到声明静态供给；缺速率时使用中性在途work并探测未测空副本。

实际接线：完整原请求 → NativeTaskSession/Job → Core全局C/W和存储 → admission →
带本owner逐副本在途C/W的TopologySnapshot → 目标副本router → ReplicaTransport → 对应HTTP服务 →
原完整响应 → Core权威终态／结果lease → 消费者释放。成功响应的软速率反馈不归还Core容量；
取消、失败及未知调用仍保留既有责任，压力采样复用已有缓存／非阻塞provider，不叠加service running与owner在途。
声明设备重叠的自适应配置拒绝；空设备声明的fixture不建立GPU事实。多个外部owner共同硬容量仍pending。
共享准备仍显式拒绝；HTTP完成不是准备结果的设备读取终止证明。

## 配对设置与结果

每服务2个人工执行槽，硬允许4个owner HTTP；work是人工时延单位。双副本异构单work为8/32ms、同速12/12ms，单副本12ms。
独立24行校准K2/4/8（单副本1/2/4），按最小完整JCT选K，原值在完整观测；这是有限选点，不声称实际服务饱和校准。
评价每query48行、3次交错重复，work序列[1,1,3,1,2,1]重复8次；突发分3次16行、间隔150ms。
误差场景在偶数行估4、奇数行估1，真实work保持；供给排空目标150ms先定，不按结果重调。
总60评价＋9校准query，3,096 POST，28.286秒，全部完整请求／结果关联／恰好一次消费／容量／清理核对通过。

四臂：独立选K的既有轮转；同K与校准固定速率least-work；同K在线速率路由；在线路由再加供给反馈。
固定速率臂与在线臂采用相同策略装配和反馈成本；供给臂没有改变全局硬K/W、请求内容或模型工作集合。

轮转逻辑在途与HTTP峰值不是GPU活动数。供给的排队等待下降若伴随JCT变慢，按负结果保留。
