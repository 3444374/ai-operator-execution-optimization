# Core／Map观察成本的本地隔离

本地控制支持一个具体判断：**实验记账会改变已接纳任务的提交节奏，单项耗时不能直接从完整执行时间扣除。**
启用同一缓冲日志时，逐条SQLite记账与内存控制的完整fixture中位数为0.871675／0.690775秒；
内存臂少20.753%，准备窗口却从43增至88。内存计数只作无模型诊断，生产默认和真实请求计费保持。
这不是服务器、SQL、原生Daft/Ray或GPU性能结果，也不支持直接启用成组RPC。

## 问题、源码与执行身份

按[查询调优清单](../../../plans/查询调优.md#next-submission-work)，隔离
[已有真实记录](../../postgresql/text_map_arrow_real_20261003/README.md#submission-followup)中的观察开销与提交前等待。
依据仍是[提交与完成粒度条件](../../../../docs/research/优化方法依据.md#submission-granularity-condition)。
本轮是SemLoom内部控制，不是原生baseline，也不比较模型质量。

- 参考生产源码为main `2b1ea713af2bd1f303ae362ce19a95ba57517e44`，Core、传输和生产默认未改。
  运行现有`build_fixed_model_execution`、注册Job的`SessionEngine`、`BoundedAsyncBackend`与`RayMapTransport`。
  真实组织、接纳、逐条调用、结果验证、引用释放和Core轮询均运行。
- `SyntheticTable`代替有限Arrow表，`SyntheticRay`代替厂商API；put只返回本机引用，worker使用独立事件循环线程与固定结果。
  不运行Ray、Daft、Arrow、HTTP、PostgreSQL或模型，诊断期间网络connect直接拒绝。
- 本机Python3.12.6、Darwin arm64、SQLite3.45.3，缺少三个厂商库，不安装依赖。
  RSS、真实对象存储、GPU利用率、模型质量与训练时间均为unavailable，原因是本轮不测这些对象。
- 主分析为`run-03`，计时脚本SHA-256为`a880ecef8454dd59c24790ff7c6ea36532058150b417450e7c6e298d913e920f`。
  完整脚本与依赖摘要保留在归档；发布版本随后只修正失败排空后的最终计数，分析函数与计时版本核对一致。

## 有限清单与计时口径

四臂为逐条持久／内存计数，各自配以内存事件／实际`BufferedEvents`精简投影写入。
两臂都先持久预留整个单元并独占claim，再使用同一请求摘要、内容核对、发送前计数与结果处理。
持久臂调用现有`SharedClaimedUnit.reserve`，内存臂调用现有`ClaimedUnit.reserve`；没有新增真实请求模式。

固定单Job、最多持有256行、活动64条、准备批次16行、64KiB输入窗口、128KiB表引用额度。
Core保留原组合器的输入／结果字节额度，每项256MiB；这些是记账上限，不是实际分配或进程峰值。
有限输入与确定结果均带序号，完整内容和关联逐行验证；消费端复制后释放lease，并按序号恢复输出。
模拟worker并发完成，不等待整组结果。

每批准备sleep0.5毫秒、put每次sleep0.2毫秒，worker每行sleep20–26毫秒，均是人为设置；
实际线程调度可能增加时长，不是服务器校准。每次60秒、整体5分钟，执行／计数／身份／资源错误即停。
每臂16行检查、1024行一次预热与三次循环交错测量，合计20次执行、16,448次模拟调用；HTTP／模型／PG均为0。
预热和小检查不进入中位数。主清单13.690秒完成，全部调用、持久摘要与退出核对通过。

`query_seconds`从首次offer到全部结果释放且Core完成，包含计数和在线日志工作。
`startup_seconds`覆盖执行器构建与打开Job，建账本、输入准备和替身线程创建在它之前。
`teardown_seconds`还包含事后分析、摘要核对与执行器／writer退出，`case_seconds`包含这些退出成本。
该计时不是完整数据库查询；不能把观察成本移出计时后称为执行算法改善。
`first_result_seconds`是首次Core交付，不是客户端或SQL首行。

逻辑活动均值为同一`query_seconds`区间内活动计数的面积除以时长；模拟worker均值为该区间内各方法持续时间之和除以时长。
两者分母相同，均不代表GPU利用率。窗口是自然选出的有限行，一个窗口可拆成多个表批次。
表字节数使用替身明确的计费公式，不是真实Arrow/Ray内存。
Core `submitted`在backend返回后记录；主清单没有观察到它晚于RPC的行，仍不能把它当作精确的接纳瞬间。

## 判断与下一步

**源码与受控观察：** 名额在backend接纳后就被Core计费，后续准备和实验guard仍在这段占用内。
持久臂逻辑活动接近60，而模拟worker约28–30；内存臂worker约37–38。
观察层会改变“已接纳”到“正在执行”的比例，逻辑活动接近64不能当作服务已被充分供给。

**受控观察与推断：** 减少guard阻塞后，完成通知和补充输入更快交错，窗口与表批次增加。
这说明观察设施与准备确有耦合，与先前线程／批量记账的反例相容；
不能把本机0.35秒reserve换成服务器约5秒，或据此预测完整SQL能省多少。输入、模型、service时长和真实进程／网络均可能改变结果。

**尚待验证：** 替身调用只调度本机future，不能据其约7–15毫秒累计成本决定改真实Ray RPC。
本轮不实现或采用成组RPC，不恢复等待聚合，不改变名额释放或真实发送前持久计费。
下一步先为正式对照设计统一、有限且不改变供给节奏的观察方式，核对独占所有者、退出、未知请求和baseline可比性；
再在实际固定Ray版本上判断逐条提交是否值得改。多模态仍沿[单Job切片](../../../plans/数据组织.md#scene-preparation-pilot)推进，本轮没有实现共享准备。

这些时间不进入结论。仅修订诊断驱动：有交付才release，有空间才offer，等待通知或轮询期限。
