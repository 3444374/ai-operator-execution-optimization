# 单Job文本Map的准备与提交分段

研究对象是 PostgreSQL 内置 AI 语义算子的外部分布式物理执行与调度优化。
按[准备分段计划](../../../plans/查询调优.md#map-input-preparation)完成可选接法，原即时执行路径继续作为默认。
本报告拥有本地行为、替身对照、服务器实际库检查与失败；PG接入、真实模型、物理内存及多Job收益pending。

## 实现与资源归属

[`TaskPreparation`](../../../../code/src/scheduling/core/session_contract.py)只借用Core已接纳的有限前段，不发送模型请求。
[`SessionEngine`](../../../../code/src/scheduling/core/session.py)在原动作额度内推进准备，只有就绪成员才参加原组织/模型请求与work检查。
输入记录在准备线程、共享数据或未知模型结果仍持有时继续记账；关闭consumer后，Core reap可以继续确认本地归还。
准备失败走原后端错误交付，模型结果确认和本地归还短暂错开时延后交付，保留输入，不错误判定为查询失败。

[`MapInputPreparation`](../../../../code/src/execution_provider/adapters/map_preparation.py)复用[`BoundedStageBroker`](../../../../code/src/scheduling/runtime/stage_broker.py)，
按已到达前段与相同Job/工作量签名组织有限准备块。最多一个准备线程，先预留编码数据与两份Arrow/Ray表示的复制空间；
完成后持有一个Ray对象，各行仍独立发送完整请求和返回结果，不等未来行，不合并模型请求。
同块快行结束不会释放慢行或未提交行仍需的对象；未知Ray结果保留对象和work，取消不能冒充远端结束。
`RayMapConfig.preparation=None`保持旧接法，显式配置才启用；当前组装仅支持一个Job。

`ready_work`计入整个持有块的预计工作量，`model_inflight`是从首个成员提交至全部成员确认的共享块数量，
包含尚未提交的同块成员，不等于HTTP/GPU活动数。实际请求/work仍由Core原上限控制。
字节计数针对已声明表示及引用，Rust/Python/Ray进程RSS和模型显存未测，不能称完整物理内存上限。
控制臂的Core在途包括准备，候选在准备完成后才取得该名额，在途面积不能直接解释为服务利用率。

## 合并审查的本地取消回归

针对已推送的`e9de01c7`，审查发现准备归还的重试先消耗每轮动作额度，会持续拖住尚未发送请求的取消通知。
纯fixture中留存12行、每轮8个动作，取消后的连续5轮都只有准备重试，没有backend取消通知。
同一Job的多个flow（任务流）也可能由前方不可归还的输入持续遮住后方已可归还输入。

修订将远端结果轮询和本地归还分开：先推进所有终止flow的取消通知，再用共用游标轮转本地输入。
原动作额度不增加；未知远端结果、尚在准备的输入和已交给consumer的结果仍保留原所有权。
旧式单session采用相同顺序，默认无准备接口时保持原清理路径。

新增5个行为方法覆盖动作额度1/8、两种推进方式、同Job多flow、关闭consumer后归还，以及异步发送前等待时取消。
同一批新用例在原Core源码上产生11个子用例失败；修订后的230项本地回归中219项通过、11项跳过。
异步等待用例确认下一行准备仍持有输入时，取消能抑制尚未发出的actor方法，并最终归还全部输入。
本轮HTTP、模型和PG查询均为0，没有新增服务器运行。缺库与平台跳过按原日志解释，不称全部实际库通过。
