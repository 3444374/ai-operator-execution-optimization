# 文本 Map 四路径服务器验证与有限模型比较

2026-09-30。研究对象为 PostgreSQL 内置 AI 语义算子的外部分布式物理执行与调度优化。
本轮延续 `codex/text-map-matched-comparison`，没有切换分支、提交、推送或合并。
执行依据为[四路径计划](../../../plans/completed/text_map_matched_comparison.md)；此前的
[本地准备记录](../text_map_comparison_preparation_20260928/README.md)保留当时的82项检查。

## 环境、输入与执行身份

使用用户指定的单 RTX4090 服务器，PostgreSQL 18.3、Ray 2.56.1、Daft 0.7.21、vLLM 0.25.1。
driver 与模型服务使用不同的既有虚拟环境，当前 Map 所需能力检查通过；未据此声称全部可选能力齐备。
为本轮构建独立 PG18.3 extension 安装目录，数据库、模型缓存、Ray 临时文件和日志均在数据盘。
真实运行前核对了756份执行源码摘要；当时源码尚未提交，身份见[源码清单](raw/source-final.json)。
机器检查与构建记录在[受控材料](raw/controlled-index.json)中，连接地址、密码和真实 runtime env 不入库。

模型为 Qwen2.5-7B-Instruct，revision `a09a35458c702b33eeacc393d103063234e8bc28`，
九份模型/配置文件与既有 revision 摘要相同。GPU0、BF16、单副本、4096上下文、128服务序列、
8192批次token、0.8显存比例、FCFS、分块输入处理、关闭前缀缓存；实际启动参数另存原始材料。
各路径请求采用相同消息、temperature=0、top_p=1、n=1、最多128输出token及相同标签解析。

输入为 Movie-derived Map，每条原始评论生成情感标签，保留派生任务身份。
重建512行开发输入；先用其中16行检查正确性，再从历史数据以外选1024行评价。
新评价与全部历史排除输入的电影、评论ID、文本摘要交集均为0，见
[输入与重叠记录](raw/controlled/assets/comparison-inputs.json)。
最初 pandas3.0.5 产物与旧PG字节摘要不同，另用既有隔离环境的 pandas2.3.3 重建，
2000行原始数据摘要与历史相同；两份材料都保留。
新评价另排除旧2000、512、1024行输入，并未把旧评价数据改名使用。

| 路径 | 执行拥有者 | 角色 |
|---|---|---|
| PG＋SemLoom HTTP | PostgreSQL / SemLoom | 内部静态参照 |
| PG＋SemLoom Daft/Ray | PostgreSQL / SemLoom；Ray Core worker执行HTTP | 内部候选 |
| PG-source direct | 有界客户端 | 诊断参照 |
| Ray Data SQL→HTTP | 原生 SQL reader、HTTP Processor 与 Ray 调度 | 外部系统 baseline |

PG、模型与Ray服务在查询前启动；每次查询新建专属gateway、客户端或执行图。
主要时间为调用准备开始至完整结果消费，评价与清理另计；不与旧常驻gateway数字合并。
本轮有限集合选点不证明吞吐平台、质量等价或通用性能优势。

### 时间与资源缺项

四路径准备时间中位数依次约0.503、5.247、0.193、2.578秒；准备之后至EOF依次约15.410、11.242、7.564、50.175秒。
分段中位数不能相加当成总时间中位数。PG Daft/Ray的准备成本抵消了部分后续时间改善，
但这不是对单个内部函数的因果归因。
PG HTTP/direct的HTTP峰值分别为16/64，原生Ray为2；PG Daft/Ray跨worker的HTTP时间线因未完成时钟核对而不可用。
服务时间序列共有实际采样值，采样错误0；模型与整个campaign worker后代另有RSS记录。
RSS相加会重复计算共享页，且不能覆盖所有PG/系统进程，故不报告整个系统的唯一物理内存或内存效率排名。
读取、组织、序列化、准入、模型、汇合各段尚无统一的逐查询完整分解；不以总时间差填补这些缺项。
本轮不做结果持久写表，没有writeback指标；能耗和MFU不作结论。

## 原生Ray供给诊断与唯一优先后续项

来源为本轮原始轨迹和固定版本源码检查，见[源码摘录与摘要](raw/native-ray-source-audit.json)。
Ray2.56.1的`HttpRequestUDF`先保存`session.post`返回的待等待对象，再逐个`await`读取响应。
标准aiohttp与本项目观测session均在等待时开始请求；每批32行本身不产生32路同时HTTP请求。
本轮还把每actor异步批次设为1，只有两个SQL读取块；
[原生统计](raw/real/worker/evaluation/ray-data-c128-r1/unit/ray-stats.txt)显示HTTP阶段实际2个任务，
持续约40.05秒，事件报告峰值2。不能把该结果解释为Ray模型服务能力的上限。

因此下一步优先**修正原生Ray供给参数及验证实际并发**，之后才据完整外部对照选择SemLoom优化问题。
当前入口新增`ray_async_batches_per_actor`，由Ray本身组织异步批次；以actor数×异步批次数核对HTTP允许上限，
每查询通过Ray的环境配置把该值送到worker，默认1保留旧行为。批行数作为单独参数保存。
没有向baseline注入SemLoom执行或调度策略。
修订后本地91项相关检查通过；服务器run06的5项实际PG/Ray集成通过，共235次合成POST
（208正常、14错误、8延时、5挂起），真实模型0次。新用例每actor异步批次4、批行数1，
实际HTTP峰值4、恰好8次请求；默认1的旧路径、错误及超时恢复均通过，PG/Ray与GPU清理核对通过。
见[本地日志](raw/followup/local-tests.txt)、[服务器日志](raw/followup/controller.txt)、
[逐单元记录](raw/followup/units.json)、[清理](raw/followup/cleanup.json)。
修订后的756份执行源码与服务器一致，摘要见[后续源码](raw/followup/source-after-followup.json)。
真实41,024次结果的源码清单与服务器源文件快照保持原样，不使用新代码重解释旧运行。
后续真实清单须重新声明原生候选、读取块、实际供给、服务签名和模型预算；本次剩余额度为0。
