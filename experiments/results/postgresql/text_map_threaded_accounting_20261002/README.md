# 同步与线程记账的无模型对照

2026-10-02。按[调优计划](../../../plans/查询调优.md#热路径独立计时与无模型验证)，
将持久记账移出gateway事件循环，检验恢复等待能否减少完整查询时间。
研究对象是 PostgreSQL 内置 AI 语义算子的外部分布式物理执行与调度优化。
**本轮结果为负：线程选择中位数11.570秒，同步8.287秒，慢39.606%；默认同步保留。**
本轮是同实现观察成本诊断，真实模型请求0，不更新原生baseline排名或真实性能结论。

## 实现与验证

源码`2f49660cf20f1c6fe30ca296d876cb438ea599e0`，821份源码摘要与干净受控文件状态核对通过。
可选`remote_budget_mode=threaded`使用一个I/O线程串行执行原`ledger.reserve`；请求内容核对与记录
仍在原事件循环。Ray发送前回调支持等待异步完成，在等待后再次检查取消；事务未完成不发RPC。
取消等待已排队事务完成，已提交额度不退款；额度耗尽或记录失败不发请求，未知远端执行继续保留计费。
线程在事件writer关闭前排空；生产默认没有回调时不创建记账线程。原SQLite事务、请求正文与容量不修改。

最小异步回调检查在修改前复现3个失败断言，修改后通过。本地相关70项中63项通过、7项因缺Daft/Arrow跳过；
目标环境70项全部通过，包含真实SQLite提交、额度耗尽、取消等待提交、不退款、失败观察、旧HTTP/同步和
旧结果读取。原PG库摘要为`38370204a7d487f24b7a10d2f452f9ea1502b0e8be7dc6587789c0d9ca83186d`，未重建。

## 条件、清单与失败保留

PG18.3、Ray2.56.1、Daft0.7.21、Arrow24.0.0、psycopg3.3.4、httpx0.28.1，现成driver未修改。
两臂各一个服务拥有的worker与共享gateway；共享Ray8个逻辑CPU、256MiB对象存储、0GPU，初始可用6。
C64、PG窗口256、批次最多16行、2MiB输入窗口、4MiB对象额度；Daft8线程，统一设置
`DO_NOT_TRACK=true`和`RAY_USAGE_STATS_ENABLED=0`，没有物理CPU隔离。
唯一显式变量为记账执行位置，进入resolved config和observer摘要。输入是相同合成中英文文本，
本地HTTP确定性返回POSITIVE/NEGATIVE，token字段是fixture值，不作推理工作量。

计划为两臂各16行检查，1024行各一次预热与三次交错测量，共10条查询、8,224次fixture上限，
整体15分钟、单查询120秒并预留清理。第二份16行摘要因控制器使用重复文件名而停止：
两条查询已通过，HTTP实际32次，资源与ACL归还，失败和账本原始快照保留。
修正文件名后只继续剩余8,192次，复用同一个持久账本与原截止时间，不重放32次或重置额度。
继续部分耗时109.848秒并完成全部8条查询。16行检查与计时分属两次fixture服务生命周期，分别登记；
全部计时重复来自继续部分同一服务，不混入前面检查值。PG、Ray、HTTP、worker、端口和父目录ACL独立核对通过。

## 时间为何增加

| 每1024行，重复1 / 2 / 3 | 同步 | 线程 |
|---|---:|---:|
| Ray对象批次数 | 78 / 74 / 73 | 463 / 480 / 498 |
| 平均每批行数 | 13.128 / 13.838 / 14.027 | 2.212 / 2.133 / 2.056 |
| 有限输入窗口数，即迭代器close次数 | 21 / 21 / 21 | 460 / 477 / 495 |
| 批次next函数执行累计，秒 | 1.013 / 0.898 / 1.011 | 6.988 / 7.162 / 7.063 |
| 批次next结束至事件循环恢复累计，秒 | 5.893 / 5.955 / 6.356 | 0.528 / 0.499 / 0.542 |
| Ray put函数执行累计，秒 | 0.551 / 0.579 / 0.672 | 1.393 / 1.395 / 1.549 |
| reserve函数进入至退出累计，秒 | 5.384 / 5.343 / 5.689 | 10.757 / 10.908 / 11.108 |
| worker退出至driver回复均值，毫秒 | 41.938 / 42.107 / 42.349 | 2.685 / 2.477 / 2.464 |

**事实**：等待事件循环恢复大幅减少，但传输批次及有限输入窗口变得很小，Daft迭代与对象put的执行累计明显增加。
源码`RayMapTransport._flush`立即选取当前pending行，每个选定窗口调用一次`iter_payload_batches`；
后者为每个窗口创建Arrow表与Daft执行图。异步记账改变任务完成与补充时序，当前实现没有等待合并小窗口。
这一源码行为与460–495个小窗口的实测相符；不是actor数量或批次上限发生了变化。

reserve进入至退出的时长包含线程调度与Python/SQLite/I/O，不是纯磁盘时间。
线程选择的账本排队均值610–630毫秒、恢复均值0.675–0.775毫秒；这些逐行等待大量重叠，不能相加成查询成本。
多线程竞争、事务内部SQL与持久提交的各自占比尚未采集，不直接归因Python GIL或磁盘。
因此“移走5.2秒阻塞就能获得5.2秒收益”的推断没有成立，数据组织与提交时序必须一起考察。

## 结论与后续

本配置保留同步默认，线程选择仅作为显式诊断对照。下一项优先检查小窗口反复创建，比较有界合并或
已选payload的轻量分批方式，并保持行身份、完整请求、取消和容量。当前没有实现这些后续选择，
也没有新增真实模型授权；真实性能、质量、服务饱和与通用收益仍待相应验证。
