## 完成情况与可声明范围

12条SQL查询全部完成，**持久预扣4144次、服务访问4144次、vLLM成功计数增加4144次**。
输入/请求/结果逐行关联、SQL结果消费、PG与执行核心的资源结清检查通过；无缺行和无法解析的分类输出。
控制器从模型文件核对至清理共303.231秒，没有失败请求重试、额度重置或额外模型请求。

两臂都是同一PG语义算子及SemLoom执行核心：HTTP路径直接异步调用服务；新增路径使用Daft Native有限批次，
由Ray Core异步worker调用同一服务。它们属于项目内部工程对照，不是Daft/Ray Data原生系统baseline。
结果返回PG并成为SQL查询结果；本轮只安装输入表，没有增加模型结果持久写表、COPY或索引构建。

本次C64三轮中Daft/Ray查询均较短，但没有预声明统计优越性检验、稳态规模搜索或持续供给合格评价。
因此只报告本次观察，不宣称普遍加速、新容量基线、旧C64间歇问题已修复或多机器能力。

## 固定设置与身份

- PostgreSQL 18.3，既有诊断扩展安装；扩展二进制SHA与运行前752份源码SHA均保留。
  工作区起点`519a2a93`，源码来自`codex/incremental-multimodal-path`的待提交修改，文件摘要是运行身份。
- 单张RTX4090，Qwen2.5-7B-Instruct，revision `a09a35458c702b33eeacc393d103063234e8bc28`；
  全部模型文件按既有reference重新计算SHA。vLLM 0.25.1、BF16、张量并行1、上下文4096、
  序列上限128、批次token上限8192、前缀缓存关闭、GPU内存比例0.8，服务启动参数与实际进程核对。
- 同一Map instruction和UTF-8结果解析，temperature=0、top_p=1、max_tokens=128、n=1、非流式、无额外stop字符串。
  每个输入行对应一次独立请求，不将多行拼为一个prompt。
- 使用既有Movie tuning的512行，manifest SHA为`0ac500242d30562101e60ef49a117e83c4d8a5de9cd86ebdf2eb75e49707a922`。
  C1取前8行，C4取前16行；原始列、标签和身份由manifest校验，不使用独立评价集。
- C为客户端在途上限。PG窗口128行，输入/结果各128MiB、PG保留256MiB、暂存4MiB。
  Daft 0.7.21、Ray 2.56.1；一个异步worker，每批行数为min(16,C)，数据窗口2MiB，对象额度4MiB。
  这些额度不代表全部进程RSS或Ray对象存储的物理总内存上限。
- 全新持久账本最多4144次尝试；单查询90秒，总时限20分钟。C1/C4通过后才执行C64，
  每臂一次预热、三次测量；顺序为HTTP→Ray、Ray→HTTP、HTTP→Ray、Ray→HTTP。
  每个容量各自新建常驻gateway，C64的四次查询复用对应gateway。

## 观测、失败保留与清理

Ray对象预留早于put，最后一条已确认结果到达后归还；各查询对象计数、行完成和逻辑额度检查通过。
HTTP活跃区间可用；Ray只记录远端完成和worker本地耗时，未对齐跨进程时钟，因此其HTTP占用时间线不可用。
两路径事件内容并非完全相同，当前耗时差不能直接全归因于数据分批或对象传输。

原始记录包括PG流转、结果消费、对象预留/释放、gateway/PG/consumer RSS以及模型服务采样。
这些阶段会重叠，不能把累计时间相加解释整个查询。Ray worker及全部Ray服务RSS没有完整采集，
没有据网关RSS估算全系统内存，也没有报告缺乏统一定义的模型计算时间或GPU利用率收益。

启动真实服务前先用相同脚本进行受控预演。第一次在创建配置文件时失败，替身和真实请求均为0；
改为每个容量使用独立配置文件后，第二次12条SQL、4144次替身请求通过，耗时72.851秒。
