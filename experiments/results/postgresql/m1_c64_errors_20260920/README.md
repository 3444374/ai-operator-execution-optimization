## 已知事实与尚不能确定的原因

上次总账本在发送前记录1,552次尝试，服务端确认成功1,550次；C64中的sequence468、508进入
`core_uncertain`，最终PG查询失败。`BoundedAsyncBackend.poll`将多数底层异常统一映射为
`MODEL_UNAVAILABLE`，原事件未保存异常类型，因此不能从该错误码反推具体原因。
服务日志没有对应模型异常堆栈；两条差额也不能单独证明连接断开或服务端收到过请求。

本轮依次核对连接/HTTP客户端、请求记账和事件记录三类可能；新增诊断覆盖这些操作抛出的异常。
本轮未出现 `core_http_error` 或 `core_uncertain`，所以没有获得新的真实异常样本来区分它们。
没有调整连接复用、超时、服务容量或加入重试，也没有把受控注入的异常当作旧故障的真实类型。

C64表示**客户端最多64条在途请求**，包含等待连接、服务排队、模型执行和读取响应。
它不保证每一时刻都有64条，也不等同于模型运行中的序列数。四次C64的实际HTTP峰值均64，
查询中段的平均在途数约52.7–53.4；[完整供给值](raw/completed-queries.json.gz)保留计量定义。

## 修改与受控检查

[`AsyncFixedModelTransport.execute`](../../../../code/src/execution_provider/adapters/async_fixed_model.py)
在异常离开传输层前发出 `http_error`；实验观察器保存为 `core_http_error`。
事件包含task key、异常类型、最多四层原因类型，以及最内层代码的文件名、函数名和行号。
类型/文件/函数名称有长度上限；不记录异常消息、请求正文、响应正文或认证头。
诊断观察器自身抛出普通异常时，仍重新抛出原执行异常。

原执行函数内容移入 `_execute`，正常请求逻辑保留。异常不会被转换成成功结果；
原来未确认请求的资源处理和不重试行为继续由既有backend负责。
这是补齐诊断信息的工程修改，不是已经确认的连接或模型缺陷修复。

[传输测试](../../../../code/tests/execution_provider/test_async_transport.py)验证：

- 人为注入 `RemoteProtocolError` 时，恰好一次尝试、一次诊断，重新抛出同一个异常对象；消息和正文不进入诊断。
- 原因链包含循环时仍有限；诊断观察器随后失败也不覆盖原异常。
- 正常流式响应字节与原开始/结束事件保持一致，无错误事件。

新增诊断前，上述首项检查因缺少事件失败；修改后聚焦传输、backend和缓冲记录的11项全部通过。
Linux provider共77项，68通过、9项依环境跳过，包含未确认请求保留Job容量的既有检查。
后来增加的两个测试仅在本地运行；真实运行的源码快照与最终测试文件分别记录，未替换服务器运行快照。
测试编排中一次模块名错误、一次已被读完的Mock响应构造错误均保留在
[原始检查日志](raw/checks-and-service-logs.json.gz)，修正调用和fixture后通过；没有据此改变生产读取行为。
