# PostgreSQL Map 的有限窗口 token 工作量组织

日期：2026-09-10。角色：内部实现与行为/资源诊断记录。研究对象为 PostgreSQL 内置 AI 语义算子的外部分布式物理执行与调度优化。
对应[工作包 D 规格](../../../plans/data_organization_batching.md#工作包-cd-的实施规格2026-09-10继续)。

## 实现及验证对象

复用 `WorkWindowOrganizer`、`WorkDescriptor`、`SessionPolicies`、同一 SessionEngine 和异步 HTTP transport。
可选 `--organization-config` 加入三种控制：输入序固定行数、输入序固定工作量、有限候选前缀内按长度升序。
候选上限只查看已接纳且尚未提交的任务；不提前查询未来数据。分组仍展开成逐行独立请求，没有新增整组完成等待。
数据库继续拥有完整消息、生成参数、parser 和行/取消/结果生命周期，原生 Ray/LOTUS 没有注入这些策略。

tokenizer 只读取本地文件，禁止远程自定义代码，并在加载前后检查内容 SHA。完整规范消息的输入 token 数
加 `max_tokens` 作为活跃工作量；输出部分是生成预算上界，不是模型输出长度预测。估计身份包含模型和服务版本、
tokenizer 指纹、context 上限及计数规则。超出 context 的输入失败，不截断出站消息。
元数据在既有 1024 字节限制内接受；结果预留、字节预算、请求上限和取消机制继续由原核心负责。

查询配置保存组织文件及其 SHA；实际运行复制经过核对的配置。审计分别检查：

- 每次准备对应的 sequence、语义 payload 和完整请求 SHA，允许同一行反压后进行完全一致的准备；
- 实际 POST 字节、服务返回的 prompt token usage 与声明估计一致，不能仅用本地计数自证；
- 每次候选确为当时已接纳且未提交队列的有限前缀，选中成员符合控制配置；
- 核心实际提交成员、每组索引/大小、HTTP 开始顺序、活跃 token 工作量和最终责任；
- 原有独立 PG producer 行绑定和评价继续检查所有输入/输出，不从分组或完成顺序生成预期行号。

## 受控结果

同一 36 行异质输入，C=2、L=16、PG 留存 B=2 MiB/暂存 S=4 MiB、候选16、组行数4、
组工作量目标400、活跃工作量512、context512、生成上限128。HTTP fixture 使用相同保存的 fast tokenizer，
返回合法固定情感标签，并按输入长度设置响应延时；它不是语言模型。

| 控制 | 组织组数 | 实际输入序提交 | 活跃 token 峰值 | 后续行先提交的最大数量 |
|---|---:|---|---:|---:|
| 固定行数 | 9 | 是 | 444 | 0 |
| 固定工作量 | 27 | 是 | 444 | 0 |
| 长度分组 | 29 | 否 | 484 | 12 |

三组共108次受控HTTP、0次真实模型调用；36行各出现一次，标签全部符合fixture，服务端token数逐行匹配，
候选最多16，最终HTTP、Job及PG留存责任为0。行数与工作量控制产生不同分组但相同提交顺序，
因此不能把分组数变化解释成新的执行并行度。长度控制使短任务先提交，并完成所有长任务；
这只证明当前有限PG留存窗口下的行为，不保证无限持续到达时的公平性。

查询JCT分别1.504820、1.536043、1.293826秒，均为一次受控响应观测，不作模型性能或统计结论。
200ms采样的gateway RSS峰值约842–844MB，包含tokenizer及其Python依赖；它不属于payload字节账本，
采样可能遗漏更短峰值。模型tokenizer常驻成本与每行准备时间须另报，不能声称整个gateway进程受4MiB限制。

Linux调度369、provider55、PG合同116、文本/内存/组织审计6项通过；完整PG TAP为18文件2138项。
专项覆盖元数据可接纳、完整请求不变、context超限零后端调用、在途断开后回收及下一查询恢复，
以及篡改prompt usage、请求SHA、候选、分组、活跃work或校准身份时拒绝证据。
首个本地测试错误把请求取消视为资源已回收；改为由Engine推进清理后断言，原失败日志保留。
准备脚本还曾将可选缺少nvcc误当成preflight失败；报告总体为ok，未安装依赖或调用模型。
