## PG节点返回与客户端接收

原安装未编入节点追踪；设置GUC仍没有追踪输出，16行分段明确为unavailable。
用同一源码的`SEMLOOM_FLOW_DIAGNOSTIC=1`构建独立extension和PG软件目录；
PostgreSQL主二进制摘要与原安装相同，原库未修改。新增两条1024行顺序查询，共2,048次fixture POST。
共享Ray8个逻辑CPU、一个C64 worker、初始可用7个CPU名额；额外PG日志可能增加执行成本，数字不放入上表。
PG与Python都使用同一机器的`CLOCK_MONOTONIC`，逐行核对producer编号、Core提交、节点阶段和客户端结果。

| 诊断查询 | 首个节点返回（秒） | 客户端首行（秒） | 首行节点→客户端（秒） |
|---|---:|---:|---:|
| 首次查询 | 1.681 | 5.783 | 4.102 |
| 后续查询 | 0.233 | 2.688 | 2.455 |

后续查询的首批客户端交付包含316行；按PostgreSQL文本DataRow编码计算，四次交付分别约
8,106/8,190/8,216/2,026字节，最后77行随结束交付。前三批接近8KiB，第一批最后一个节点返回与
客户端开始消费只相差0.269毫秒。该观察与[PG18.3的8192字节发送缓冲](https://github.com/postgres/postgres/blob/REL_18_3/src/backend/libpq/pqcomm.c)
及[协议消息格式](https://www.postgresql.org/docs/18/protocol-message-formats.html)相符，支持结果发送缓冲解释。
没有抓取逐包网络记录；不把整个2.455秒写成网络传输时间，也不据此宣称刷新输出会降低完整查询耗时。
该定位属于无模型诊断，不从它补造旧真实运行的PG节点时间戳。
