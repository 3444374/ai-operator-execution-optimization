## 审查后的决定

| 审查事项 | 本次处理与证据范围 |
|---|---|
| D只看自报usage | 按`core_submitted`建立计算责任，只在`core_terminal`解除；每个work/request快照与重建值相符，缺失、少报、重复终态等均拒绝 |
| 排序后比较组内提交 | 成员索引/大小与原始提交顺序分开检查；整段提交序还必须等于选中组依次展开的顺序，不先排序消除错误 |
| HTTP顺序的含义 | 分列Core提交与transport-start次序，新增一致性字段；允许异步开始顺序不同，不把列出两序列写成已保证相同 |
| work是否真的限制了提交 | 增加默认关闭的Core容量拒绝观察；组织adapter启用。区分flow eligibility与选中成员dispatch，在重建责任后按requests/work/both分类 |
| 每项work的依据 | 服务返回prompt usage与描述匹配；生成预算另对回`SemanticPlanSpec.max_tokens`，防止一组自洽但偏小的work取代真实预算 |
| rows/work的物理含义 | 保留逐项独立HTTP，不增加整组屏障。`service_quantum`说明由下游决定物理执行；Map组织组不是共同完成或模型batch |
| C总留存实现 | 保留原实现与释放责任，在相同L/B/S及Core配置下补真实对照；不回滚或改PG C源码 |
| 审查中的A/B缺口 | 由`d2f9cc13`已覆盖；本次沿用共同结果文件校验、非PG关联、首错/取消时点与慢源交付修复，不重复开发 |

容量事件只观察原有判定，没有新生产账本，也不改变`can_dispatch`、Job选择、组内完成方式或归还条件。
计数表示实际容量检查被拒的次数，包含重复探测；不是阻塞时长，也不是不同任务数。
HTTP await结束、取消通知、结果交付、后端未知均不能提前释放计算责任。独立重建仅针对单Map无重试路径的
active-work/active-request；PG留存峰值与其他逻辑字节仍按各自观测范围核验，不叫整个系统的独立内存证明。

紧预算的三次查询都比对应宽松预算更慢，不把“限制生效”写成“性能优化”。rows/work仍保持输入序；

## 质量、留存和测量范围

TP/FP/TN/FN分别为真正例、假正例、真负例、假负例。八个验证配置中，七个为TP75/FP2/TN33/FN18，准确率84.375%；rows紧预算为TP76/FP2/TN33/FN17，
准确率85.15625%，与其余配置有1行预测不同。所有输出均合法、出站消息集合一致，逐行模型完成与最终行绑定通过。
这记录的是模型返回差异，不改写成八组预测一致，也不将它算作执行错行；未定位该模型差异的数值原因。

六个D验证单元的PG留存峰值均4,489,728字节、64行，最终为0；query期间gateway采样RSS约902–904MB，
含常驻tokenizer依赖，不能称整个系统内存受8MiB限制。C gateway约48MB；C/D配置不同，不能拿此直接做token化收益消融。
各D配置均准备128项/128次，没有观察到反压重复token化；累计准备约0.094–0.129秒，属于查询时间。
模型tokenizer在gateway启动时加载，SQL JCT不含gateway启动；query-rss只代表采样时点，不能保证捕获启动峰值。

验证首行在应用端可见的时间分别接近各自JCT（差约2–3ms），backend终态到应用消费的积压峰值均为128。
实际计划只有Custom Scan及Seq Scan，没有Sort；本次未定位延迟集中在哪一层。
**该积压包含gateway、SQL传输、PG顺序恢复及消费者，不能当作PG节点内已完成未交付行数**，也不证明PG保留128行。
精确的PG ready-row计数仍未采集；避免用这个代理值与L=32/64直接判定内存越界。

## 结论与后续

C的总留存能力和D的可替换组织接口保留；新增证据补齐了提交责任与顺序审计，并在真实模型上证明work限制确实可生效。
本轮不提供稳态性能、强静态参照、跨原生系统排名或多Job公平结论。
下一步优先为有独立重复的同资源比较、请求数FIFO对token表征FIFO的准备/常驻成本消融，以及PG节点内结果等待观测。
不建设通用准备缓存，不把准备移出计时，不为制造rows/work差异加入整组完成屏障；E/F未执行。

服务正常退出；PG停止、socket移除、模型端口可重绑、GPU无计算进程、任务进程无残留，原/root ACL恢复。
PG/ACL清理记录距模型准备起点502.065秒，小于20分钟；后续进程组复核也未发现模型子进程残留。
