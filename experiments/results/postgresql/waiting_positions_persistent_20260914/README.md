## 目的与设置

继续检验提交限制是否改善完整查询，补充常驻gateway/tokenizer成本与C4/C8稳定性。
生产调度策略不变；新增有限串行查询实验适配器，复用生产gateway、持久POST账本、PG配置与评价。
PG拥有每条SQL及结果生命周期，实验group拥有一个gateway/tokenizer与192次POST分配。
每条查询分别观察EOF、Job归零、socket session结束；只有group结束才记录transport关闭。

- 测量源码`4f06ab1e`，最终实现`e480bc30`补强失败汇总：预算关闭或结果汇总写入失败时不能继续显示成功。
  后者没有改变成功测量路径；最终Linux合同检查及完整`code/`哈希另行核对。
- Linux/Python3.12.3/PG18.3；复用先前`SEMLOOM_FLOW_DIAGNOSTIC=1`、`-O2 -Werror`测试构建，
  逐个C/H源码与已安装库SHA匹配。未重建或重跑无关PG全套；真实模型请求0次。
- 真实PG→生产gateway→本机受控分类HTTP。服务槽4、listen backlog32、L8；Core输入/结果各8MiB、
  PG total8MiB/暂存4MiB、context512、最大输出128，输入序输出。没有修改模型服务或GPU配置。
- 与上一轮相同的32行合成evaluation文本/ID，24/80/144/224词循环，完整请求work187/243/307/387。
  上一轮已使用这些数据；本轮不是新的独立质量评价集，也不使用本轮结果重新选择输入或W。
- 四个gateway均先启动并全程常驻；任一时刻仅运行一条查询。四组各1次预热+5次测量，
  预热0123，测量0123、1230、2301、3012、0123（顺序编号对应下表四行）。
  共24查询/768受控POST，SQL阶段每条15秒，外层500秒，实际编排39.156秒。
- 公共PG准备函数提取另跑旧total-budget Map入口：1查询/120受控POST，通过，约3.965秒。
  本轮总计25查询/888受控POST；旧入口不进入常驻对照，亦未重复原先672次试验。

## 计时与观测核对

每查询计时从方法调用开始，包含manifest读取、PG连接/配置与SQL执行，到客户端EOF结束。
共享数据准备/导入及gateway/tokenizer启动单列；结果持久化、查询后事件投影与评价另报。
同一group的原始JSONL不修改，查询记录保存完整字节区间；后续查询的组织配置引用第一次启动记录。
没有伪造每查询启动或transport关闭。每条查询均等待真实Job归零和对应session结束才继续。

不可变普通表的单Map全扫描在调用时拥有共同逻辑资格a；此假设不适用于任意SQL、NULL、依赖或LIMIT。
逐行核对五段时间之和等于客户端收到−a：资格→提交、提交→权威终态、终态→PG就绪、
PG就绪→节点交付、节点交付→客户端。权威终态是Core结算；HTTP包含连接/服务排队/响应读取，不能当GPU时间。
小结果仍存在协议缓冲：节点→客户端的等待不等于PG持有行数或内存占用。

原始记录离线重新验证：24条查询的结果SHA/字节/行数、PG独立行绑定、请求多重集、五段守恒、
各group session1…6、无跨查询事件混入、资源归零与最终transport关闭全部通过。
HTTP handler按SQL时间区间重新匹配32个请求摘要，不能仅因总请求数相同就认为查询关联正确。
宽W全部保持提交0…31且无work-only拒绝；紧W同序且均观察到work-only拒绝。
4×192次额度由group持有，无退款、重置或隐式重试。最终本地/Linux各16项相关合同检查通过。

## 资源、失败与清理

所有查询的PG行关联32/32，合成分类invalid/false-positive/false-negative均0；这只证明fixture合同。
每条查询HTTP及逻辑资源回到0，四个group均完成6个Job；transport关闭仅各一次，最后usage全0。
RSS按同一采样时点同时包含四个常驻gateway、driver/HTTP fixture与当前PG backend，间隔0.2秒。
常驻gateway各自观测峰值：C4约47.41MiB、C8约47.66MiB、宽token约803.82MiB、紧token约804.17MiB；
driver约588.36MiB、PG backend约13.38MiB，同tick合计峰值2304.72MiB。
各自峰值不相加作为并发峰值；RSS可能重复统计共享页，也可能错过短峰值。没有测量整个系统的唯一物理内存。

查询及旧入口回归没有运行失败。第一次离线复核误调用会写`evaluation.json`的评价入口，
收到`FileExistsError: evaluation already recorded`；失败脚本与说明保留。
修订复核器读取已有结果、先核对SHA/行数/字节，再调用纯评价函数；没有覆盖原评价或重新发出HTTP。
关闭失败的汇总状态也补充故障注入检查，不把正常运行未出现错误当成所有失败路径已验证。

最终PG pid文件、gateway socket、任务进程均为空，临时ACL已恢复；HTTP active0且服务线程退出。
两张GPU各1MiB、利用率0%；本轮未启动真实模型。原始私有证据、两版复核器和隔离源码保留。

## 事实、推断与不能声称

**事实**：C8五次均快于对应轮次C4，中位JCT0.406923秒对0.494904秒，降低17.78%；
这是同一fixture内比上一轮更稳定的观察，尚不是跨服务/跨输入的最优并发资格。
宽token组中位JCT0.395086秒，与request C8接近；约2.91%的差异不足以证明token表征带来收益。

**事实**：相对同C同序宽W，紧W的HTTP P99中位数从0.102986降至0.059492秒（降低42.23%），
但完整JCT从0.395086升至1.315864秒（增加233.06%，约3.33倍）。提交前和节点→客户端等待同时增加。
紧W把最多8个请求的提交机会压到至多2个，无法充分使用4个服务槽；本轮服务时长由fixture预定。
该受控结果继续支持“减少在途工作不必然改善完整查询”的反例。

**事实**：token组一次启动约5.53/5.63秒，常驻后每查询准备中位数约14/15毫秒。
这使先前按每查询新gateway计算的成本与常驻查询成本分开，但保留了约804MiB/实例的RSS观察。
共享准备、预热和启动没有消失；若计算整组摊销成本，须加回启动及预热，并注明摊销查询数量。

**推断范围**：原始trace说明等待位置变化；尚未证明真实GPU工作量限制的收益或一般性劣势。
完整诊断观测与低扰动执行尚无匹配消融。四实例全常驻、每组单生命周期、短查询和固定合成输入
限制了外推；不能将跨轮变化称为严格单变量因果，也不能由HTTP P99替代查询指标。
