## 为什么调整

[旧常驻实验](../waiting_positions_persistent_20260914/README.md)已经说明：提交后 HTTP P99 降低 42.23%，
完整查询却从 0.395086 增至 1.315864 秒。W512 最多容纳两个最小 work=187 的请求，不能充分使用四个受控槽。
旧实验作为测量反例结束，不再用它证明工作量控制有效。

源码 `MAX_MODEL_RESPONSE_BYTES=1,048,576`，Core 结果 32 MiB 使可接纳数最多为 32；
旧 C64 点不能测试声明的供给。原 44,544 次、三种控制×两种日志的表已撤下；
[数据准备报告](../waiting_positions_real_preparation_20260914/README.md)的输入、统计与原始配置继续保留为历史证据。

## 实现与判断

- `m1_campaign.py` 使用 v2 显式阶段、统一存储、组清单、配对轮次和按行数计算的 POST 总量。
  旧配置在访问 PG 前被拒绝；本地预检输出 Core 输入/结果、行数以及 PG 留存/暂存的保守估量。
- 筛查复用常驻 PG gateway 与已有 PG-source direct；阶段不自动接续。工作量调参必须引用同签名、
  同资源和同判定参数的筛查报告，面对选定的请求数参照，并保持同一个较高保护 C。
- `m1_selection.py` 使用完整有效吞吐、持续 HTTP 供给和配对原值；没有平台、供给不足或重复波动大时
  返回具体状态，不从接近的中位数制造“已饱和”。工作量无优势、未触发或付出吞吐代价均保留。
- 评价使用独立输入，配置须匹配已记录且校验 SHA 的调参决定。输出差异按行值摘要计算，
  不使用包含接收时刻的记录文件 SHA 判断预测变化。合法但标签判断错误的结果继续进入吞吐与质量分母。
- `m1_measurement.py` 汇总实际 HTTP 占用时间、逻辑资源时间积分、分进程 RSS 字节秒、CPU 时间和真实输出 token。
  Core 结果预算始终标为预留；PG 没有完整字节时间线时明确不可用。公共阶段采样包含各臂运行期间的全部常驻 gateway。

独立评价比较有限较高 FIFO、调优请求数 FIFO 和调优工作量 FIFO；同 C 且 W 不生效的 token FIFO 只承担少量表征消融。
M2 继续研究全局信息与有限候选，M4 单独研究多查询服务分配，不扩大 M1 的研究任务。
没有修改 PG 语义、生产 Core、MapOrganizationConfig 或 vLLM 调度器。

## 验证

[本地检查日志](raw/local-checks.log)、[源文件摘要](raw/source-sha256.json)与[校验清单](raw/SHA256SUMS)保留本轮证据。35 项通过，其中 20 项为新 M1 行为检查，
其余覆盖已有等待分解、常驻查询结束、输入划分和 direct/PG 实验适配。
新增检查覆盖以下反例及正常行为：

- C64/32 MiB 在数据库和账本访问前拒绝；输入、PG 留存、PG 暂存也能分别拒绝不可达点。
- 统一 128 MiB Core 结果预算允许 128 项预留；实际供给仍写未证明。
- 最高档继续改善、瞬时峰值但中段供给不足、大重复波动、非法/缺失/混合身份结果均不产生错误选点。
- 语义答错保留；配对吞吐损失与输出变化同时报告；未触发的 W 不选为工作量候选。
- 显式 24 条 fixture 查询分别走替身 PG/direct，共核算 3,072 项，不访问外部服务，也不开始评价。
- 失败保留部分记录并停止；调参报告不匹配、后改评价设置或将日志模式塞入容量矩阵均被拒绝。

[CLI 静态预检](raw/static-preflight.json)另使用临时 128 行合成输入核对本地命令：
旧 C64 配置的 `core_results=32`，统一资源示例的 `core_results=128`；前者拒绝、后者通过静态估量。
示例数字仅为结构/逻辑检查，不是下一批真实请求额度。

最初一次 unittest 命令误写模块为 `code.tests`，因标准库 `code` 名称冲突在加载阶段报错，执行 0 项；
改用 `PYTHONPATH=code` 与 `tests.experiments` 后运行上述检查。没有失败真实查询，也没有模型重试。

## 尚未验证

- 本轮没有运行修改后的真实 PG campaign 或模型，已有历史 PG/gateway 检查不能替代此次完整编排的现场验证。
- 当前匹配 direct 包含 SQL 读取与每查询客户端准备；它的平坦曲线不能单独证明纯服务平台，不能与 PG 时间相减归因。
- vLLM running/waiting、KV 和抢占需用已有外部服务采样器核对当前部署；本轮汇总明确写未附加。
  这些字段的[官方定义](https://docs.vllm.ai/en/v0.25.1/usage/metrics/)只是采集依据，未冒充实测。
- 静态 PG 行估量使用当前行分配公式和保守元数据余量；运行前还须核对实际计划窗口、输入身份和全过程资源。
- 配对观测范围不是置信区间；重复数量和接受差异须在真实运行前确定，波动过大时报告不明确。
- 本模块依赖已有账本期限和每查询期限；调用者仍负责服务与外部进程监督，准备/清理卡住时由监督停止进程。

真实调用继续暂停。下一步先审阅少量可达筛查点和对应的新请求/时间额度；不恢复旧 44,544 次方案。
