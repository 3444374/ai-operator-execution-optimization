## 修复内容与回归检查

原实现每检查一个排队候选，都重新遍历整个任务表，汇总全局、session和Job的使用量。
候选越多，单轮只读可达性/进展检查重复做的工作越多。现有任务表继续是唯一责任来源。

[`any_dispatchable`](../../../code/src/scheduling/core/session_capacity.py)只在一次只读扫描内复用派生使用量，
供全局Job/flow选择、owner进展和session交付进展三处使用。返回后即丢弃；下一次提交、完成、取消、释放和扫描
都重新读取真实任务表。没有增加持久计数账本、模型请求重试、跨轮缓存或新的调度策略。
这是针对源码与profile证据的工程修复，不是论文方法贡献。

[行为回归](../../../code/tests/scheduling/test_capacity_wait.py)包含128个留存任务、4个在执行请求、124个排队候选：
原owner单tick汇总745次，断言失败；只修前两处后，owner＋delivery仍汇总379次，第二次断言失败。
完整修复将同样的检查控制在固定的≤12次汇总，并验证一个请求完成后立即允许下一个FIFO成员执行。
两次失败和最终通过分别保留在 `regression-before`、`regression-delivery-before`、`regression-after` 日志中。

## C64失败、记账差额与证据缺口

[失败查询](raw/failed-query.json.gz)返回 `SQLSTATE 08006`，消息为 `SemLoom model endpoint is unavailable`。
[事件投影](raw/failed-events.json.gz)显示该查询512个HTTP开始/结束、510个Core权威终态、2个`core_uncertain`；
两项对应sequence468和508。gateway记录480次Map结果交付，客户端实际保存443行。
[记录器](raw/failed-recording.json.gz)将这些行明确标为 `partial_results_are_provisional=true`，保留内容SHA，拒绝成功评分。

账本在HTTP发送前计数，因此其 `actual_posts=1552` 在本次应读作**1,552次已记账尝试**，不能证明每次都到达模型。
服务访问日志和最后服务采样的success counter均为1,550，即16＋512＋512＋510。
多出的两次没有服务端成功证据，不退款、不重置额度；[控制器](raw/controller-summary.json.gz)记录计数不一致并保持失败。

源码 `BoundedAsyncBackend.poll` 把执行异常转换为 `MODEL_UNAVAILABLE`，当前事件没有保留原异常类型；
[事件计数与缺项](raw/failed-event-counts.json.gz)如实标注。服务日志没有对应的模型错误堆栈，最后采样running/waiting均0，
所以不能仅凭PG消息断定模型崩溃，也不能确定是连接、客户端内部操作或其他执行异常。
没有据此增加重试、修改超时、换服务参数或认定Core修复已经覆盖C64。

`p64` gateway的[关闭记录](raw/failed-gateway.json.gz)另保留“进程需要强制终止”。
两个未确认任务没有被伪造为正常终态；最外层控制器随后停止全部自有服务。
[最终核对](raw/final-cleanup.json.gz)：18092/57734/57735/57736无监听，PG/模型/任务进程清理，
GPU0/GPU1均1MiB、0%且无计算进程，临时ACL恢复。文本模型正常停止；gateway强制停止单独记述，二者不混同。
