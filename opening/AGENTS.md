# opening/AGENTS.md

本目录维护开题相关材料，包括开题报告、开题汇报 PPT、飞书进度汇报、文献精读、答辩问答和材料同步日志。进入本目录前先读根目录 `AGENTS.md`，再读本文件、`README.md` 和 `navigation.md`。

## 工作定位

- 开题不是证明课题已经完成，而是证明题目有研究价值、问题定义清楚、技术路线可执行、前期准备有基础、后续计划能落地。
- 开题材料不能写成项目宣传稿。必须主动说明当前证据、边界、风险和后续验证计划。
- 当前汇报主线优先采用：先讲数据库成为 AI workload 入口后带来的数据执行链路问题，再讲已有实验发现的 batch、调度、模型服务和写回瓶颈，最后讲上游数据组织与调度提交控制的优化方向。

## 目录职责

- `report/`：开题报告正文、Word 转写材料、学校模板适配记录。
- `slides/`：开题 PPT 源稿、讲稿备注、PPTX 输出和模板适配说明。
- `feishu/`：飞书进度汇报稿、周/月度同步材料。
- `literature/`：开题文献精读清单（`reading_list.md`）与既有 Top 15 笔记快照（`top15_reading_notes/`）。泛读笔记在 `research/reading_notes/`，新的权威精读笔记在 `research/精读文献笔记/`，PDF 在 `research/reference/`。
- `assets/`：PPT 可复用图、SVG、表格、流程图和模板素材说明。
- `logs/`：非实验类 project log，记录开题材料、文献、PPT、飞书同步变更。

## 写作规则

- 结论必须有来源和边界：文献、官方文档、本地实验事实、合理推断、待验证问题要分开写。
- 不把 Ray 写成唯一研究对象。更稳的表达是"数据库 AI 负载的执行优化与调度"；Daft/Ray/Lance 是系统机制和验证平台，不是简单产品集成题目。
- 不把开题阶段的初步实验写成最终贡献。使用“可行性依据”“初步信号”“后续将扩大验证”等表述。
- 创新点写成预期创新点，并与研究内容、技术路线、评价指标一一对应。
- 正文和 PPT 避免 AI 味：少用空泛意义、宣传式表述、过度强调、长段落和没有依据的“重要意义”。
- 正式对外材料不得直接使用只有项目成员才熟悉的管理用语或缩写。遇到“冻结、门禁、闭环、边界、约束、合同、产品轨、框架轨、正式点、晋级、失效”等说法时，优先改写为具体对象、具体条件和实际动作；确属学术术语时，在首次出现处解释清楚。
- 图题先说明图在比较什么或回答什么问题。图下注释要让不熟悉项目的读者知道坐标和线条怎么看、主要现象是什么，以及这组结果目前还不能推出什么，不能只写实验内部分类和数据来源。
- 图中可见文字也属于对外正文。总标题使用“研究对象或比较条件 + 主要观察”，分图标题使用可直接验证的现象；框内保留系统名时同时写明它负责读取、组织、提交、执行还是写回。不得让“证据链、候选组合、状态不足、容量边界、WorkDescriptor、shared credit”等内部或抽象标签脱离解释单独出现。
- 图中可以使用确有解释作用的项目数据结构或执行量，例如 WorkDescriptor、BatchRequest、RuntimeStateSnapshot、Request Credit 和 Work Credit；必须在图内或紧邻图注说明中文含义。不得把“冻结、门禁、闭环、晋级、正式点、产品轨、框架轨”等项目管理抽象当成读者已知概念。
- 报告中的必要图包括研究对象图、两项研究内容的方法图和总体实验方案图。优先修改已有可编辑源图；已有图能够回答同一问题时，不新增近义架构图。蓝色固定表示研究内容一，橙色固定表示研究内容二，紫色表示两项内容共同使用的组件或公共执行部分，绿色表示结果、评价或写回，灰色表示观测、注释或边界。
- 报告、PPT、图表和飞书稿定稿前执行一次自然语言检查：搜索内部工作用语和未解释的英文，朗读含有连续抽象名词的句子；如果一句话只能由项目成员解释，就继续改写。
- 动机部分采用“总动机 → 子问题 → 证据实验 → 观察结论 → 研究内容”的层级。总动机必须是一句能够统摄多个实验的研究不足，实验脚本、对照臂、参数扫描和实现模块不能与总动机并列。多个子实验共同支持一个总动机时，先写父命题，再说明每个实验排除了哪一种简单解释。
- 层次调整优先通过段首总述、段间过渡和段末收束完成，不因强调层次就把正文拆成大量细标题。每项研究内容先用一句话说明研究对象和总问题，再列出需要完成的少量组成部分；每组动机实验先回到总问题，再说明各实验分别证明单一指标遗漏了哪一类信息。当前研究内容一包含“分阶段工作量表征、数据组织”两个环节；研究内容二包含“提交控制、服务实例路由、多作业调度”三个部分。
- 同一层的标题、表格行和连续页面必须具有相同粒度。检查时依次问：父标题能否概括全部子项，兄弟项是否都属于问题、证据或方法中的同一类，每项证据能否回到唯一研究问题，研究内容是否稳定而没有随实验数量膨胀。当前报告固定为三个动机实验对应两项研究内容：动机实验一导向数据组织，动机实验二和三共同导向提交、路由与多作业调度；代价估计和跨模态验证分别是共同使能与验证角色，不提升为平级研究内容。
- 代价估计按“数据库计划比较的共同支撑 + 两项研究内容的可选增强”展开。研究内容一可选择使用预计批次时间和资源需求，研究内容二可选择使用预计服务时间、剩余工作和服务目标余量；先建立依据可观测工作特征和实际状态运行的基础方法，再以实际吞吐、完成时间或尾延迟检验代价信息带来的额外收益。
- 对外正文优先正面说明对象的角色、输入、输出和作用位置。内部分类争议不主动带入正文；否定式表述主要保留给实验结果的证据范围、文献方法的适用条件和必要的概念辨析。
- 综述正文使用论文正式英文原题，中文用于解释问题、方法、证据和与本课题的关系；不使用书名号包裹自译中文论文名。
- 动机实验二和三的合并理由必须落实到同一个上游调度决策：服务侧状态决定“何时提交、发往哪里”，作业侧状态决定“下一份工作来自哪个作业”，三类动作依次对应提交控制、服务实例路由和多作业调度。不得只写“二、三对应研究内容二”而省略这条因果桥。
- 第一章保留数据库业务记录、AI 语义算子和外部执行链路的必要解释，只压缩提前出现的具体实现、参数和实验结果；不得为了避免“剧透”而删掉读者理解课题所需的运行例子。国内外研究现状必须形成覆盖主要方向的连续文献综述，不能用“不要表格”概括其要求：正文需要综合讲解多篇相关工作，对 `research/精读文献笔记/` 中的当前权威精读和 `opening/literature/top15_reading_notes/` 中仍适用的开题快照给予更充分篇幅，具体说明研究问题、核心方法、实验结论或适用条件、局限以及与本课题的关系；其他文献用于补足发展脉络和方法分类。不得用研究问题表或文献对照表替代这部分论述。除第一章用于解释业务记录和 AI 输出的示例表外，正文原则上不新增表格。
- 进度安排按约定研究周期划分多月时间段，可使用“2026 年 8 月—2026 年 11 月”或“第 1—3 个月”等范围，不按单月逐项罗列。每段只写阶段目标，不展开实验参数和实现任务清单；除非学校模板强制要求，开题材料、学位论文撰写、送审和答辩准备不列入研究进度。

## PPT 规则

- 学校模板是版式约束，不是背景截图。优先复用母版、占位符、主题字体、页眉页脚。
- 正文、图表和流程图必须放在安全内容区，不压页眉、页脚、校徽。
- 一页只突出一个主结论。图中只放关键词，解释放到备注。
- 每页备注默认包含两块：`汇报讲稿` 和 `答辩备注`。
- PPT 生成或修改后必须用 WPS/PowerPoint 实际打开检查。
- **修改 PPT 时，如果用户说明已手动调整了部分内容（图片位置、文本位置、字号等），不要重新运行 build_ppt.py 做全量覆盖。** 必须用 python-pptx 直接操作现成 .pptx 文件的对应 shape，做增量修改，保护用户的手动调整不被冲掉。

## 同步规则

- 改题目时，同步报告、PPT、封面、飞书标题和 README。
- 改研究内容时，同步技术路线、进度安排、创新点和答辩备注。
- 改文献时，同步报告参考文献、精读清单、PPT 参考页和文献日志。
- 改实验口径时，同步 `motivation/results/`、`learning/experiment_walkthrough.md`、报告、PPT 和飞书版相关表述。
- 非实验类修改记录到 `opening/logs/project_log.md`，不要写进 experiment log。
- 需要查找材料时先读 `navigation.md`：项目总方向查根 `README.md` / `PROJECT_INDEX.md`，实验结果查 `motivation/results/` 或 `feasibility/results/`，学习讲解查 `learning/`，文献证据查 `research/`。
- 报告、PPT、飞书版必须互相同步：报告负责完整论证，PPT 负责现场讲解，飞书负责发布同步，不允许三者形成不同口径。

## 文献规则

- 文献优先从 CCF-A 会议/期刊和权威系统论文中选择，再补官方文档和工程系统资料。
- 参考文献不能只满足数量。核心精读文献要能回答：解决什么问题、核心方法是什么、和本课题有什么关系、有什么不足。
- Snowflake、pgai、PostgresML、pgvector、Ray、Daft、Lance 等资料要区分论文、官方文档、源码 README 和本地实验事实。
- 同一工作已有正式会议或期刊版本时，报告优先引用正式版本，并用正式题名、作者顺序、venue、卷期、页码和 DOI；仍只有预印本时才引用 arXiv 版本号。论文已录用但卷期、页码或 DOI 尚未公布时，引用官方录用名单或会议程序并标注 `accepted`/`to appear`，不得提前补造出版信息。
- 本地精读 PDF 与正式发表版本不一致时，分别记录“发表状态”和“实际阅读版本”。正文涉及查询数、数据集、图表或实验结果时必须说明数字来自哪个版本，不能把正式 venue 与旧预印本的实验细节混合成一个未加说明的题录。
## 飞书同步规则

- 本地 Markdown 是源稿，飞书文档是发布面。
- 开题报告与开题汇报同步到用户给出的开题飞书 wiki。
- 动机测试与可行性测试同步到用户给出的实验飞书 wiki。
- 实际写入飞书前必须先检查本地报告、PPT、实验结果和飞书版口径一致。
- 普通飞书 wiki / docx 使用 `lark-doc`；嵌入 Base 时再用 `lark-base`；直接编辑飞书幻灯片时再用 `lark-slides`。
- 飞书上的实验内容记录标准与项目实验报告保持一致，讲解方式参考 `learning/experiment_walkthrough.md`：必须解释实验问题、链路位置、变量含义、原始结果、结果怎么读、能说明什么、不能说明什么和下一步。
## 默认参考 skill

开题工作可按任务需要使用以下 skill。它们是方法参考，不是固定流程；真正执行时必须结合本项目的真实阶段、已有实验结果、导师要求、学校模板和当前材料目标灵活选择。不要无脑同时调用，按当前任务选择最小必要集合。

- `karpathy-guidelines`：用于控制假设、边界、实验结论、代码和文档修改范围。
- `humanizer`：用于开题报告、PPT 讲稿、飞书材料的自然表达，避免 AI 味、宣传式表述和空泛意义。
- `academic-research-suite`：用于开题任务组织、研究计划、实验设计、材料完整性检查和阶段性 review。
- `deep-research`：用于需要系统综述、研究问题收敛、研究空间判断和证据地图时。
- `nature-academic-search`：用于开题文献调研、权威论文检索、引用核验、CCF-A 优先文献筛选和参考文献管理。
- `vibe-research-workflow`：用于 AI 辅助研究的流程控制，保证研究判断、核心结论和学术责任由用户掌握。
- `ppt-master`：用于开题 PPT 的源稿到 PPTX 工作流、模板适配、页面生成、备注和导出检查。
- `nature-paper2ppt`：用于借鉴学术汇报叙事、证据驱动的页面组织、图表选择和自检规则。
- `figure-designer`：用于设计开题核心图，包括问题动机图、技术路线图和实验结果图。
- `nature-figure`：用于需要论文级实验图、组图、导出规范和图表质量审查时。
- `lark-doc`：用于普通飞书 wiki / docx 的读取与同步。
- `lark-base`：用于飞书文档中嵌入 Base / 多维表格时的结构化数据维护。
- `lark-slides`：用于后续直接创建或编辑飞书幻灯片时。

文献调研默认优先使用 `nature-academic-search`；需要较完整的研究版图或综述时，再结合 `deep-research` 和 `academic-research-suite`。如果本地已有项目证据已经足够支撑某个判断，优先使用本项目真实材料，再用 skill 补文献、结构和表达。
