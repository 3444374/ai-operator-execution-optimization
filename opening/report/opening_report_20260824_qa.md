## 2. 研究方案与当前完成内容

报告已区分计划中的数据库入口和当前实验使用的物理执行入口。计划中的 PostgreSQL AI 语义算子负责查询计划、权限、取消、错误和结果生命周期，文本场景复用 LOTUS v1.2.4 `sem_map` 的提示构造和输出解析语义；当前实验中的 `AI_COMPLETE` 与 `AI_EMBED` 表示任务的输入输出含义，尚未完成 LOTUS 语义入口迁移和 PostgreSQL 查询计划接入。

现有实验采用的 AI 操作来源已逐项交代：直接路径使用项目异步 HTTP 客户端；DuckDB 路径使用社区 `ai` 扩展的 `ai_try_complete`；Daft Native 和 Daft Ray 使用 Daft 内置 `functions.prompt`；Ray Data 使用其 HTTP Processor 或 `map_batches` 执行图；项目文本路径使用 Daft/Arrow、Ray 有状态执行单元和 vLLM；图像向量由 Hugging Face Transformers 的 CLIP 模型产生。现有结果用于验证数据库读取之后的数据组织、请求提交、模型执行和结果收集，不被写成数据库内 AI 算子已经实现的证据。

这种分层方式能够先观察数据库读取之后的组批、提交、路由和多作业选择，但不能替代数据库侧记录流交接、查询取消、错误传播和优化器集成验证。报告已相应把现有结果限定为外部物理方法的可行性依据，并把 PostgreSQL 查询计划接入列为后续工作。

## 3. 核心概念与重复检查

正文在首次需要的位置区分了语义工作项、批次请求和模型服务请求，并解释了语义算子、词元、向量化、在途工作、作业、工作描述、模型服务实例、KV 缓存、MFU、P95/P99、JCT、SLO、Jain 指数、岭回归、LightGBM、L2 归一化等概念。批次请求是交给调度模块的数据组织结果，不等同于外部模型服务实际接收的一次调用。英文系统名保留英文，指标和内部结构名在首次出现时给出中文含义。

“容量”没有作为抽象额度使用：背景只区分配置允许接收的工作与实际正在准备、排队和执行的工作；研究内容二进一步说明，固定容量是同一实验中每个模型服务实例允许所有作业合计使用的模型服务请求位置和工作量空间保持不变。提交请求会同时占用目标实例的一个请求位置和相应工作量空间，请求完成后两者重新可用；静态方法在每个实例上为作业预留空间，共享方法让仍有待处理工作的作业使用空出的公共空间。第四章用每个实例 128 个请求位置和 65,536 个预计词元工作量说明具体分配关系。

代价估计的主要作用写为数据库优化器比较 AI 算子与关系算子的候选计划，并可在独立验证后向两项研究内容提供额外信息。数据组织和调度本身均有不依赖代价估计的基础方法。当前代价实验只比较一个文本 AI 物理执行链在四种在途工作量上限下的完成时间与排序，未被写成 SQL 计划优化或两项策略已经获得收益。

## 4. 实验叙述与证据范围

第三章的动机实验只说明研究问题：固定行数不能表示文本工作量，图像不同阶段具有不同工作特征，单一容量或运行指标不能代表服务状态，多作业并发会改变逐作业完成时间。第四章详细说明实验输入、硬件与模型、被测路径、改变的变量、重复次数、指标、结果和不能外推的结论。

数据库读写端到端对照和框架原生对照分开说明。SQuAD 三条数据库读写路径的数据、模型、GPU 和输出要求一致，但项目路径的计时还包括指标采集、运行记录写入和作业结束处理，因此现有绝对时间只作观察，不进行不到 1% 的细微性能排名。DuckDB 的 ShareGPT 路径因输出含义不能严格对齐，不与其他路径作性能排名。图像路径当前支持静态执行链、阶段拆分和多作业干扰观察，不被写成状态感知调度已经取得收益；pgvector 写回与检索质量实验仍列为后续验证。
