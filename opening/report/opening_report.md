# 数据库 AI 负载的执行优化与调度研究

## 1. 课题背景、目的和意义

近年来，人工智能（Artificial Intelligence，AI）模型逐步进入数据分析与数据管理流程，数据库所承担的任务也从结构化数据存储、检索和统计分析，扩展到文本生成、语义理解、智能分类、向量化和多模态分析。向量化是把文本或图像转换成数值向量，以便进行相似度检索；多模态分析则同时涉及文本、图像、音频或视频等不同形式的数据。Snowflake Cortex AISQL、Google BigQuery ML/AI、Oracle AI Vector Search，以及开源关系数据库 PostgreSQL 生态中的 pgvector 和 pgai，已经允许用户通过结构化查询语言（Structured Query Language，SQL）或数据库工作流触发模型调用[1-5]。其中，pgvector 用于在 PostgreSQL 中保存和检索向量，pgai 用于连接数据库数据与外部 AI 模型。在这类工作流中，数据库不仅保存业务数据，还要筛选待处理数据、触发 AI 操作并管理处理结果。

这里所说的数据库 AI 工作流，是由数据库查询产生、并且需要调用模型处理的一组任务。数据库中保存的仍然是评论、客服工单、新闻、企业文档和图片等业务数据，而不是预先准备好的一列提示词。提示词是发送给模型的指令和输入内容。例如，在电商评论分析中，数据库表的一行可能包含商品编号、评论编号和评论正文。用户先用普通 SQL 筛选某个商品近期的评论，再通过 AI 语义算子判断每条评论主要涉及续航、物流还是屏幕质量问题。本文所说的 AI 语义算子，是查询中调用模型完成分类、摘要、抽取、向量化或语义判断的操作[20,22,29]。数据库查询的对象仍然是业务记录，AI 语义算子规定模型要对这些记录完成什么处理。

假设数据库中有如下评论表。`review_id` 是评论编号，`product_id` 是商品编号，`review_text` 是评论正文，`created_at` 是记录创建时间：

| `review_id` | `product_id` | `review_text` | `created_at` |
|---:|---|---|---|
| 101 | phone_01 | 手机很好用，但是电池续航有点差 | 2026-08-18 |
| 102 | phone_01 | 发货太慢了，等了一个星期 | 2026-08-19 |
| 103 | phone_02 | 拍照效果很好，夜景也很清楚 | 2026-08-19 |
| 104 | phone_01 | 屏幕用了两天就出现坏点 | 2026-08-20 |

普通关系查询可以筛选出某个商品最近需要分析的评论：

```sql
SELECT review_id, review_text
FROM reviews
WHERE product_id = 'phone_01'
  AND created_at >= CURRENT_DATE - INTERVAL '30 days';
```

如果业务人员还希望判断每条评论主要反映什么问题，则可以用概念性的 AI SQL 表示。这里的 AI SQL 是在普通 SQL 中加入模型调用函数；示例中的 `AI_COMPLETE` 表示调用文本生成模型处理一条评论：

```sql
SELECT
    review_id,
    review_text,
    AI_COMPLETE(
        review_text,
        instruction => '判断这条评论主要讨论的问题，只返回问题类别'
    ) AS issue
FROM reviews
WHERE product_id = 'phone_01'
  AND created_at >= CURRENT_DATE - INTERVAL '30 days';
```

不同数据库产品的 AI 函数名称和参数形式可能不同，上述 SQL 只用于说明查询语义。数据库先通过普通条件筛选业务记录，再由 AI 算子处理所选记录，结果仍与原记录一一对应：

| `review_id` | `review_text` | `issue` |
|---:|---|---|
| 101 | 手机很好用，但是电池续航有点差 | 电池续航 |
| 102 | 发货太慢了，等了一个星期 | 物流 |
| 104 | 屏幕用了两天就出现坏点 | 屏幕质量 |

在这个例子中，`review_id=101` 的业务记录与“判断主要问题”这一 AI 操作结合后，形成一条完整的分类请求；如果同一条评论用于生成客服回复，则会在另一个 AI 操作下形成不同请求。因此，请求的身份不能只用数据库行号表示，还需要知道它来自哪个查询、哪个 AI 算子以及哪条业务记录。数据库中的行回答“处理的是哪份数据”，AI 算子回答“要对这份数据做什么”，二者结合后才构成执行层需要组织和调度的工作对象。

传统数据库查询主要围绕扫描、连接、排序和聚合等关系算子展开。本文所说的执行代价，是完成一个算子预计需要的时间和计算、内存及输入输出资源，不是货币价格。虽然这些算子的执行代价并不都与数据量成线性关系，但行数、数据字节数、中央处理器（Central Processing Unit，CPU）、内存和输入输出（Input/Output，I/O）等信息通常能够描述其主要成本，执行引擎也能够依据分区和批大小组织计算。当 AI 算子进入数据库工作流后，一条查询需要处理的范围延伸到了外部模型服务。模型服务是持续接收请求、在图形处理器（Graphics Processing Unit，GPU）上运行模型并返回结果的程序。数据库筛出的记录还需要经历请求构造和文本词元化，也就是把文本转换成模型能够处理的词元（token）；图像则需要读取、解码和缩放。随后，请求被提交到模型服务并等待 GPU 推理，结果完成后再返回数据库执行链。本文把这段从数据库数据形成模型请求，到模型完成计算并返回结果的过程称为外部 AI 数据执行链路。

第一个问题是，AI 操作的处理需求不再只由数据库记录数量决定。本文把一条请求或一组请求预计需要完成的处理称为工作量（work）。文本工作量可以用输入和预计输出词元数描述，图像工作量则可能包括图像读取、解码、缩放和模型计算。同样是一条数据库记录，短评论与长文档的工作量可能相差很大。因此，数据库记录仍然负责标识输入数据和对应结果，但仅凭记录数量难以完整描述 AI 操作带来的处理需求。具体采用哪些工作量特征、怎样形成执行批次以及如何通过实验验证，在后续研究内容和研究方案中展开。

当评论分类、新闻摘要和工单分类等查询并发执行时，数据库输出的记录还可能分别属于不同的 AI 操作。此时，一条记录只有与所属查询和具体 AI 操作结合，才能确定它进入模型服务后要完成什么任务。数据在数据库中的输出顺序或物理相邻关系，并不天然表示这些任务具有相同语义或相近处理代价。这使数据库到模型服务之间不能再被理解为单一、均匀的记录流，而是由多种 AI 处理任务共同形成的执行负载。

第二个问题是，模型服务的容量配置不等于它当前的运行状态。本文把已经提交、但尚未完成的请求，以及按输入词元数、输出上限或图像规模等已知信息计算出的工作量，统称为在途工作（active work）。这里的工作量用于记录已提交工作的规模，并不是代价估计器预测的执行时间。GPU 推理服务通常会配置最大并发请求数、显存限制或最大在途工作量，这些参数规定系统最多允许多少工作进入服务。但是，在相同容量配置下，上游若持续快速提交请求，服务端可能同时存在大量正在执行和排队的请求；上游若受数据库读取、数据准备或提交速度限制，GPU 又可能得不到足够工作。因此，“最多允许多少工作进入”说的是容量上限，“此刻有多少工作正在准备、排队和执行”说的是实际运行状态。只设置一个较大的固定并发值，既不能保证模型服务持续得到有效供给，也可能使大量请求过早进入服务端并形成不必要的等待。

第三个问题是，数据库用户等待的是完整作业，而模型服务直接处理的是单个请求。本文将同一数据库查询，或者任务类型、输入分布和服务要求相近的一组 AI 请求称为一个作业（Job）；工作负载（workload）则用于描述实验中采用的一批作业及其输入分布。一个作业可能包含数百乃至数万条请求。多个作业共享同一组 GPU 服务时，持续产生大量请求的长作业可能使后到的短作业等待明显增加；如果永久为短作业保留固定资源，短作业暂时没有待处理数据时又可能造成资源闲置。因此，数据库 AI 执行既要考虑整体资源利用，也要考虑不同作业的完成时间、相互干扰和服务均衡。

上述问题说明，传统数据库执行层和模型服务层之间存在一个需要单独研究的执行区域。数据库知道每项查询和算子要处理哪些业务记录、这些记录属于哪个作业、还有多少数据尚未处理，以及结果应当怎样写回；模型服务知道哪些请求已经到达、多少请求正在运行或排队、缓存是否紧张以及请求完成得多快。数据库通常看不到模型服务的实时压力，模型服务也不知道数据库端还有多少数据尚未转化为请求、这些请求分别属于哪个完整作业，以及各作业已经完成到什么程度。两端信息没有形成衔接时，单纯沿用传统数据分批方式和静态并发配置，容易出现模型服务供给不足、请求过早堆积和作业间干扰。

基于这一问题，本课题将数据库记录离开传统关系执行部分、形成 AI 请求并进入模型服务之前的区域抽象为 AI 数据执行层（AI Data Execution Layer）。这一抽象用于明确本课题的研究对象：数据库筛选出的业务数据如何转化为外部 AI 执行负载，这些负载如何有序进入模型服务，以及多个数据库作业如何共享有限的模型服务能力。研究围绕 AI 算子的物理执行过程展开，并始终保持算子的逻辑功能和结果对应关系。例如，分类结果仍对应原始评论，文本生成结果仍对应原始输入，向量仍写回对应记录。

图 1 只比较两类算子的基本执行差异。传统数据库算子通常围绕记录规模和 CPU、I/O 等资源组织执行；外部 AI 算子还要把数据库记录转换为模型输入，经过数据准备后提交到一个或多个模型服务实例，并收集返回结果。这里的提交是让请求进入模型服务的等待或执行范围，路由是为新请求选择具体的服务实例。数据库侧还需要知道服务端是否正在排队、是否经常等不到新请求，以及请求完成的速度，才能决定后续工作怎样进入服务。

本课题以逐记录的文本生成、向量化和分类任务为主要场景，研究两个相互关联的问题：一是数据库产生的 AI 执行负载应当怎样描述和组织，才能反映文本、图像等任务在不同处理阶段的实际需求；二是模型服务能力有限且多个数据库作业并发时，怎样依据实际运行状态安排请求提交、服务实例选择和作业之间的资源使用。算子代价信息则返回数据库侧，为关系算子与 AI 算子的执行顺序、物理执行方案和多条 SQL 的运行安排提供参考。

本课题的研究目的，是在保证输入记录、AI 操作和输出结果正确对应的前提下，减少工作量差异造成的执行失衡，在模型服务供给不足与请求过早堆积之间取得平衡，并减轻多个作业共享 GPU 服务时的相互干扰。方案成效将通过正确结果吞吐、排队和尾延迟、资源使用以及完整作业的完成情况共同评价。正确结果吞吐表示单位时间内完成且结果有效的记录数或词元数，尾延迟表示完成最慢的一部分请求所经历的时间。

从理论研究意义看，现有数据库 AI 研究更多关注 AI 算子语义、查询计划、模型选择和调用次数，模型服务研究则主要关注已经到达服务端请求的批处理、显存管理和 GPU 调度。本课题关注两者之间的数据执行层，把“业务记录怎样在特定 AI 操作下形成执行负载”“数据库端任务信息怎样与模型服务运行状态衔接”以及“请求级执行怎样服务于作业级目标”放在同一条链路中考察，从而补充数据库查询与外部模型执行之间的系统研究。

从应用意义看，数据库内置或数据库触发的 AI 操作具有高计算成本和较强工作量异质性，GPU 资源又通常是整个执行链中成本较高的资源。如果上游长期供给不足，会造成模型服务资源闲置；如果大量请求无控制地提前提交，则会增加排队、显存压力和尾延迟；如果多个作业缺少合理的共享机制，还可能出现某一类任务长期受到干扰。因此，建立可描述、可观测和可控制的 AI 数据执行层，有助于提高数据库驱动模型服务的资源使用效率，并改善复杂工作负载下的作业完成体验。

本课题当前研究单一资源管理主体内部多个数据库作业或工作负载类别共享同一模型服务资源池的情形，相关结论聚焦作业级效率、隔离和服务均衡。这里的隔离是限制一个作业对其他作业完成时间和延迟的影响；多租户则指多个彼此独立的用户或组织共同使用系统，多租户资源公平管理属于更广泛的后续问题。

## 2. 国内外研究现状

### 2.1 数据库 AI 算子与语义查询优化现状

随着生成式人工智能和向量检索逐步融入数据分析过程，数据库系统开始直接支持 AI 算子和 AI SQL。Snowflake Cortex AISQL 提供文本生成、嵌入、分类和语义过滤等能力，并围绕昂贵 AI 调用研究谓词重排、模型选择和查询重写[1]。谓词是查询中判断一条记录是否满足条件的表达式，谓词重排就是改变多个判断条件的执行先后。Google BigQuery ML/AI 提供生成文本与向量相关的数据仓库函数[2]，Oracle AI Vector Search 将向量生成与向量检索纳入 SQL 数据处理过程[3]。PostgreSQL 生态中的 pgvector 提供向量类型与向量索引，pgai 等组件则进一步连接数据库数据和外部模型服务[4-5]。

学术界针对语义算子和 AI 查询优化也开展了大量研究。LOTUS 将大语言模型能力抽象为语义算子，在满足指定准确率要求的前提下研究声明式数据处理与优化方法[20]。Palimpzest 从声明式 AI 数据分析角度研究算子选择和执行优化[22]。Abacus 将成本优化思想用于语义算子系统，根据算子代价进行物理执行方案选择[21]。SemBench 从基准测试角度研究语义查询处理系统的统一评价[23]。Galois 进一步面向 SQL 调用大语言模型的场景研究逻辑和物理查询优化[29]。GaussML、NeurDB 和 LEADS 等工作代表将机器学习能力进一步纳入数据库内部执行和自动优化的研究路线[6-9]。InferDB 通过数据库索引近似替代部分在线模型推理[38]，SmartLite 则面向资源受限环境将压缩后的神经网络执行转换为数据库内部操作[39]。这些方法进一步说明，数据库 AI 执行可以沿模型内置、索引近似和外部模型调用等不同路线展开，但它们处理的对象以及对结果质量的要求并不相同。

这类研究主要解决 AI 能力如何以数据库算子的形式被表达、组合和优化。例如，数据库优化器需要判断关系过滤与昂贵 AI 谓词的执行顺序，选择满足质量要求的模型和物理实现，并比较不同语义算子组合形成的执行计划。执行计划是数据库为一条 SQL 选择的算子顺序和具体实现方式。传统数据库可以根据基数、CPU 和 I/O 等信息估计扫描、过滤、连接和聚合的成本，其中基数表示某个算子预计输出多少条记录。AI 语义算子还会产生数据准备、外部模型调用、模型服务排队和 GPU 执行等成本。如果数据库无法估计这部分工作，就很难把 AI 算子与传统关系算子放在同一执行计划中进行比较，也缺少安排多条 AI SQL 执行顺序和并发方式的依据。

数据库 AI 算子研究为本课题提供了应用场景和查询语义基础，也提出了两个相互衔接的问题。一方面，数据库需要获得 AI 语义算子的预计执行时间和资源需求，才能与传统关系算子共同进行计划优化和查询编排。另一方面，逻辑上逐条记录定义的 AI 算子在物理执行时不必为每条记录单独建立 GPU 任务；只要保持输入记录与输出结果的对应关系，外部执行层仍可根据工作量、批处理和模型服务状态组织多个请求共同执行。本课题由此连接数据库侧的算子代价信息与模型服务上游的物理执行过程。

### 2.2 分布式数据执行与异构流水线现状

数据库触发的大规模 AI 操作往往需要在多个 CPU 工作线程、GPU 和模型服务实例之间执行，因此分布式数据执行框架为此类系统提供了重要基础。Ray 通过任务（task）和有状态执行单元（actor）两类抽象支持分布式 AI 应用[10]。任务执行一次计算后结束；有状态执行单元则可以在多次调用之间持续保存队列、计数器或模型实例。Ray Data 面向数据预处理和模型推理提供数据块、批处理、流水线和背压等机制。背压是指下游来不及处理时，上游主动降低数据产生或提交速度，防止待处理数据无限积累。它的 `map_batches` 接口可以指定每批期望包含的行数，也可以使用固定规模或自动伸缩的有状态执行单元池完成模型推理[47]。这里的批大小首先表示数据行数，并不直接等于模型处理这些行所需的计算量。Streaming Batch Model 等工作则进一步研究 CPU 与 GPU 异构阶段之间的数据流、动态分区和容错[18]。

Daft 是面向复杂数据和 AI 工作负载的分布式数据帧（DataFrame）引擎。数据帧以带有列名的表格形式组织数据，并支持对分区数据进行并行转换。Daft 能够使用 Apache Arrow 的列式内存格式组织数据，也可以借助 Ray 执行分布式任务[19]。Arrow 让不同语言和系统按统一的列式布局共享数据，减少阶段之间的格式转换。DuckDB 是可以直接嵌入应用进程的分析型数据库[24]；DataFusion 等使用 Arrow 的数据处理引擎，则采用列式数据和模块化执行方式[25]。NeuStream 等研究进一步关注流式数据处理与深度学习服务之间的流水化协同[30]。

现有数据执行框架已经能够把大数据集拆开处理，在不同 CPU/GPU 资源上放置任务，限制局部缓冲区，并通过背压协调上下游速度。但是，这些框架通常围绕数据块（block）、分区（partition）或批次（batch）进行调度。数据块是连续存放的一组记录，分区是可以独立处理的一部分数据，批次是一次交给某个算子处理的一组记录。框架知道它们包含多少行、多少字节以及需要哪些系统资源，却不会天然知道这些记录经过 AI 算子后将产生多少输入和输出词元，也不知道当前模型服务处于供给不足还是大量排队状态，更不会天然掌握多个数据库作业还剩多少 AI 工作。

这意味着 Daft 和 Ray 等框架适合作为本课题的实现基础，却不能直接替代 AI 工作量组织和作业级调度。普通背压控制的是上下游数据积累速度；本课题还要依据输入词元数、输出上限、图像或帧规模等已知特征计算 AI 工作量，限制已经进入模型服务的工作，并安排不同作业的提交顺序。这里的服务目标是对作业完成时间、请求延迟或按时完成比例等指标提出的要求。Ray 能够运行有状态执行单元，但不会自行依据数据库作业的剩余工作、服务目标和模型端状态决定作业之间的服务顺序。

### 2.3 GPU 模型服务与请求调度现状

GPU 模型服务是当前大模型系统研究的重要方向。已有综述从请求处理、执行优化和内存管理角度整理了大模型推理中的批处理、调度、负载均衡与代价估计问题[40]。Orca 提出的迭代级调度（iteration-level scheduling）能够在模型每生成一轮词元时重新组织请求[11]。vLLM 是面向大语言模型的推理服务引擎，它使用 PagedAttention 按页管理键值缓存（Key-Value Cache，KV Cache）[12]。键值缓存保存模型处理已有上下文时产生的中间结果，避免生成后续词元时重复计算。vLLM 还采用连续批处理（continuous batching）：请求可以在其他请求尚未结束时加入执行，完成后也可以及时移出，而不是等待整个固定批次一起结束。vLLM 的调度配置提供每轮最多处理的序列数和词元数，并支持先来先服务或优先级策略[48]。这些参数限制的是模型服务一次调度迭代中的工作，不表示数据库上游已经提交但尚未完成的全部工作。Sarathi-Serve 进一步缓解提示词预填充（prefill）和逐词生成（decode）之间的相互干扰[13]。预填充一次处理完整输入并建立缓存，逐词生成则在后续步骤中每次产生新的词元。DistServe 和 Splitwise 分别从服务质量和硬件资源匹配角度研究这两个阶段的分离执行[14,41]。Clockwork、Parrot、Llumnix 和 SGLang 等系统则分别研究可预测执行、语义复用、动态服务调度和结构化模型程序运行时[15,17,31,42]。

随着模型服务从单用户环境进入共享平台，公平性和服务隔离也成为重要研究问题。已有研究尝试按照请求实际消耗的模型服务量分配执行机会[16]。作业应当获得的服务量与实际已经获得的服务量之间的差额，本文称为服务差额。FairServe 进一步考虑不同应用和多次模型调用的加权服务与限流[43]；DLPM 同时考虑服务差额与共享提示词前缀的局部性[44]。这里的前缀局部性，是让开头文本相同的请求在时间上相邻并尽量发往同一服务实例，以便复用键值缓存。Autellix 则把累计服务量用于多次模型调用组成的程序级调度[45]。这三项工作目前在项目文献库中均按预印本处理，而且主要位于模型服务或应用运行时层。在更广泛的资源管理领域，主导资源公平（Dominant Resource Fairness）按照每项作业在 CPU、GPU 或内存等资源中占用比例最高的一项衡量其资源份额，用于处理多种资源的公平分配[32]。Pisces 研究多租户存储中的性能隔离与资源共享[33]，数据库领域也研究了多租户事务处理中的公平调度[34]。Themis、Tiresias 和 Pollux 则分别从作业完成体验、已获得服务量和满足资源效率目标的有效处理进度等角度研究 GPU 集群中的多作业调度[35-37]。

然而，模型服务中的调度器通常只能够处理已经进入模型服务的请求。对于一个来自数据库的大规模 AI 作业，模型服务并不知道还有多少数据库记录尚未完成数据读取和请求构造，也无法直接判断不同请求属于哪些完整的数据库查询任务。模型服务内部调度解决的是“已经收到的请求怎样执行”，而数据库 AI 数据执行层还需要回答“哪些请求现在应该进入模型服务”。二者具有明显的上下游关系。

此外，将所有数据库请求提前推入模型服务并依靠模型服务内部调度，也会使上游失去一部分控制能力。已经进入服务端排队的请求占用了队列和缓存资源，并且对不能中途暂停的模型请求而言，上游很难再改变其执行顺序。因此，即使服务端具有成熟的连续批处理，上游仍然需要决定应当保持多少工作处于在途状态，并在多个数据库作业之间控制新请求的释放顺序。本文所说的状态感知提交，是根据当前数据准备进度、模型服务排队和运行情况以及作业完成进度安排新请求，而不是只依赖运行前设定的固定并发数。

### 2.4 当前研究存在的问题

综合上述研究，数据库 AI 算子、分布式数据执行和 GPU 模型服务已经分别形成了较丰富的方法，但它们之间仍有两类衔接问题没有得到充分处理。

一类问题发生在数据组织阶段。前文介绍的数据框架使用数据块、分区或按目标行数形成的批次完成数据切分和并行执行[18-19,47]，模型服务则对已经到达的请求进行迭代级或连续批处理[11-12]。这些机制各有明确作用，但没有直接回答数据库记录在到达模型服务前应该怎样按 AI 处理需求组成请求。AI 执行成本还受到输入词元、生成长度、图像准备、张量大小和模型阶段等因素影响。张量是模型用于表示输入和中间结果的多维数值数组。即使能够按照工作量形成较均匀的批次，大规模改变记录顺序也可能破坏共享提示词前缀或其他有利的数据局部性。数据局部性表示相关记录在处理顺序或服务实例上保持接近，从而有机会复用缓存或减少数据搬移。因此，数据库记录怎样转换为 AI 工作量，以及工作量均衡和数据局部性在不同模型服务压力下怎样取舍，仍需进一步研究。

另一类问题发生在请求进入模型服务之前。前文介绍的模型服务内部调度、多客户端服务量分配和 GPU 集群作业调度，分别处理已经到达的请求、客户端之间的服务差异或集群资源分配[16,35-37,43-45,48]。数据库上游面对的是另一段工作：还有多少记录尚未形成请求，哪些作业正在等待，以及模型服务此时实际处于排队、运行还是暂时空闲状态。固定并发上限不能反映这些变化；在多个作业共享模型服务时，预先分开可提交空间容易留下空闲，完全共享又可能使长作业持续影响短作业。现有研究尚未充分把数据库作业进度、模型服务状态和上游请求释放联系起来，以同时考察总体效率、作业完成时间和服务均衡。

数据库优化器还需要获得 AI 语义算子的成本信息。已有学习型代价模型研究表明，平均预测误差较低并不等于能够选出实测更快的执行计划[26-28]；CONCERTO 也说明，并行执行中的阶段结构和资源竞争会影响代价估计[46]。因此，代价估计既要检查执行时间和资源需求的预测误差，也要检查它能否正确排列结果含义相同的候选计划，并最终改善数据库选择的执行方案。经过独立验证的预计执行时间和预计剩余执行时间还可以作为前两项研究的补充信息，但数据组织与上游调度本身不以获得这些预测为前提。

据此，本课题研究分阶段工作量组织、固定容量下的上游调度，以及为数据库计划比较提供支持的 AI 算子代价信息。

图 2 进一步概括本课题与相邻系统层次的关系。数据库侧掌握记录、查询、作业以及输入输出要求，模型服务侧负责已经到达的请求怎样在 GPU 上执行，并能够观测排队、运行、缓存和完成情况。两侧信息目前没有自然对应起来：数据库记录尚需转换为能够反映 AI 处理需求的工作描述，模型服务的实际状态尚需与数据库作业进度联系起来，多个作业同时提交时也需要共同安排提交顺序和服务实例。本课题的两项研究内容正是围绕这三方面联系展开。

## 3. 研究目标与研究内容

### 3.1 研究目标

本课题拟面向数据库触发的 AI 工作负载，构建并评价数据库与模型服务之间的 AI 数据执行层。研究目标是使数据库记录能够按照 AI 处理需求形成工作单元，在预先测得的模型服务能力范围内安排请求提交、服务实例选择和多个作业的运行，并向数据库优化器和工作负载调度模块提供 AI 算子的成本信息。这里的模型服务能力不是泛指 GPU 数量或显存比例，而是当前机器、模型和服务配置下，允许同时进入执行链且尚未完成的请求数量，以及按工作描述计算的工作量规模。

研究不以单一吞吐指标作为目标，而是在结果正确完整的前提下，同时考察资源使用、排队和尾延迟、作业完成时间以及多个作业之间的相互影响。各方法将在相同数据、模型、硬件和计时范围下比较，并进一步说明它们适合哪些工作负载和运行状态。

文本生成是主要验证场景，图像向量化和分类用于检验工作描述、状态观测和作业调度方法能否复用于另一种数据模态。不同模态保留各自的数据准备和模型执行特征，共用数据组织、调度和评价接口。模型执行后端是实际加载模型、接收准备后输入并完成推理的程序，文本和图像可以使用不同后端。

### 3.2 研究内容

本课题包含两项研究内容：分阶段工作量表征与数据组织，以及固定容量下的提交、路由与多作业调度。算子代价信息连接数据库侧的计划优化与外部 AI 执行过程，文本和图像任务用于检验方法能否适用于不同类型的数据。

#### 3.2.1 分阶段工作量表征与数据组织

如第 2.2 节所述，现有数据框架可以按数据块、分区或目标行数形成批次，但这些单位没有直接表达每条记录对应的 AI 处理需求。在第一章定义的语义请求基础上，本项研究进一步描述请求的物理执行特征。本文把保存这些信息的结构化记录称为工作描述（WorkDescriptor）。每份工作描述保留查询、AI 算子、作业和原始记录的身份，并记录词元规模、数据字节、图像准备量等与处理需求有关的信息。多个查询的请求交错到达时，系统根据模型后端、提示模板、生成参数和结果要求判断哪些请求可以共同执行，再在不拆分完整请求的前提下形成批次。本课题组织的是请求到达模型服务之前的工作，已经进入服务的请求仍由模型服务完成内部批处理和 GPU 执行。

对于文本任务，工作量需要反映输入文本规模、可能的输出规模以及模型执行阶段的主要计算需求；对于图像任务，工作量还需要区分数据读取、图像准备、张量构造和模型执行等阶段。不同阶段使用的具体物理单位可以不同，但均需要被映射为结构化、可比较的工作描述。研究将保留不同阶段的工作特征，使后续系统能够选择当前主要受限阶段作为组织和调度依据，而不强行把所有模态压缩成一个工作量数值。

在获得工作量描述之后，需要研究数据库记录怎样形成执行批次。本课题把直接使用运行前已知特征、无需先预测执行时间的方法称为基础数据组织方法。它可以使用输入词元数、输出上限、图像或帧规模、共享前缀和批次工作量上限等信息。数据组织主要涉及三个相互关联的因素。其一是工作量预算，即一个待执行批次应该包含多少 AI 计算工作；其二是工作量均衡，即多个批次或多个模型服务实例之间是否存在明显的计算量偏差；其三是数据局部性，即为了改善工作量均衡而改变记录顺序时，是否破坏共享提示词前缀、缓存复用或其他有利的数据关系。

因此，本项研究并不简单假定“工作量越均匀越好”，而是研究工作量均衡和局部性之间可能存在的冲突。模型服务侧已有工作也表明，前缀局部性收益与服务公平之间需要通过限制每项作业当前能够占用的工作量来进行权衡[44]；本课题进一步考察这一冲突在数据库记录形成模型请求之前怎样表现。当模型服务缓存压力较低时，改善批间工作量均衡可能更重要；当大量请求共享提示词前缀且模型服务缓存接近占满时，保留原有局部性可能获得更高收益。最终需要通过不同工作负载和服务压力下的实验，说明每种组织方法在哪些条件下有效、在哪些条件下不再有效。

第一项研究内容的对象与输出如图 3 所示。原始记录首先被转换为包含阶段工作特征、作业身份和局部性信息的工作描述，再由不同候选组织方法形成批执行请求。基础数据组织方法可以独立完成这一过程。只有当代价估计在独立数据上达到可用水平后，才进一步把预计批次执行时间或资源需求作为可选输入，并与不使用预测的基础方法在相同工作量上限和后续调度条件下比较。研究不预先假定重排序、装箱或加入代价信息一定优于保序组织。

#### 3.2.2 固定容量下的提交、路由与多作业调度

如第 2.3 节所述，模型服务可以限制每轮处理的序列数和词元数，并在服务内部安排已经到达的请求；集群调度系统则关注 GPU 等资源怎样分配给作业。本项研究关注两者之间的数据库上游：工作单元形成之后，下一份工作什么时候进入模型服务、由哪个服务实例执行，以及多个数据库作业同时运行时怎样安排尚未提交的工作。这里的模型服务容量，是指在当前机器、模型和服务配置下，模型服务可以同时接收而尚未完成的请求规模。这个范围可以用未完成请求数和按工作描述累计的总工作量共同表示，并在运行前通过实验测量，不需要先预测请求执行时间。运行期间还需要继续观察实际执行、排队和完成情况，因为相同的配置上限并不意味着模型服务始终处于相同状态。

本课题把只使用运行前容量测量、请求完成通知和实际运行状态的方法称为基础调度方法。研究将比较为各作业预先保留固定份额、让仍有工作可提交的作业共同使用空闲容量，以及结合运行状态选择后续工作等思路。工作释放关注多个作业之间的提交先后，服务实例路由则关注新请求应发往哪个模型服务实例。两类决策都只安排尚未提交的请求，不暂停已经开始执行的模型请求，也不改变模型服务内部的组批和 GPU 执行方式。预计服务时间或预计剩余执行时间只有在独立验证后才作为可选信息加入，并与基础调度方法分别比较。

多作业调度需要同时考察多项指标。完全均匀的资源分配不一定具有最短作业完成时间，总吞吐最大也不代表每个作业都具有良好体验。已有模型服务和集群调度研究分别采用累计服务量、程序级完成时间和减速比等视角描述这种差异[16,35-36,43-45]。减速比是作业并发运行时间与该作业独立运行时间之比，数值越大表示共享资源带来的影响越明显。因此，本课题同时评价总体效率、最差作业完成体验、服务目标违约、作业实际获得的服务量落后于目标份额的程度，以及最长连续未获得服务的时间。当前研究对象是单一资源管理主体内部的多个作业或工作负载类别，相关结论表述为作业级共享与服务均衡。

如图 4 所示，第二项研究内容把各作业尚未提交的请求、模型服务已经接收的工作以及多个服务实例的运行情况联系起来。研究将在预先测得的工作范围内，考察下一条请求什么时候提交、从哪个作业中选择以及发往哪个服务实例，并比较固定分配、共享空闲容量和使用运行状态等不同思路。具体采用哪种作业选择和路由方法，由后续对照实验决定。

#### 3.2.3 AI 算子代价信息与跨模态验证

数据库优化器需要把 AI 语义算子的成本与扫描、过滤、连接等关系算子的成本共同纳入计划比较。本课题拟从执行前可知的工作特征和历史运行数据出发，估计 AI 算子的执行时间、资源需求及其可能波动的范围。对于单条 SQL，这些信息用于比较结果含义相同的算子顺序和物理执行方案；对于同时到达的多条 SQL，工作负载调度模块可以结合各查询的预计成本、预计剩余执行时间和服务目标安排执行顺序与并发方式。这是代价估计在本课题中的主要用途。

工作描述保存输入规模、模型参数、作业身份和数据局部性等运行前已知信息，数据组织和作业记录可以直接使用这些特征。只有当预计执行时间经过独立实验验证后，才将其作为可选的辅助信息：预计批次执行时间或资源需求可以为数据组织提供参考，预计服务时间和预计剩余执行时间可以为作业选择与服务实例选择提供参考。每种加入代价信息的方法都要与只使用已知工作特征、容量测量和实际运行状态的基础方法比较。

在跨模态验证方面，文本生成承担主要研究方法的完整验证，图像向量化和分类用于验证分阶段工作量、作业级状态和共享容量机制能否复用。对于文本特有的共享前缀和生成长度，以及图像特有的解码、缩放和张量准备，分别由模态相关部分处理；共同的数据组织、状态观测、作业记账和实验评价框架保持一致。

## 4. 研究方案与可行性分析

### 4.1 研究方案

本课题计划在现有数据库和分布式 AI 执行框架基础上构建实验系统。PostgreSQL 提供数据库任务和输入数据，Daft 负责数据读取及数据帧执行[19]，Apache Arrow 负责列式数据块表示[25]，工作描述与数据组织模块将数据库记录转换为可执行批次，Ray 提供分布式任务和有状态执行单元[10]。文本任务由 vLLM 模型服务完成生成[12]，图像任务由基于 Ray 的 GPU 有状态执行单元完成模型推理，结果统一收集，并在端到端验证中写回 PostgreSQL 或 pgvector。本文所说的端到端，是从数据库开始读取输入，一直统计到模型结果完成收集或写回的完整过程；具体实验采用哪一个终点，会在实验设置中说明。

系统总体关系如图 5 所示。PostgreSQL 与 Daft 构成统一数据入口，工作描述和数据组织连接到提交与多作业调度，文本和图像在输入适配与模型执行后端上采用不同实现。运行状态快照保存某一时刻的数据准备、模型服务和作业进度信息。图中同时包含已经建立的执行链和计划研究的决策模块，当前完成情况在 4.2 节按实验逐项说明。

图上方的 AI 算子代价估计是一条独立的计划路径。它读取工作描述和历史测量，估计 AI 语义算子可能需要的执行时间和资源，并把结果主要提供给数据库优化器或多条 SQL 的调度，用于比较传统 SQL 算子与 AI 语义算子的组合代价以及候选执行安排。经过独立验证后，部分估计结果还可以作为数据组织和调度方法的可选输入。虚线状态返回表示另一类信息：运行状态快照（RuntimeStateSnapshot）和执行记录（Trace）保存实际发生的排队、运行、KV 缓存、请求完成速度和作业进度，并返回提交与路由模块。前者是运行前或计划阶段的估计，后者是执行过程中采集的事实，两者不会混作同一种信号。图中同时包含已经建立的数据读取、模型调用与结果收集链路，以及后续计划研究的决策模块；当前完成情况在 4.2 节按实验逐项说明。

PostgreSQL 计划用作实验的数据入口和结果存储，记录输入数据、所属作业与最终结果的对应关系。数据库写回主要用于检查结果数量、输入输出对应、重复和遗漏，并在必要时评价向量写回后的检索质量。

Daft 和 Apache Arrow 用于承担数据执行层中的数据读取、列式表示和分区处理。研究计划在 Daft 输出的基础上增加分阶段工作描述（WorkDescriptor），用于连接数据处理结果与后续的工作组织和提交决策。工作描述将保留记录和作业身份，并表示数据读取、输入准备、模型执行和结果处理等阶段的工作特征。文本可采用输入词元、输出规模和共享提示词前缀等信息，图像则考察编码数据、解码缩放、张量和模型执行等信息。最终保留哪些特征，将由各阶段耗时测量和每次只改变一类特征的对照实验决定，不预设一套特征在所有模态中都同样有效。

工作描述进入数据组织器后形成批执行请求（BatchRequest），也就是一次提交给后端、其中包含若干完整且能够共同执行的请求的物理执行单元。候选方法将覆盖固定行数、按工作量预算组批、尽量组织相似工作，以及保留数据原有局部性等思路。研究不预先确定最终算法，而是在模型、GPU 数量、模型服务配置、最大在途工作量和后续调度方式一致的情况下，比较工作量分布、共享前缀保持程度、缓存命中率、吞吐和尾延迟。缓存命中率表示请求成功复用已有缓存结果的比例。当前已完成的五种方法及其参数在 4.2.2 节中交代。

调度部分计划使用 Ray 的有状态执行单元保存各作业尚未提交的工作，并长期维护每个模型服务实例的未完成请求数和按工作描述累计的工作量。每个服务实例能够接收多少工作，将在固定机器、模型、服务配置和代表性工作负载上预先测量；运行环境或负载分布明显变化时重新测量。

各候选方法使用相同的作业队列、容量参数和完成通知，只替换“下一次从哪个作业取出哪份工作”的选择方法。请求提交后相应计数增加，完成通知到达后计数减少。这样可以在其余执行条件不变的情况下比较不同提交方法，也能准确记录请求实际占用模型服务的时间。

数据准备进度、模型服务的排队与运行请求数、请求完成速率和各作业进度将保存在统一的运行状态记录中。服务实例路由模块使用同一份状态决定新请求发往哪里；请求进入服务实例后的内部组批和 GPU 执行仍由模型服务负责。

轻量 AI 算子代价估计以关系算子处理后的预计记录数、文本或图像输入规模、模型配置、外部执行方式和历史测量为输入，输出预计执行时间、资源需求和估计区间。估计区间表示真实结果预计落入的数值范围，用来反映单个预测值的不确定程度。候选方法从解析模型和简单统计模型开始，再根据独立数据上的结果决定是否需要更复杂的模型。PostgreSQL 执行计划中的传统代价值（cost）使用相对单位，不能与以秒表示的 AI 算子时间直接相加。研究将通过历史运行数据把关系算子和 AI 算子的代价校准到可比较的时间与资源指标，或者保留多维代价供优化器按目标进行比较。

代价估计实验将构造两类输入。一类是查询结果含义一致、但关系过滤与 AI 算子顺序或 AI 算子物理执行方式不同的候选 SQL 计划；另一类是包含多条并发 AI SQL 的固定查询清单。系统先逐一实测各候选计划或查询组合的时间和资源使用，再让优化器或工作负载调度模块只依据运行前能够获得的信息作出选择，以比较估计结果与实际执行结果。

实验评价首先检查输入数据、模型参数和输出含义是否一致，结果数量是否完整，以及每条输入能否与唯一结果对应。在此基础上报告正确结果吞吐、作业完成时间（Job Completion Time，JCT）、P95/P99 尾延迟和首词元延迟（Time To First Token，TTFT）。JCT 是作业到达后直到其全部请求完成的时间；P95/P99 分别表示 95% 和 99% 的请求延迟不超过该数值；TTFT 是文本请求提交后等待第一个输出词元的时间。模型服务状态使用正在运行的请求数、排队请求数、排队时间、键值缓存、完成速率和 MFU 解释，其中 MFU 用于辅助判断 GPU 是否得到充分使用。多作业场景还报告减速比、最差作业尾延迟、服务级目标（Service Level Objective，SLO）违约、服务差额和最长连续未获得服务的时间。SLO 是实验为完成时间或延迟预先设定的目标，超过目标即记为违约。Jain 公平指数取值在 0 到 1 之间，越接近 1 表示各作业按所选口径得到的服务越均匀；它只作辅助指标，不代表已经提供资源份额保证。

代价估计分三个层次评价。首先比较 AI 算子预计执行时间、资源需求和估计区间与实测结果的差异；其次在语义等价的 SQL 执行计划之间比较计划排序是否正确；最后评价数据库优化器采用这些代价信息后选出的计划与实测较优计划相比需要多长时间。多 SQL 编排不以配置排序代替系统效果，而是直接报告各查询的完成时间、尾延迟、服务目标和总体资源使用情况。不同采集时间、工作负载、模型服务配置和硬件上的独立数据用于检验估计方法是否能够继续使用。对于前两项研究内容，实验先比较不使用代价预测的基础方法，再在相同条件下分别加入预计批次执行时间、预计服务时间或预计剩余执行时间，最终以实际吞吐、作业完成时间和尾延迟判断这些信息是否带来额外收益。

实验设计包括单项方法对照和完整执行路径对照。单项方法对照在项目自身执行栈内部进行，例如比较数据组织方法时保持调度方式不变，比较工作释放方法时保持数据组织方式和模型服务可接收的工作范围不变，使一次实验只改变一个主要因素。

完整执行路径对照包括两类。一类比较直接静态分片、DuckDB AI 原生执行和项目静态方案从 PostgreSQL 读取到结果收集或写回的完整过程。直接静态分片是提前把记录分给各模型服务实例，再用固定并发提交；原生执行则保留被测系统自己的数据划分、背压和调度方式，只增加统一的数据源、结果收集和指标记录。另一类比较直接提交、Daft 原生执行、Daft 基于 Ray 的原生执行和 Ray Data 原生执行。只有输入数据、模型、输出要求、硬件资源和计时范围一致时才进行性能比较，具体配置、结果和不能直接比较的情况在 4.2.1 节和 4.2.3 节说明。

所有正式实验在开始前确定输入记录、到达时间和输出要求，运行期间不更换；随机种子也保持一致，使随机划分或顺序能够复现。每类配置先进行预热，让模型加载、缓存和运行环境进入稳定状态，预热结果不计入统计。随后交替运行不同候选方法，避免机器温度或后台负载随时间变化时总是影响同一种方法，并保存请求级提交和完成记录、运行状态时序、GPU 指标、作业级记录以及代码和配置版本。小规模实验如果一次性系统初始化开销占主导，只用于能力与正确性检查，不进入持续运行性能排名。只有比较双方使用相同的数据源、完整结果要求、资源配置和计时起止点时，才形成相对性能结论。

### 4.2 可行性分析

本课题已经具备可运行的文本和图像实验链，但不同实验回答的问题并不相同。下面分别交代每组实验的机器、模型、工作负载、比较对象和可以得到的结论，避免把局部阶段测量、静态方案比较和动态方法验证混在一起。

#### 4.2.1 完整数据库路径与工作量描述基础

文本完整路径实验比较三种执行方式。直接静态分片把数据库记录平均分给两个模型服务实例，并由固定并发的超文本传输协议（Hypertext Transfer Protocol，HTTP）客户端通过网络接口提交；DuckDB AI 路径使用 DuckDB 1.5.4 和社区版 `ai` 扩展 0.4.14 执行 SQL 中的 AI 调用；项目静态路径使用 Daft 组织数据，并由 Ray 有状态执行单元按照预先选定且运行期间保持不变的参数提交请求。三条路径都从 PostgreSQL 18.4 读取数据，使用双 RTX 4090 和两个 Qwen2.5-7B vLLM 服务实例。Qwen2.5-7B 是约含 70 亿参数的文本生成模型。实验开启共享前缀缓存，使开头文本相同的请求可以复用已经计算的中间结果。最终结果进入同一 PostgreSQL 结果表，数据库扫描开始到结果表读回完成构成端到端计时范围。

均匀控制组包含 10,570 条 SQuAD 记录。SQuAD 是根据给定文章段落回答问题的数据集，本实验把输出限制为最多 64 个词元，使三条路径使用相同的答案长度要求。直接静态分片和 DuckDB AI 路径在每个服务实例上使用 32 个并发请求；项目静态路径在每个服务实例上最多保留 128 个未完成请求和 65,536 个预计词元工作量，并使用 8 个工作进程，每个进程的并发数为 32。三条路径采用的是各自实验开始前选定的静态配置，因此并发参数不要求相同，但数据、模型、GPU 数量、输出要求和计时范围保持一致。每条路径运行 1 次预热和 3 次交错统计重复。

三次统计运行中，直接静态分片、DuckDB AI 和项目静态路径的端到端时间均值分别为 62.126 s（秒）、62.074 s 和 61.601 s，正确结果吞吐分别为 136.632、136.675 和 137.770 行/秒。答案完全匹配率表示模型答案与标准答案文字完全一致的比例；F1 分数同时考虑答案词项的查准率和查全率，用于允许部分词项匹配的问答质量评价。三条路径的完全匹配率分别为 80.306%、80.265% 和 80.274%，F1 分数分别为 89.381%、89.359% 和 89.368%。DuckDB AI 路径在三次运行的 31,710 行结果中有 3 行没有满足固定输出长度要求，其余两条路径没有出现这类情况。总体上，三条路径的性能和答案质量都很接近。项目静态路径相对于直接静态分片的正确结果吞吐只高 0.83%，不能据此判断项目方案明显更快。该组数据来自 AutoDL 云端 GPU 实验环境中的 PostgreSQL 18.4，仍需在目标 PostgreSQL 18.3 平台复测。

实验还使用 2,048 条受控 ShareGPT 记录和 256 词元输出上限运行了同样三条路径。ShareGPT 是由真实多轮对话整理得到的数据集，不同记录的输入长度差异较大，适合观察非均匀文本负载。每条路径进行 1 次预热和 3 次统计重复，三次统计共处理 6,144 行。直接静态分片、DuckDB AI 和项目静态路径的端到端时间均值分别为 180.332 s、180.416 s 和 116.703 s，原始行吞吐分别为 11.357、11.352 和 17.550 行/秒。不过，这组数字不能用于三条路径的性能排名。后续容量扫描发现，每个服务实例 32 个并发请求只能达到该 ShareGPT 场景已测最高服务吞吐的 52.07%，直接静态分片和 DuckDB AI 路径没有充分向模型服务提供工作；同时，DuckDB AI 的 6,144 行结果中有 4,921 行没有满足统一的固定输出长度要求，只有平均 407.67/2,048 行得到符合该要求的非空结果。因此，这组 ShareGPT 实验只记录不同路径的执行现象和输出差异，不把项目路径较短的运行时间写成相对于 DuckDB AI 或直接静态分片的方法收益。

固定行数不能稳定表示模型工作这一现象来自较早的本地预研。实验使用单张 RTX 5070、Qwen2.5-1.5B（约含 15 亿参数的文本生成模型）和 512 条混合文本记录，其中 ShareGPT 提供多轮对话，BurstGPT 提供根据在线模型服务请求轨迹构造的突发输入。单条输出最多为 16 个词元，固定每 16 行形成一个模型请求。3 次统计运行中，每个批次都恰好包含 16 行，但输入词元与允许输出量之和最小为 474、最大为 6,793，相差约 14.3 倍。该结果只用于说明“行数相同而模型工作不同”，不作为双卡系统的性能结论。

#### 4.2.2 数据组织实验

数据组织实验使用双 RTX 4090 和 Qwen2.5-1.5B。工作负载为 2,048 条多轮 ShareGPT 记录，输入长度为 3～1,486 个词元，目标输出为 1～256 个词元。模型服务开启共享前缀缓存，提交侧固定每个服务实例最多 256 个未完成请求和 65,536 个预计词元工作量，采用 50 ms（毫秒）固定提交等待和最少排队请求路由。比较对象为固定 16 行、保序词元预算、长度对齐、最佳适配装箱和同时限制最大行数的词元预算五种组批方式；每种方式在两种服务部署条件下各运行 1 次预热和 3 次统计重复。

第一种部署条件在每张 GPU 上放置一个模型服务实例，每个实例最多使用约 90% GPU 显存，键值缓存峰值只有 7%～10%。五种组批方式的吞吐为 50.3K～56.3K token/s，其中 K 表示千，token/s 表示每秒处理的词元数。第二种条件在每张 GPU 上放置两个服务实例，每个实例最多使用约 43% GPU 显存，键值缓存峰值达到 98%～100%。此时五种方式的吞吐扩大为 39.4K～50.0K token/s：保留原始记录顺序的词元预算方法约为 50.0K token/s，固定 16 行约为 47.4K token/s，三种需要重新排列记录的方法约为 39.4K～40.4K token/s。重排序方法把原本相邻的相同提示词前缀打散后，共享前缀缓存命中率由低压力条件下的 60%～76% 降至约 6%～7%；保序方法在高压力条件下仍保持约 47%～48%。

这组实验还需要说明两个限制。首先，两种条件同时改变了服务实例数量和每个实例可用的显存比例，所以它比较的是两种完整运行条件，而不是只改变一个缓存数值的单因素实验。其次，在双服务实例条件下，五种策略只达到同协议直接客户端吞吐参照的约 63%～71%。这里的同协议直接客户端使用相同的 HTTP 接口、输入和输出要求，但不经过 Daft 和 Ray 数据执行图，并以固定并发持续发送请求，用于估计模型服务在该请求方式下能够达到的处理速度。当前项目路径中的 65,536 工作量上限把实际未完成请求数限制在 4～22 个，因此 50K～56K token/s 是相同上限下的策略比较结果，不是该硬件的最高吞吐。四服务实例下不设置这一工作量上限的直接客户端又因缓存频繁淘汰而异常降速，也不能拿来当作可靠的服务上限。

图 7 展示了五种组批方式在上述两种运行条件下的吞吐和共享前缀缓存命中率。它说明改变记录组织方式可能同时改变批间工作量和数据局部性，方法的相对表现会随整体服务部署和缓存使用情况变化；它不能说明某种组批方法在其他模型、显存配置或工作负载中仍然保持相同排名。

#### 4.2.3 容量测量、运行状态与原生执行路径

容量扫描使用双 RTX 4090、两个 Qwen2.5-7B vLLM 服务实例和 2,048 条 ShareGPT/BurstGPT 记录。实验关闭共享前缀缓存，单条输出最多 256 个词元。提交侧固定每个服务实例最多 256 个未完成请求，只把每个服务实例的预计在途词元工作量依次设为 16,384、24,576、32,768、49,152、65,536、81,920、98,304 和 131,072；每档运行 1 次预热和 3 次统计重复。65,536 档的平均吞吐为 8,030 token/s，也就是模型服务每秒处理 8,030 个输入和输出词元，达到最高已测均值 8,211 token/s 的 97.80%；增加到下一档 81,920 后只提高 0.92%，P99 请求延迟却由 36.78 s 增至 38.71 s。本文把吞吐已经接近已测最高值、继续增加在途工作只能带来很小提升的位置称为近饱和点。按实验前确定的选择方法，65,536 是这一环境中达到至少 95% 已测最高吞吐的最小工作量上限，不是可以跨环境沿用的常数。

相同的 65,536 上限并不保证运行时同样繁忙。另一组实验保持硬件、模型、每个服务实例的请求数和工作量上限不变，只改变请求到达节奏。在输入供应充足的条件下，在途工作能够接近上限，MFU 约为 35%；当请求到达间隔放慢到模型服务经常等不到新请求时，观测到的在途工作峰值约为 18.7K～19.4K，只达到 65,536 的约 29%，MFU 约为 7.07%。29% 指整次运行中的峰值，不是平均值。这说明“配置允许多少工作”与“当前实际上有多少工作”是两个不同问题。

同环境原生执行路径观察进一步说明，排队少不一定表示执行更好。该实验使用双 RTX 4090、两个开启共享前缀缓存的 Qwen2.5-7B 服务实例、2,048 条受控 ShareGPT 记录和 256 词元输出上限。直接有界客户端、Daft 原生提示词函数、Daft 的 Ray 执行方式和 Ray Data 官方 HTTP 处理图均进行 1 次预热和 3 次统计运行。四条路径的作业完成时间分别为 95.49 s、98.36 s、101.53 s 和 478.66 s；Daft 两条路径的平均排队请求数约为 783 和 742，平均服务排队时间约为 37.5 s，而当前 Ray Data 配置的平均运行请求数只有 17.3、排队请求为 0、MFU 为 11.2%。因此，Daft 路径表现为提前提交了大量请求，Ray Data 当前配置则没有持续向模型服务提供足够工作。这里描述的是这些公开执行图和选定参数下的外部现象，不能据此归因某个框架内部算法，也不能写成 Ray Data 在其他配置下普遍较慢。

#### 4.2.4 多作业共享与状态感知工作释放

四作业实验使用双 RTX 4090、两个开启共享前缀缓存的 Qwen2.5-7B 服务实例。一个包含 512 条记录的短作业在 0 s 启动，三个各含 512 条记录的长作业在 5 s 启动。每个服务实例最多允许 128 个请求处于已经提交但尚未完成的状态，这些请求的预计词元工作量合计不超过 65,536。提交一条请求会占用一个请求位置和与其预计词元数相应的工作量空间；请求完成后，两部分空间都重新用于后续请求。

静态分区为每个作业分别保留 32 个请求位置和 16,384 个预计词元工作量。即使某个作业暂时没有请求，它所保留的空间也不能由其他作业使用。共享方式不再把总容量长期切成四份，四个作业分别保留自己的等待队列，共同使用每个服务实例的 128 个请求位置和 65,536 个预计词元空间。每当有空间空出，调度器从各作业的等待队列中选择下一条能够放入当前剩余空间的请求。该实验使用等权差额轮转选择作业：它按照预计词元数记录各作业已经获得的提交机会，而不是简单地让每个作业每次提交一条请求。这样可以避免只比较请求数量而忽略长短请求的工作量差异。两个方案都进行 1 次预热和 3 次交错重复，总任务、总容量和模型配置相同。

共享方式相对于静态分区使整组服务吞吐由 11,863 提高到 12,892 token/s，增加 8.68%；整组作业完成时间由 143.33 s 降至 131.91 s，缩短 7.97%；MFU 由 38.20% 提高至 46.76%。按三次重复均值，短作业和三个长作业的完成时间相对于静态分区分别缩短 72.23%、8.28%、20.24% 和 52.66%，但收益差别很大。两个长作业在共享方式下仍比它们单独使用四分之一保留份额时慢 29% 和 14%，所以共享方式没有保证每个作业都达到其保留份额下的独立运行效果。

公平性指标也必须使用相同参照。把每个作业在并发运行中的完成速率都除以它独占完整资源时的完成速率后，Jain 指数由静态分区的 0.988 降至共享方式的 0.876；直接按实际完成工作量计算的 Jain 指数则由 0.960 降至 0.923。另一个 0.998 是将静态分区与“作业单独使用四分之一份额”比较得到的数值，分母不同，不能与共享方式的 0.876 写成同一指标的前后变化。上述结果说明共享未使用份额改善了总体效率和四个作业的完成时间，但作业之间的收益分配更不均匀。

项目还完成了一组两作业工作释放实验。后台长作业在 0 s 启动，前台短作业在 5 s 到达，两者各含 512 条多轮 ShareGPT 记录；硬件仍为双 RTX 4090 和两个 Qwen2.5-7B 服务实例，每个服务实例保持 128 个请求、65,536 个预计词元工作量的上限。实验比较静态分区和四种共同使用模型服务总提交容量的工作释放方法，每种方法运行 1 次预热和 3 次统计重复。共享先来先服务按照请求进入等待队列的先后提交；差额轮转根据预计词元数记录各作业已经获得的提交机会；外部虚拟词元计数（Virtual Token Counter，VTC）风格调度用累计词元服务量近似作业已经获得的资源，优先选择累计值较小的作业；项目工作释放方法则根据作业当前是否仍有可执行工作、已经使用的工作量和累计服务差额选择下一份工作。实验记录了前台作业的服务目标，但当前项目方法没有用这一信息参与打分；各模型服务实例的排队和完成速率也只被采集，没有参与这组决策。因此，这组实验比较的是几种作业进度和服务量记账方法，还不能代表后续计划研究的完整状态感知方法。

四种共同使用模型服务总提交容量的方法，其吞吐为 12,103～12,441 token/s，差异不到 3%；项目工作释放方法在这四种方法中的前台作业完成时间和 P99 最低，分别为 57.0 s 和 50.3 s，但静态分区仍达到更低的 36.2 s 和 29.2 s，并且前台服务目标违约率为 0。静态分区的总体吞吐为 9,508 token/s，项目方法为 12,393 token/s。该结果说明当前项目方法在这组实验中提高了总体吞吐，但没有像静态分区那样充分保护后到达的短作业，不能写成状态感知方法已经优于所有参照方案。

#### 4.2.5 AI 算子代价估计的前期实验与图像跨模态基础

现有代价估计实验先从 AI 算子的一个物理执行参数入手，考察估计方法能否区分不同在途工作量上限对应的执行时间。实验固定使用双 RTX 4090、两个开启共享前缀缓存的 Qwen2.5-7B vLLM 服务实例、每个服务实例 256 个请求并发上限、8,192 词元组批预算和 50 ms 固定提交等待，不包含数据库写回。唯一变化的是每个服务实例允许的预计在途词元工作量，四个候选值为 32,768、49,152、65,536 和 98,304。20 个执行情境由 5 类输入分布、2 种记录数和 2 种输出上限组合而成：短提示词、长提示词、共享前缀较集中的 ShareGPT、多轮 ShareGPT 和代理程序轨迹型提示词，分别取 128 或 256 条记录，输出上限取 64 或 256 个词元。

这里测量的是一条已经实现的文本 AI 算子执行链：从 PostgreSQL 读取数据，经 Daft 和 Arrow 形成输入，按照词元预算组织工作，再由 Ray 有状态执行单元提交给两个 vLLM 服务实例，直至收集完整结果；实验没有计入数据库写回。每个“执行情境×候选值”先运行 3 次；对波动较大的 63 个组合补充到 6 次，另外 17 个组合保持 3 次，共得到 429 条用于统计的运行记录。留一执行情境验证每次留下一个输入分布、记录数和输出上限组合及其四个候选值，使用其余十九个情境拟合估计器。当前混合模型先根据固定开销、提示词元总量以及“记录数×单条输出词元上限”得到一个基础时间，再用一种更稳定的线性回归方法，即岭回归（Ridge regression），结合在途工作量上限、组批和服务配置等运行前信息修正这个时间。岭回归会限制某一项输入特征对预测结果的影响被放得过大，可以减轻样本数量较少、多个配置特征相互关联时估计容易波动的问题。

混合模型在四个候选值之间的两两排序准确率为 0.808。该指标把同一执行情境中的四个候选上限逐对比较，统计预测的快慢关系与实测一致的比例。在 20 个留出情境上，模型所选上限相对于实测最佳上限的中位性能损失为 0，情境等权平均损失为 2.90%，最坏情境为 14.72%。这里的性能损失，是所选上限的实测执行时间比该情境中最快上限多出的百分比。14.72% 只略低于实验前采用的 15% 最坏情境参考值，而且补充重复是针对高波动组合选择性进行的。因此，这组结果只能说明估计方法在当前文本环境下能够初步区分四种在途工作量上限的执行代价，不能说明换到新硬件、新模型或新工作负载后仍然可靠。

图 10 同时比较六种估计方法的时间预测偏差、对四种在途工作量上限的排序，以及选错上限造成的实际性能损失。六种方法包括训练数据整体均值、按固定开销和词元规模计算的解析模型、按相似运行配置查找历史中位时间、岭回归、LightGBM，以及解析估计与岭回归残差修正组成的混合模型。残差是解析模型预测时间与实测时间之间还没有解释的差值，岭回归用于继续估计并修正这部分差值。LightGBM 是把多棵决策树组合起来进行预测的机器学习方法。对每种方法，20 个留出情境和每个情境中的 4 个候选值共同形成 80 组“实测时间均值与预测时间”对。中位绝对相对偏差先计算每组预测与实测相差的比例，再取 80 组结果的中位数；平均绝对误差则直接计算预测时间与实测时间相差多少秒，再取平均值。解析模型的中位绝对相对偏差为 17.8%，岭回归的平均绝对误差为 3.18 s，分别是六种方法中的最低值。混合模型的相应结果为 30.1% 和 4.06 s，因此它不是这组实验中单点时间预测误差最小的方法，但它对四种候选上限的排序和最终选择结果较好。该实验只验证一个 AI 算子在四种外部执行参数下的代价差异，没有加入传统关系算子、完整 SQL 执行计划或多 SQL 编排，也没有把预测结果接入数据组织和多作业调度。因此，当前结果不能说明数据库优化器已经利用这些估计改进执行计划，也不能说明前两项研究内容已经因代价信息而获得额外收益。

图像准备阶段测量使用单张 RTX 4090、PostgreSQL 18.4 中的 5,000 张 COCO 图像和 CLIP ViT-B/32。COCO 是包含日常场景图像及标注的公开数据集，CLIP 是把图像和文本映射到同一向量空间的模型，ViT-B/32 是本实验采用的具体模型结构。张量快速路径把解码后的图像直接转换为模型输入张量，减少不必要的中间格式转换。对于批大小 16、64 和 256，每张图像的解码、缩放和张量构造中位时间为 4.44～4.78 ms；GPU 有状态执行单元完成数据搬移、模型前向计算和结果归一化的中位时间为 0.143～0.346 ms。模型前向是模型根据输入计算图像向量的过程，归一化则把输出向量调整到统一尺度。图 11a 对每次重复先计算“CPU 准备时间/GPU 执行时间”，再取 30 次重复的中位数，三个批大小分别为 13.9、31.0 和 29.5 倍。若直接用两阶段各自的中位时间相除，结果分别为 13.8、31.2 和 29.5 倍；两种统计顺序不同，但都说明图像准备和模型执行需要分阶段记录。每个配置还包含 5 次预热。该测量不包含 Daft/Ray 调度和 pgvector 写回，不能据此确定整条图像执行链的唯一瓶颈。

在双 RTX 4090 上，项目还使用 CLIP ViT-B/32 和约 12 万张图像比较了项目静态执行路径与 Ray Data 原生执行图。两条路径使用相同的 64 图批大小、两个 GPU 模型进程和相同的 L2 归一化输出。L2 归一化是把每个向量缩放到长度为 1，使后续相似度比较采用一致尺度。两条路径分别在 8 个和 16 个 CPU 工作进程下运行 1 次预热和 3 次统计重复。第一轮同 CPU 比较中，项目路径的算子完成时间在 8 个 CPU 进程下低 12.8%，在 16 个 CPU 进程下低 15.1%；另一轮同规模重复得到 10.0% 和 18.5% 的同向结果。因此，第一轮同资源比较支持的差值约为 13%～15%，后一轮重复保持相同方向，也显示不同批次的幅度会波动；曾由 CPU 配置不一致得到的 45.7% 差值不纳入结论。两条路径的平均 GPU 忙碌比例都只有约 6%～10%，说明该实验仍受图像准备和数据供给影响；它没有加入根据实时状态改变提交方式的策略，所以不能写成动态调度收益。该实验也没有执行 pgvector 写回和检索质量评价。

图 11 给出图像路径中三个会影响上游提交的阶段现象。前两部分来自 30 次重复测量，最后的在途窗口扫描只进行了一次筛查，用于选择后续实验范围，不能作为动态方法的性能证据。

读图说明：图 11a 的纵轴是同一次重复中 CPU 准备时间与 GPU 执行时间的比值，圆点是 30 次比值的中位数，误差线所示的四分位距（Interquartile Range，IQR）覆盖中间 50% 的结果。图 11b 比较张量已经位于 GPU、张量位于不可换页的半精度主机内存，以及张量位于普通单精度主机内存三种输入表示。主机内存是 CPU 一侧的内存；不可换页表示这块内存保持在物理内存中，便于向 GPU 传输；半精度 FP16 和单精度 FP32 分别使用 16 位和 32 位浮点数保存每个数值。PCIe 是 CPU 主机与 GPU 等设备之间传输数据的连接通道，但图中的差异还包含数据格式转换和复制次数变化，不能全部归因于 PCIe 带宽。图 11c 的“最大在途批次数”是已经提交但尚未完成的批次上限：窗口过小时模型进程等不到足够工作，继续放大后吞吐不再上升而等待增加。该部分只进行了一次参数筛查，用于确定后续实验需要覆盖的提交窗口范围；它没有比较两种动态方法，也不能证明某种状态感知方法已经有效。

图像四作业实验使用同一双 RTX 4090、CLIP 模型和四段互不重叠的 COCO 数据：2,000 张图像的短作业在 0 s 到达，三个各 3,000 张图像的长作业在 0.5 s 到达。Daft 内置图像函数和 Ray Data 原生执行图都进行了四个独立作业与四作业并发的 1 次预热和 3 次统计运行。Daft 的短作业并发完成时间相对于独立运行增加 1.76%，三个长作业增加 112.73%～218.77%；Ray Data 的短作业增加 9.56%，三个长作业增加 6.05%～64.10%。这些数值只在同一执行图内部比较，说明图像作业的相互影响会随作业和执行方式变化，不能拿两条路径的绝对完成时间作框架排名。

项目图像路径还完成了分阶段工作描述和只记录、不驱动动作的状态快照接入。24 次运行全部完成预期结果，3,114 个提交或完成事件的状态快照均在 50 ms 有效期内，构建平均耗时 0.141 ms。四作业下，带状态记录的现有共享协调方式与静态分区的整组完成时间分别为 5.691 s 和 5.635 s，相差 0.98%，没有达到 5% 的改善幅度。该实验支持的是状态可以低成本采集，并不支持“状态感知图像调度已经提高性能”。

从整体系统条件看，当前已经建立 PostgreSQL、Daft/Arrow、Ray、文本或图像模型执行器和结果收集之间的可运行链路，并能够记录工作量、作业身份、提交与完成事件、模型服务状态和 GPU 指标。现有实验已经把主要研究现象和静态比较对象测量出来；AI 算子代价能否与关系算子代价共同支持 SQL 计划优化和多 SQL 编排、状态信息能否稳定改善工作释放，以及图像动态提交和 pgvector 写回后的检索质量，仍需后续实验回答。

## 6. 预期成果

本课题预期形成一套不依赖执行时间预测也能运行的分阶段工作量描述和数据组织方法，给出文本与图像任务的工作特征、批次组织接口和实现，并通过对照实验说明工作量均衡与数据局部性分别在什么运行条件下影响执行效果。

预期形成一套基于 Ray 的上游提交、服务实例路由和多作业协调组件。组件能够在不依赖代价预测时使用容量测量、完成通知和实际运行状态安排尚未提交的工作，并支持在相同模型服务能力范围内替换不同的工作选择和路由方法。配套实验将给出总体效率、作业完成时间、尾延迟和服务均衡之间的实际取舍。

预期形成面向数据库优化器和工作负载调度模块的轻量 AI 算子代价估计组件，以及结果含义相同的候选 SQL 计划和多 SQL 运行案例。相关成果包括估计接口、模型实现、预测误差、计划排序结果，以及数据库采用代价信息后实际得到的查询完成时间和资源使用情况。经过验证的代价信息还将分别接入数据组织与多作业调度实验，用于判断它们能否在两项基础方法上带来额外收益。

预期完成一套基于 PostgreSQL、Daft、Apache Arrow、Ray 和 GPU 模型服务的可复现实验系统。系统支持文本生成、图像向量化和分类，并为音频、视频等任务保留阶段工作描述和执行后端接口。项目将整理实验代码、配置、固定输入清单、请求级运行记录、原始统计结果、数据图和复现说明，使各项结论能够追溯到具体实验条件和数据。
