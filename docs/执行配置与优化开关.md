## 当前默认与选择顺序

| 要选择的行为 | 当前树源码默认 | 可选入口及含义 |
|---|---|---|
| 普通文本 Filter records 的模型提交 | `profile=None`解析为`mode="sync"` | `create_records_core(..., profile=...)`可显式选`async`；不因此变成多算子记录级链 |
| 有限多算子链的推进粒度 | `execution="fused"` | `record_local_sections`允许合法记录的后继继续推进；Extract仍保留完整关系屏障 |
| 请求数窗口是否运行时调整 | 固定；`admission=None` | 普通records可显式选`admission.kind="resource_feedback"`，每查询从1起；完整链owner的参数以其Python API为准 |
| 链的就绪任务次序 | `ready_order="fifo"` | 可选`round_robin`或带明确参数的`successor_first`；通用MethodDriver自身默认轮转，不能混用默认口径 |
| 链的token在途限流 | `token_budget=None`，关闭 | 显式`ChainTokenBudget`启用W安全上限；不是按token组成提交批次 |
| 每批token B组批 | `prepared_batching=None`，关闭 | 可显式启用同步fused单Filter／Map或异步记录链的token组批；rolling也可不设B，保留完整请求和IPC字节保护。同步受逻辑字节额度，异步另受请求许可。见[同步接口](../code/src/execution_provider/adapters/README.md#prepared-request-batching)和[异步接口](../code/src/execution_provider/adapters/README.md#optional-async-record-token-batches)；与W不同 |
| worker审计副本提前释放 | `release_completed_audit=False` | 仅共享fused链worker支持；记录级明确拒绝 |
| 历史PG Ray Map的物化／准备（已归档） | `payload_backend="daft"`、`preparation=None` | 可选Arrow物化、准备分段、调用方拥有的HTTP worker池；各有独立条件 |
| 历史Animals Q7图像URI保留 | 原入口`media_retention_bytes=0`，关闭 | 旧runner已归档；共享媒体组件保留，但不能把原CLI参数传给当前原生VLM入口；不等于模型结果／KV缓存 |

先选实际前端和执行路径，再选容量、生命周期和待比较的一个策略。研究优先验证记录级推进，不表示以上全局默认已改变。
固定行数、固定并发、动态并发、token组批和token限流是不同选择，不能只看“async”或“token”字样判断行为。

## 普通文本 records：同步、异步与动态策略

源码：[Core工厂](../code/src/execution_provider/adapters/lotus_records_core.py)、[profile解析](../code/src/execution_provider/adapters/records_profile.py)、[反馈配置](../code/src/scheduling/submission_control/feedback_options.py)和[请求策略](../code/src/scheduling/submission_control/request_scan.py)。
Python入口为`create_records_core`；profile、IPC／capacity、组批、rolling及resident等关键字以链接的工厂定义为准，不另维护一份函数签名。
普通Movie配置用`core_profile`；resident session／维护plan用`profile`。这是配置字段差别，不是两套算法。
低层异步actor只提供非阻塞`try_submit_*`与poll／ACK，旧阻塞RPC已退役；现用owner的提交方法返回awaitable，同步模型调用保留。
本批没有改变C／R、字节声明或vLLM参数。[接口与CPU范围](../experiments/results/diagnostics/records_runtime_refactor_20261104/README.md#retired-blocking-async-rpcs)记录27项纯内存通过，以及87ce实际IPC的15通过／1项测试同步失败；d6abc只补结果就绪后触发关闭的同步点，该单项已一次通过，未改生产或放宽断言，其余15项未重跑。
普通Movie的`backend="semloom-local-model-core"`默认同步；兼容入口`"semloom-local-model-core-async"`显式选择异步。
切换后端名仍须提供合法资源，不能通过别名绕过profile／IPC容量检查。

| 准确参数／值 | 默认 | 作用、何时考虑使用 | 条件与效果 |
|---|---|---|---|
| `profile.mode`: `sync`／`async` | `sync` | 同步模型核每次完整返回；异步owner支持多个独立最终结果在途，适合检查持续供给 | 两者都要求prepare/model批行数为1；异步不自动调窗。[E1](#e1)不是普通单Filter入口的通用加速证据 |
| `profile.max_inflight` | 固定路径取解析后的请求额度；请求反馈从1起 | 显式固定当前查询请求数上限C | 正整数且不超过owner硬请求额度R；显式budget模式须给C或admission。async的C不按引擎每轮`max_num_seqs`截断，仍受Core／actor／IPC及字节结果额度保护。`"auto"`只取声明请求额度，不做性能搜索 |
| `profile.stage_timing` | `False` | 需要定位准备、提交、等待和收集时开启计时 | 有观测成本；不提供GPU内部瓶颈判定 |
| `profile.admission` | `None` | 显式`{"kind":"resource_feedback", ...}`启用反馈；需要检查压力保护或有限探索时使用 | 只支持async；未传入就不创建该反馈采样任务，不自动启用W或B |
| `async_limits` | `None`，从owner或完整独立budget推导 | 高级Python／普通Movie配置中限定IPC输入、结果、命令及控制槽 | 按完整owner容量校验，不能只绑定动态初始C；完整独立budget支持部分IPC覆盖，显式IPC可小于硬R。详见[容量](#budgets) |

普通records选prepared／rolling传输时须显式async且`stage_timing=False`；B是可选组包条件，
非rolling批模式不接请求admission，rolling可在有B或无B时显式选择当前请求反馈及准备模式，见[Movie入口](../code/src/experiments/movie_matrix.README.md#record-token-batch-entry)。
请求反馈使用 `ResourceRequestConfig`，与非rolling的 `batch_feedback` 分开；后者继续使用
`SupplyFeedbackConfig` 及批反馈的测量实现。
公共配置类型位于 [feedback_options.py](../code/src/scheduling/submission_control/feedback_options.py)，
共用供给状态和成对工作量计量位于 [feedback_work.py](../code/src/scheduling/submission_control/feedback_work.py)。
现代请求不再为取配置／数据而加载批策略；现用配置数值与策略规则没有改动。
当前请求参数如下：

| `profile.admission`字段 | 默认 | 作用与条件 |
|---|---|---|
| `kind` | 无；显式传`"resource_feedback"`才启用 | 只支持async，每个查询从一个请求开始 |
| `poll_interval_s` | 0.25 | 读取间隔；须不大于测量窗口和来源年龄上限 |
| `window_s` | 1.0 | 工作量测量区间，秒；不是来源时钟或总探索期限 |
| `max_sample_age_s` | 1.0 | 来源可接受年龄，秒；重复帧不刷新原时间 |
| `min_samples` | 16 | 一个有效性能测量区间至少需要的已完成请求数量；不作为资源试探的起步完成数 |
| `measurement_windows` | 3 | 比较使用的测量区间数，至少为2 |
| `min_gain` | 0.03 | 工作量可比较时的增益判断值，不是已证明收益 |
| `min_remaining` | 0 | 0不添加正数尾部工作预算；正值由调用方显式选择 |
| `exploration_s` | `None` | 可选探索时间预算，不改变原查询截止和清理责任 |
| `max_changes` | `None` | 可选调窗次数预算，耗尽不表示找到了硬件平台 |
| `allow_exploration` | `True` | False停止性能试探，压力响应继续 |
| `require_memory_feedback` | `False` | True要求模型actor可见cgroup v2的有效内存区间才允许增长；不发放RAM或限制RSS |

请求许可来自实际owner／Core／IPC／结果预留，缺少或过期信号保持未知；物理CPU/GPU读数只参与
已获许可范围内的可逆试探位置，不推导可用容量或性能保证。GPU归属从实际模型actor采样，
当前请求配置不接受调用方指定的GPU列表。

旧请求策略、两种具名配置与跨查询提示／请求缓存已退出现用入口。

## 有限算子链：fused、记录级、后继选择与W

入口：[SemLoomRecordChainCore](../code/src/execution_provider/adapters/lotus_record_chain_core.py)。这是Python API；
PR73的四case CLI只是固定16行M→M→F验收入口，不是任意链的自动选参器或完整SemBench运行器。

| 准确参数 | 默认 | 作用／开启时机 | 条件与已有证据 |
|---|---|---|---|
| `execution` | `"fused"` | `record_local_sections`在必要前驱已成功解析后推进该记录后继；用于检验跨阶段等待 | fused要求`cpu_workers=max_active_batches=1`；record要求两个batch rows都1。Extract仍完整装配。有限功能见[E1](#e1)、[E3](#e3) |
| `ready_order` | `"fifo"` | `round_robin`轮转；`successor_first`在源任务与后继同时就绪时偏向后继 | 自定义ready仅同部署同角色F/M，拒绝fused、Extract及角色切换；已在Core中的任务不被此项重新排序 |
| `successor_first` | `None` | 选择后继优先时提供`SuccessorFirst(max_burst, max_wait_s)` | 两字段均须显式正值；连续后继次数和最大等待限制偏向。新192次未触发竞争，不能宣称策略收益；旧两轮变慢见[E4](#e4) |
| `ready_clock`／`on_ready_event` | `None`／`None` | 高级诊断：提供就绪时钟／观察回调，保留实际就绪和选择事件 | 必须可调用；不是独立性能策略或硬件事件。不要为了诊断更换业务语义 |
| `token_budget` | `None` | 显式`ChainTokenBudget(...)`启用在途W，作为防止下游积压的宽松高位安全护栏 | 仅同模型同角色F/M；不支持fused／Extract。W应绑定实际容量，不能把功能测试W134当正常推荐值 |
| `release_completed_audit` | `False` | 成功编码后尽早撤掉worker自己的审计列表引用，适合检查持有寿命 | 仅fused共享worker；Core／Ray／Daft有限链Python入口均有此项。普通Movie单Filter／session不经过该worker；record明确拒绝。只有CPU／组件证据，不证明RSS或完整查询收益 |
| `capacity` | `None` | 按执行模式选CoreChainCapacity或CoreRecordsCapacity；需要明确单项输入／结果空间时指定 | 类型须匹配模式；额度不覆盖全部关系、审计、进程RSS或GPU KV |
| `method_limits` | `None`，由owner推导 | `MethodLimits(input_bytes,state_bytes,result_bytes,stages)`限定记录继续执行时保留的状态 | 仅record；stage数须覆盖完整计划；不是vLLM预算 |
| `prepared_batching` | `None`，关闭 | `PreparedBatching("token_budget", None, B)`按完整输入token＋输出cap组织兼容就绪请求；适合检查不等长记录的供给 | record要求FIFO、`progression="record"`、W关闭，无每批行帽；现有关系屏障保留。已测范围及无冷查询加速结论见[PR84验收](../code/INFRA_STATUS.md#async-record-token-batches) |
| `batch_concurrency` | `None`；启用record组批后解析为1 | 未配置batch_feedback时固定尚有未结算计算成员的应用传输批数C_batch | 正整数且不超过成员容量R；仅非rolling record token组批。B、C_batch、R分别设置，不能当作vLLM物理批大小 |
| `batch_feedback` | `None`，关闭 | 显式`SupplyFeedbackConfig(max_batches, options=...)`或Movie／Session同名对象，让固定B的批槽C_batch反馈调整 | 初始C_batch须1、max_batches≤R，仅reference；与rolling、resident token及显式独立budget互斥，见[批槽入口](../code/src/experiments/movie_matrix.README.md#record-token-batch-entry) |
| `rolling_refill` | `False` | 完成单条即释放请求额度补位，B只组织提交 | 与批并发／批反馈互斥；Movie／Session旧预算模式固定C_request=R，显式budget下C与硬R分开；Python owner按request_window校验。isolated及rolling resident可选，见[复用范围](#reuse) |
| `preparation_mode` | Movie／Session为`"serial"` | 可选`"interleaved"`交错准备和派发，或`"event_driven"`根据已有推进通知准备；Python工厂对应`interleaved_preparation`／`event_driven_preparation` | 只接rolling；event_driven同时启用interleaved。可与无B及`resource_feedback`组合，不接批反馈；不创建新的模型控制器 |
| `experimental_skip_token_packing` | `False` | 仅实验：保留已有B配置而旁路其切包，包成员可能变化，字节／结果保护保持 | 只接record-local rolling，允许当前请求反馈；非rolling和fused拒绝。通常直接省略B即可，不需要此标志；见[所属接口与CPU范围](../code/src/execution_provider/adapters/README.md#fixed-rolling-token-packing-ablation-cpu-experiment-only)，无查询提速结论 |
| `request_feedback` | `None` | Python chain选项；Movie用`core_profile.admission`、Session用`profile.admission`选择请求级动态rolling | 须rolling且FIFO／record／W关闭；每查询从1起，不继承跨查询策略状态。B可省略；请求许可仍取原Core／actor／IPC和结果预留，见[入口与默认](../code/src/experiments/movie_matrix.README.md#record-token-batch-entry)；不据接口可用宣称性能收益 |
| `actor_owner`／`control_dir` | `None`／`None` | 高级集成：传入匹配的prepared-only async owner／控制文件目录 | 必须满足原owner身份和关闭责任；不是已支持跨查询模型复用的开关 |

不配置B的rolling按可用请求许可、兼容的模型／生成身份和IPC字节组成传输包，每个成员仍是完整提示。
无B、交错／事件准备、请求反馈的普通Movie与resident session入口已有[CPU用例](../code/tests/experiments/test_movie_token_packing_bypass.py)；
这不删除实际模型上下文检查，也不会因该组合额外给vLLM设置每轮token或sequence参数；用户显式引擎值仍按原配置传递。

PR84的B=17506、R=259及native128／fixed128使用Movie Q1全量输入长度统计和旧对照条件预设，矩阵`concurrency_search=False`，不是资源反馈自动选参。
token reference生成／统计、预分组、R推导和此前实验成本未计入本轮冷时间；正常查询仍自行准备和计量。数值来源、未找到的64→128决策与计时范围见[PR84范围说明](../code/INFRA_STATUS.md#async-record-token-batches)，不据此声称未知任务零先验自适应。

`LotusRecordChain(..., relation_barriers=False)`是方法合法性选项：非末端／重复Extract须显式True，等待成功EOF、完整结果和关系装配；不能作为“去掉屏障提速”的开关。
chain owner仍不接受普通records的`profile`／`admission`对象；本地动态rolling候选通过上述typed `request_feedback`接入。
普通Movie／session工厂将既有`core_profile.admission`解析为该选项，不改变其他链模式；不复用请求配置缓存。
rolling固定窗口或请求反馈可通过既有session的`lifecycle="resident"`显式复用模型，批槽模式仍不支持resident。

W使用[ChainTokenBudget](../code/src/execution_provider/adapters/lotus_chain_token_budget.py)：`active_tokens`必填；
`tokenizer`、匹配的`engine`、`tokenizer_signature`、`template_signature`及每阶段`expected_output`均须明确提供。
`expected_output`的值为`OutputTokenEstimate(tokens, provenance)`，只是显式输出估计；实际W预留始终为“完整chat输入估计＋该阶段生成cap”。
后继使用实际生成列重新准备和计量。单请求超W／上下文容量会拒绝，不自行截断、拆prompt或重试。
取消或unknown本身不释放W；权威终态或既有协议验证的生产者退出证明可结算预留，后者不把unknown结果改为成功。

<a id="budgets"></a>
## 批次、并发、准备和空间预算

这里B指每批累计token目标，W指所有在途请求的token预留总量；C的单位随入口明示，普通异步records按请求，静态批路径按批。历史“B1”常指每次一行，要看原字段。
应用组批、准备批、RPC／IPC包、vLLM计算批和可回收内存块不是同一个批次。

### 文本 records 资源

来源：[RecordsResources](../code/src/semantic_methods/lotus/records.py)。默认构造值不保证能直接用于每种后端；Core要求调用方覆盖batch rows。

| 字段 | 类型默认 | 实际用途与限制 |
|---|---|---|
| `cpu_workers` | 1 | 普通records的准备actor数量；record链由调用方准备，不创建Filter准备actor，增加此数不自动并行格式化；fused须1 |
| `gpu_workers` | 1 | 当前records必须1、张量并行为1；增大不是启用多GPU的方法 |
| `prepare_batch_rows` | 4 | 静态reference准备行数；普通Core和record链必须显式1；fused的准备由共享方法worker拥有，不单独使用该批大小 |
| `model_batch_rows` | 4 | 静态／fused的一组输入行数；普通Core和record链必须1，不是token B |
| `max_active_batches` | None | SDK 与配置入口一致；普通 async 使用已有完整 Core 预算、IPC 显式请求数或服务额度，缺来源启动前拒绝。静态／低层链需要有限声明，fused 仍只支持1。None 不表示无限 |
| `query_timeout_s` | None | 不默认截断整条查询；显式有限正值按原检查点计时。取消、模型长度和资源责任仍按各自接口处理 |
| `startup_timeout_s` | 120秒 | 有限启动等待；与整查询时长分开。原生Ray普通records通过Dataset自有context用于每个actor池的就绪等待，不是整个图总启动时间 |

整查询None已贯通普通／静态／有限链、原生执行及现有Movie／IMLane调用；只保留简单时间运算共用函数，未新增调度器。
IMLane四处原`min(60, query_timeout_s)`改用已有逐命令默认10秒，命令通信与等待任务完成分开；
显式启动、命令和关闭时间不再被二次截到600秒。实际作者实现和模型验证状态见[本批报告](../experiments/results/diagnostics/records_runtime_refactor_20261104/README.md#caller-query-duration)。
历史具名实验保留当时源码和显式配置，不随当前默认改写。

`CoreRecordsCapacity`默认`item_input_bytes=item_result_bytes=2MiB,metadata_bytes=2048,step_actions=16,poll_interval_s=0.01`。
`step_actions`是一次推进的动作预算，不是准备行数、提交包大小或请求总量上限。
`CoreChainCapacity`相同，但`item_result_bytes=8MiB`；这是一整个fused任务的结果预算。
两种容量类型均定义于[中性容量模块](../code/src/execution_provider/adapters/records_capacity.py)，共享同种字段检查；原 owner 导入继续指向同一类型，融合链仍按一个完整任务和阶段工作量计量。
普通Core高级`evaluate(..., max_inflight=None)`可在现有async owner声明上限内逐查询指定C，前一查询必须结束并结清；不会热扩容actor／IPC／模型。

`core_capacity.budget`默认None；显式完整对象才分开Core任务槽／输入／结果、硬请求R与方法驻留槽／字节，字段和入口见[独立预算](../code/src/experiments/movie_matrix.README.md#显式独立资源预算默认关闭本地cpu候选)。仅普通async Filter与rolling token接入；C≤硬R，sync／fused／非rolling批槽拒绝。预算由部署声明，不是自动发现物理余量，也不完整覆盖查询关系、审计、Python／Ray副本或RSS。

C是当前提交窗口，R是有限请求声明；两者都不是vLLM每轮sequence数或物理RAM。
完整独立budget才把任务驻留、请求与结果存储分别声明；未使用它的路径仍可能从同一个请求声明推导其他额度。
IPC可以另有更小的请求／结果槽或总字节，实际派发同时满足这些额度，不因为C增长就扩大存储。
服务payload池也只分配调用方声明的逻辑字节；rolling还需完整`service_delivery`结果声明，不能把池总量视为可用物理RAM。

### 异步IPC和方法状态

来源：[AsyncEngineLimits](../code/src/serving/backends/vllm_async_engine.py)、[actor组装](../code/src/execution_provider/adapters/lotus_records_async_actor.py)。
直接构造必须给 `max_inflight`；`AsyncEngineProcess` 和 `VllmAsyncEngine` 必须接收明确 `limits`，不再补内部8。
`result_slots`／`command_slots` 省略或 null 时跟随声明请求数；省略或 null 的 `input_bytes` 取请求数×单项输入，`result_bytes` 取结果槽数×单项结果，显式较小额度保持。
`item_input_bytes=item_result_bytes=2MiB`、`control_slots=16`、`control_frame_bytes=64KiB`、`feedback_interval_s=0.0` 仍为原值。16请求的默认结果总字节为32MiB；若显式仅给16MiB，仍只容八份完整预留。
旧 R 推导路径只为省略的 IPC 字段提供默认值；完整 IPC、Core 预算或服务声明按各自已分配额度解析，单项沿所属 Core 配置。动态初始 C 不代替这些额度。
完整独立budget下，省略的IPC请求／命令槽取`active_requests`，结果槽取`held_tasks`，输入／结果总字节取对应预算；控制预留沿原协议公式。
允许部分IPC覆盖，完整显式字段和较小额度保持，不会为匹配C扩大；各层仍分别记账。有动态反馈时，反馈间隔由已校验admission接线。
这些数值是有限交接／保留额度，不表示 GPU 显存分区或 RSS 上限。完整 JSON 与 typed 声明同义；部分覆盖中的两种槽位与总输入／结果字节 null 表示未覆盖，继承所属 Core 的默认；其他字段仍须合法。
普通 async 入口省略 R 时使用已有完整 Core 预算、typed IPC、JSON 显式 `max_inflight` 或服务 payload 字节；只给请求数的 JSON 可复用其余默认，无来源则拒绝，不从输入总数或 native seq 猜额度。静态／非 rolling prepared／直接低层链仍需其支持的有限声明。
默认`method_limits`从item容量及阶段数推导；状态不足会拒绝，不能靠只放大C绕过状态容量。

IMLane 仓内桥必须接收资源声明中的请求数：当前 CLI 为
`imlane_records PORT UDF_PATH FUNCTION MAX_PENDING_BLOCKS [imlane.records.v2]`。
同一正整数传到 C++ Limits 和 Python ready 核验，结果 carrier 使用实际回执，不再内部给2或另设窗口；
旧 pending≤128 条件删除，按原生整数范围解析。单块行数、整查询行数和字节保护仍保留。
源码接线及独立标准 C++17 组件已通过 CPU 检查；完整 Arrow／作者桥尚未构建运行，旧两文件来源签名的 binary 不能直接复用。
[准确版本和正常 Movie／chain／cascade 检查](../experiments/results/diagnostics/records_runtime_refactor_20261104/README.md#runtime-structure-and-bridge-capacity)
不代表物理内存自动授予或真实模型容量。

## 配置片段

以下只展示准确字段，嵌入已有合法模型、方法和资源配置；不代表最佳数值，也不会自动启动任务。

普通records固定异步（Python）：

```python
from src.semantic_methods.lotus.records import RecordsResources
from src.execution_provider.adapters.lotus_records_core import create_records_core

# C=4只是示例；async外层C不按engine.max_num_seqs截断，仍须满足Core/IPC资源检查。
resources = RecordsResources(cpu_workers=1, gpu_workers=1,
    prepare_batch_rows=1, model_batch_rows=1, max_active_batches=4)
owner = create_records_core(method, engine, generation, resources,
    profile={"mode": "async", "max_inflight": 4})
```

当前请求反馈在普通Movie JSON中使用下述配置；session将键名换为`profile`，其它必需字段沿用合法的完整配置：

```json
{"core_profile": {"mode": "async", "admission": {"kind": "resource_feedback"}}}
```

该配置从一个请求开始，后续许可仍受调用方声明的Core／actor／IPC和结果容量管理。
非rolling批反馈的 `batch_feedback` 另按[批次配置](#budgets)声明，不与rolling请求反馈混用。

无B的rolling与事件准备可使用同一入口；这里有意省略`prepared_batching`，其它必需字段及有限容量来源仍由完整配置提供：

```json
{"rolling_refill": true, "preparation_mode": "event_driven", "core_profile": {"mode": "async", "admission": {"kind": "resource_feedback"}}}
```

Session同样把`core_profile`换为`profile`。`serial`／`interleaved`／`event_driven`改变准备与派发的推进方式，不改变逻辑算子、单条完整请求或vLLM默认值。

记录级链的固定FIFO/count（Python；同一模型部署）：

```python
from src.execution_provider.adapters.lotus_record_chain_core import SemLoomRecordChainCore

owner = SemLoomRecordChainCore(engine, resources,
    execution="record_local_sections", token_budget=None, ready_order="fifo")
```

仅在同模型同角色F/M计划中单独试后继优先：

```python
from src.execution_provider.adapters.lotus_record_chain_core import SemLoomRecordChainCore
from src.semantic_methods.driver import SuccessorFirst

owner = SemLoomRecordChainCore(engine, resources,
```
